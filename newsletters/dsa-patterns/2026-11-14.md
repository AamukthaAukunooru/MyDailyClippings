## The Two Elevators Problem

Imagine you're managing a very peculiar building with only two elevators, and they both operate under a strict "last person in, first person out" rule. That's right, they're like giant stacks. If someone steps into an empty elevator, they're at the bottom. The next person stands on top of them, and so on. To get the first person out, everyone else has to step off first.

Now, here's the catch: people arriving at your building want to form a traditional queue. They expect "first person in, first person out" service. How can you use these two LIFO, or **Last-In, First-Out**, elevators to simulate a FIFO, or **First-In, First-Out**, waiting line? This is the core challenge of today's problem: implementing a **queue** using only **stack** operations.

Specifically, we need to support four standard queue operations:
1.  **`push(x)`**: Add element `x` to the back of the queue.
2.  **`pop()`**: Remove the element from the front of the queue and return it.
3.  **`peek()`**: Get the front element without removing it.
4.  **`empty()`**: Check if the queue is empty.

And we can only use standard stack operations: `push` (add to top), `pop` (remove from top), `peek` (look at top), and `empty`.

Let's consider a small example of how our queue should behave:
-   We `push` the number 1.
-   Then `push` 2.
-   Then `push` 3.
-   If we then `pop`, we should get 1, because it was the first one pushed.
-   If we `push` 4.
-   And then `pop`, we should get 2.
-   If we `peek`, we should see 3.
-   If we `pop` again, we should get 3.
-   And finally, if we `pop` one more time, we should get 4.

This problem forces us to think about the fundamental differences between stacks and queues and how to bridge that gap with limited tools.

## The Core Idea: Reversing Order with Two Stacks

The fundamental difference between a stack and a queue is the order in which elements are retrieved. A stack gives you the most recently added item. A queue gives you the least recently added item. To get the "least recently added" item from a stack, you'd have to remove all the items that came after it. This reversal is the key.

Imagine our two "elevators" or stacks. Let's call them `inputStack` and `outputStack`.

When a new person arrives (a `push` operation), it's easiest to just put them into `inputStack`. This stack will accumulate elements in the order they arrive, but with the most recent at the top. So, if we push 1, then 2, then 3, `inputStack` would look like [1, 2, 3] from bottom to top, with 3 at the very top.

Now, what happens when someone wants to leave the queue (a `pop` or `peek` operation)? We need the *first* person who arrived, which is 1 in our example. But 1 is at the bottom of `inputStack`. To get it, we'd have to `pop` 3, then `pop` 2, and *then* we could `pop` 1.

This is where the second stack, `outputStack`, comes in handy. If we take all the elements from `inputStack` and `pop` them one by one, pushing each onto `outputStack`, something interesting happens.
-   `inputStack`: [1, 2, 3] (bottom to top)
-   Pop 3 from `inputStack`, push 3 to `outputStack`. `inputStack`: [1, 2], `outputStack`: [3]
-   Pop 2 from `inputStack`, push 2 to `outputStack`. `inputStack`: [1], `outputStack`: [3, 2]
-   Pop 1 from `inputStack`, push 1 to `outputStack`. `inputStack`: [], `outputStack`: [3, 2, 1]

Now, `outputStack` has the elements in reverse order of how they were pushed into `inputStack`. The first element pushed (1) is now at the *top* of `outputStack`! This means we can simply `pop` from `outputStack` to get the true "front" of our queue.

The crucial insight is this: we only need to perform this transfer operation when `outputStack` is empty and we need to `pop` or `peek`. As long as `outputStack` has elements, they are already in the correct FIFO order for retrieval. New elements always go to `inputStack`.

## Building Our Queue: Step by Step

Let's formalize the operations using our two stacks, `inputStack` and `outputStack`. Both start empty.

1.  **`push(x)` operation:**
    -   This is the simplest. We just add the new element `x` to the `inputStack`.
    -   Example: `inputStack.push(x)`

2.  **`pop()` operation:**
    -   First, we need to ensure `outputStack` has elements ready to be popped.
    -   We check if `outputStack` is currently empty.
    -   If `outputStack` *is* empty:
        -   We need to transfer all elements from `inputStack` to `outputStack`.
        -   While `inputStack` is not empty:
            -   Pop an element from `inputStack`.
            -   Push that element onto `outputStack`.
    -   Once `outputStack` is guaranteed to have elements (either it already had them, or we just transferred them), we can safely `pop` from `outputStack`.
    -   The value returned by `outputStack.pop()` is the front element of our queue.

3.  **`peek()` operation:**
    -   This operation is very similar to `pop()`. We follow the exact same logic to ensure `outputStack` is not empty and contains the correct elements.
    -   Check if `outputStack` is currently empty.
    -   If `outputStack` *is* empty:
        -   Transfer all elements from `inputStack` to `outputStack` as described for `pop()`.
    -   Once `outputStack` is ready, we simply `peek` at its top element.
    -   The value returned by `outputStack.peek()` is the front element of our queue, without removing it.

4.  **`empty()` operation:**
    -   Our queue is empty if and only if *both* `inputStack` and `outputStack` are empty.
    -   Example: return `inputStack.empty() AND outputStack.empty()`

This two-stack approach elegantly solves the problem by using one stack to collect new elements and the other to serve them in the correct order, with a clever transfer mechanism to reverse the order when needed.

## Tracing an Example

Let's trace our earlier example: `push(1)`, `push(2)`, `push(3)`, `pop()`, `push(4)`, `pop()`, `peek()`, `pop()`, `empty()`, `pop()`, `empty()`.

Initially: `inputStack` = [], `outputStack` = []

1.  **`push(1)`**:
    -   `inputStack` becomes [1] (1 is at the bottom, then top).
    -   `outputStack` remains [].
2.  **`push(2)`**:
    -   `inputStack` becomes [1, 2].
    -   `outputStack` remains [].
3.  **`push(3)`**:
    -   `inputStack` becomes [1, 2, 3].
    -   `outputStack` remains [].

4.  **`pop()`**:
    -   `outputStack` is empty.
    -   **Transfer**:
        -   Pop 3 from `inputStack`, push to `outputStack`. `inputStack` = [1, 2], `outputStack` = [3].
        -   Pop 2 from `inputStack`, push to `outputStack`. `inputStack` = [1], `outputStack` = [3, 2].
        -   Pop 1 from `inputStack`, push to `outputStack`. `inputStack` = [], `outputStack` = [3, 2, 1].
    -   Now, `outputStack` is not empty. Pop from `outputStack`. It returns **1**.
    -   State: `inputStack` = [], `outputStack` = [3, 2].

5.  **`push(4)`**:
    -   `inputStack` becomes [4].
    -   `outputStack` remains [3, 2].

6.  **`pop()`**:
    -   `outputStack` is not empty.
    -   Pop from `outputStack`. It returns **2**.
    -   State: `inputStack` = [4], `outputStack` = [3].

7.  **`peek()`**:
    -   `outputStack` is not empty.
    -   Peek from `outputStack`. It returns **3**.
    -   State: `inputStack` = [4], `outputStack` = [3] (no change, peek doesn't remove).

8.  **`pop()`**:
    -   `outputStack` is not empty.
    -   Pop from `outputStack`. It returns **3**.
    -   State: `inputStack` = [4], `outputStack` = [].

9.  **`empty()`**:
    -   `inputStack` is not empty ([4]). `outputStack` is empty.
    -   Returns **false**.

10. **`pop()`**:
    -   `outputStack` is empty.
    -   **Transfer**:
        -   Pop 4 from `inputStack`, push to `outputStack`. `inputStack` = [], `outputStack` = [4].
    -   Now, `outputStack` is not empty. Pop from `outputStack`. It returns **4**.
    -   State: `inputStack` = [], `outputStack` = [].

11. **`empty()`**:
    -   `inputStack` is empty. `outputStack` is empty.
    -   Returns **true**.

The trace confirms that our two-stack queue behaves exactly as a standard FIFO queue should.

## Performance and Pitfalls

Let's analyze the efficiency of this approach.

**Time Complexity:**
-   **`push(x)`**: This operation always involves a single push onto `inputStack`. This is an **O(1)** operation.
-   **`pop()` and `peek()`**: This is where it gets interesting. In the worst case, if `outputStack` is empty, we have to transfer all `N` elements from `inputStack` to `outputStack`. This would take **O(N)** time. However, this O(N) operation doesn't happen every time. Each element is pushed onto `inputStack` once, moved to `outputStack` once, and popped from `outputStack` once. Over a sequence of `N` operations, the total work for moving elements is proportional to `N`. Therefore, the **amortized time complexity** for `pop()` and `peek()` is **O(1)**. This means the average cost per operation over a long sequence of operations is constant, even if individual operations can be more expensive.
-   **`empty()`**: This operation simply checks the emptiness of two stacks, which is **O(1)**.

**Space Complexity:**
-   In the worst case, all elements are either in `inputStack` or `outputStack` (or being transferred between them). If our queue holds `N` elements, we will use **O(N)** space for the two stacks.

**Edge Cases:**
-   **Empty Queue**: If you call `pop()` or `peek()` on an empty queue, our logic will correctly identify that both stacks are empty and either throw an error (as standard stack `pop`/`peek` might) or return a specified null/default value. The `empty()` method correctly returns true.
-   **Single Element**: The logic handles a single element correctly, pushing it to `inputStack`, then transferring it to `outputStack` when `pop`/`peek` is called, and then retrieving it.

**Common Misconceptions:**
-   **`pop()` is always O(N)**: A frequent mistake is to assume that because `pop()` *can* take O(N) time, its complexity is always O(N). Understanding **amortized analysis** is key here. The total cost over many operations is what matters.
-   **Forgetting to check both stacks for `empty()`**: If you only check `outputStack`, you might incorrectly report the queue as empty when elements are waiting in `inputStack`.
-   **Unnecessary transfers**: Some might think of transferring elements back and forth. The key is that elements only move from `inputStack` to `outputStack` when `outputStack` is entirely depleted. They never move back.

## Why This Matters and What's Next

This problem is a fantastic illustration of how to simulate one data structure using another. It deepens our understanding of the fundamental properties of stacks and queues, particularly their LIFO and FIFO behaviors, and how to manipulate order. This skill of transforming data structures or operations is incredibly valuable in algorithm design. It teaches us to think creatively about how to achieve desired behavior with limited or different tools.

For interviewers, this problem is an excellent way to gauge your understanding of data structures, your ability to think through edge cases, and your grasp of time complexity, especially the concept of amortized analysis.

**Follow-up questions** might involve discussing the amortized analysis in more detail, or asking if the solution would change if `push` operations were much more frequent than `pop` and `peek`, or vice versa. Our current solution is balanced for all operation types.

A classic **related problem** that uses a similar two-data-structure simulation pattern is **Implement Stack using Queues (LeetCode 225)**. In that problem, you're given queues and need to simulate a stack. It's the inverse challenge and often solved with a similar two-container approach, but with different logic for transfers. Another related concept is **Design Circular Queue (LeetCode 622)**, which focuses on efficient array-based queue implementations.

In summary, implementing a queue with two stacks leverages the order-reversing property of transferring elements between stacks. New elements go into an `inputStack`, and when elements need to be retrieved from the front of the queue, they are transferred to an `outputStack` to reverse their order. This approach provides amortized constant time complexity for all operations, making it an efficient and elegant solution.
