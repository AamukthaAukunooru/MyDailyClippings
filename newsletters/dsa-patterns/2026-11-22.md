Have you ever looked at Roman numerals and thought, "That looks simple enough"? I, V, X, L, C, D, M. Just add them up, right? "III" is three. "LVIII" is fifty-eight. But then you stumble upon something like "IV" or "CM", and suddenly, your simple addition falls apart. "IV" isn't one plus five, it's four. "CM" isn't one hundred plus one thousand, it's nine hundred. This little twist, the **subtractive rule**, is what makes converting Roman numerals to integers a classic entry-level coding interview problem. It teaches us to look beyond the obvious and consider how the order of elements can change their meaning.

## The Problem: Roman to Integer

The task is straightforward: given a Roman numeral as a string, convert it to its integer equivalent. We're given the basic mappings:
*   I represents 1
*   V represents 5
*   X represents 10
*   L represents 50
*   C represents 100
*   D represents 500
*   M represents 1000

The Roman numerals are usually written from largest to smallest value from left to right. For example, "XXI" is twenty-one (10 + 10 + 1). However, there are six special cases where a smaller numeral placed before a larger numeral indicates subtraction:
*   I placed before V (5) makes 4 (IV)
*   I placed before X (10) makes 9 (IX)
*   X placed before L (50) makes 40 (XL)
*   X placed before C (100) makes 90 (XC)
*   C placed before D (500) makes 400 (CD)
*   C placed before M (1000) makes 900 (CM)

The input Roman numeral is guaranteed to be valid and within the range from one to three thousand nine hundred ninety-nine. Let's take "MCMXCIV" as an example. If we just added everything up: M (1000) + C (100) + M (1000) + X (10) + C (100) + I (1) + V (5) would give us two thousand two hundred sixteen, which is incorrect. The correct answer is one thousand nine hundred ninety-four.

## Building Intuition: The Subtractive Twist

Our first thought might be to just iterate from left to right, adding each symbol's value to a running total. This works for many cases, like "III" or "MDCLXVI". The problem arises when we encounter one of those special subtractive pairs. When we see an 'I' followed by a 'V', how do we know it's a four and not just a one that happens to be next to a five?

If we process from left to right, when we see 'I' and then 'V', we have to "look ahead". We see 'I', get its value (one). Then we see 'V', get its value (five). Since one is less than five, we realize it's a subtractive case. This means we should have subtracted the 'I' instead of adding it, or perhaps added 'V' minus 'I'. This "looking ahead" logic can be a bit clunky to implement cleanly.

What if we change our perspective? What if we process the Roman numeral string from **right to left**?

## The Key Insight: Reading Backwards

Imagine you're reading "MCMXCIV" from right to left.
You see 'V'. That's five. Add it to your total. Total is now five.
Next, you see 'I'. Its value is one. You compare it to the value you just processed, 'V' (which was five). Since one is *less than* five, you know this 'I' is part of a subtractive pair. So, instead of adding one, you subtract it from your total. Total is now four.
Next, you see 'C'. Its value is one hundred. You compare it to the value you just processed, 'I' (which was one). Since one hundred is *greater than or equal to* one, you add one hundred. Total is now one hundred four.
Next, you see 'X'. Its value is ten. You compare it to 'C' (one hundred). Since ten is *less than* one hundred, you subtract ten. Total is now ninety-four.

Do you see the pattern? When moving from right to left, if the current symbol's value is *smaller* than the value of the symbol immediately to its right (which we just processed), it means we've encountered a subtractive case. In all other scenarios, including the very first character we process (the rightmost one), we simply add its value. This elegant approach is a form of **greedy algorithm**, where we make the best local decision at each step to arrive at the correct global solution.

## The Optimal Approach: Step-by-Step

Let's break down the algorithm for converting a Roman numeral to an integer using this right-to-left strategy:

1.  **Create a Value Map:** First, we need a quick way to look up the integer value for each Roman symbol. We'll use a **hash map** (also known as a dictionary or associative array) for this.
    *   `'I'` maps to 1
    *   `'V'` maps to 5
    *   `'X'` maps to 10
    *   `'L'` maps to 50
    *   `'C'` maps to 100
    *   `'D'` maps to 500
    *   `'M'` maps to 1000

2.  **Initialize Variables:**
    *   `total_sum`: This will store our final integer result, initialized to zero.
    *   `previous_value`: This will store the integer value of the Roman symbol we processed in the *last* iteration, initialized to zero. This helps us make the comparison for the subtractive rule.

3.  **Iterate Right to Left:** We will loop through the Roman numeral string starting from the very last character and moving towards the first character.

4.  **Process Each Symbol:** Inside the loop, for each `current_character`:
    *   Look up its `current_value` using our hash map.
    *   **Compare:** Check if `current_value` is less than `previous_value`.
        *   If `current_value < previous_value`: This is a subtractive case. We subtract `current_value` from `total_sum`.
        *   Else (if `current_value >= previous_value`): This is an additive case. We add `current_value` to `total_sum`.
    *   **Update `previous_value`:** After processing the current character, set `previous_value` to `current_value` for the next iteration.

5.  **Return `total_sum`:** Once the loop finishes, `total_sum` will hold the correct integer value.

## Concrete Example: "MCMXCIV"

Let's trace this algorithm with our example, "MCMXCIV".

*   Our value map is ready.
*   `total_sum = 0`
*   `previous_value = 0`

We iterate from right to left:

1.  **Character 'V' (index 6):**
    *   `current_value` for 'V' is 5.
    *   Is 5 < `previous_value` (0)? No.
    *   Add 5 to `total_sum`. `total_sum` is now 5.
    *   Update `previous_value` to 5.

2.  **Character 'I' (index 5):**
    *   `current_value` for 'I' is 1.
    *   Is 1 < `previous_value` (5)? Yes.
    *   Subtract 1 from `total_sum`. `total_sum` is now 4.
    *   Update `previous_value` to 1.

3.  **Character 'C' (index 4):**
    *   `current_value` for 'C' is 100.
    *   Is 100 < `previous_value` (1)? No.
    *   Add 100 to `total_sum`. `total_sum` is now 104.
    *   Update `previous_value` to 100.

4.  **Character 'X' (index 3):**
    *   `current_value` for 'X' is 10.
    *   Is 10 < `previous_value` (100)? Yes.
    *   Subtract 10 from `total_sum`. `total_sum` is now 94.
    *   Update `previous_value` to 10.

5.  **Character 'M' (index 2):**
    *   `current_value` for 'M' is 1000.
    *   Is 1000 < `previous_value` (10)? No.
    *   Add 1000 to `total_sum`. `total_sum` is now 1094.
    *   Update `previous_value` to 1000.

6.  **Character 'C' (index 1):**
    *   `current_value` for 'C' is 100.
    *   Is 100 < `previous_value` (1000)? Yes.
    *   Subtract 100 from `total_sum`. `total_sum` is now 994.
    *   Update `previous_value` to 100.

7.  **Character 'M' (index 0):**
    *   `current_value` for 'M' is 1000.
    *   Is 1000 < `previous_value` (100)? No.
    *   Add 1000 to `total_sum`. `total_sum` is now 1994.
    *   Update `previous_value` to 1000.

The loop finishes. Our final `total_sum` is 1994, which is the correct integer for "MCMXCIV".

## Complexity Analysis

*   **Time Complexity:** The algorithm iterates through the Roman numeral string exactly once, from right to left. Each step involves a constant number of operations: a hash map lookup, a comparison, and an addition or subtraction. Therefore, if the length of the Roman numeral string is N, the time complexity is **O(N)**. This is very efficient, as we only need to "touch" each character once.

*   **Space Complexity:** We use a hash map to store the seven Roman symbol-to-integer mappings. This map has a fixed size, regardless of the input string's length. We also use a few variables for `total_sum`, `previous_value`, and `current_value`. All of these take up a constant amount of memory. Thus, the space complexity is **O(1)**, meaning it's constant and doesn't grow with the input size.

## Edge Cases and Misconceptions

The problem statement simplifies things by guaranteeing a valid Roman numeral within a specific range. This means we don't have to worry about invalid inputs like "IIX" or an empty string.

A common misconception is trying to handle all six subtractive cases explicitly with if-else statements (e.g., "if I and next is V, then add 4"). While that works, the right-to-left approach is more general and elegant because it captures the *rule* of subtraction (smaller before larger) rather than listing out every specific instance. It handles single-character strings correctly too, as the first character processed (the only one) will always have its value added since `previous_value` starts at zero.

## Why This Matters

This problem, despite being "easy," is a great learning exercise for several reasons:

1.  **String Parsing:** It's a fundamental string manipulation task, requiring careful character-by-character processing.
2.  **Algorithm Design:** It highlights how choosing the right traversal direction (right-to-left here) can significantly simplify the logic and lead to a cleaner, more efficient solution.
3.  **Greedy Approach:** The solution uses a greedy strategy, making locally optimal decisions that combine to form a globally optimal answer.
4.  **Hash Map Usage:** It demonstrates the utility of hash maps for fast lookups, which is a common pattern in many data structure and algorithm problems.
5.  **Attention to Detail:** The subtractive rule is a small detail, but it completely changes the problem. Paying attention to such nuances is crucial in coding interviews.

## Related Problems

Once you've mastered Roman to Integer, you might want to try these related problems:

1.  **Integer to Roman (LeetCode 12, Medium):** This is the inverse problem. Given an integer, convert it to a Roman numeral. It often involves a similar greedy approach, but instead of iterating through the string, you iterate through a predefined list of Roman numeral values (like 1000, 900, 500, 400, etc.) and subtract them from the input number until it reaches zero.
2.  **Length of Last Word (LeetCode 58, Easy):** While different in its specific rules, this problem also benefits from iterating a string from right to left to find the last word, often skipping trailing spaces. It reinforces the idea that sometimes starting from the end is more efficient.

In summary, converting Roman numerals to integers is a neat problem that goes beyond simple addition. The key insight is to process the string from right to left, using a running total and comparing each character's value to the one immediately to its right. This greedy approach allows us to correctly handle both additive and subtractive cases in a single, elegant pass, resulting in an efficient and robust solution.
