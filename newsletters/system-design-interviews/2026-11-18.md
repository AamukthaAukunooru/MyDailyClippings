**Interviewer:** Good morning. Today, we're designing the Facebook News Feed. Your task is to outline a system that allows users to see a personalized stream of content from their friends and pages they follow. Let's assume we're building the core feed generation and delivery mechanism.

## 1. Requirements

**Candidate:** Good morning. I'd like to start by clarifying the functional and non-functional requirements.

**Interviewer:** Sounds good.

**Candidate:** Functionally, the core requirement is for a user to view a feed of posts from people and pages they follow, ordered chronologically or by relevance. Users should also be able to create new posts. For simplicity, let's assume posts can contain text and a single image. We don't need to cover comments, likes, or shares for now, just the ability to display posts.

**Interviewer:** That's a good scope.

**Candidate:** For non-functional requirements, what kind of scale are we talking about? How many daily active users, and what's the expected latency for loading the feed?

**Interviewer:** Let's assume two hundred million daily active users, or DAU. The News Feed is critical, so we need low latency. Aim for a feed load time of under two hundred milliseconds ninety-nine percent of the time. Availability should be high, say four nines, and consistency can be eventual, as long as posts eventually appear in the feed.

**Candidate:** Two hundred million DAU, two hundred milliseconds latency, four nines availability, and eventual consistency. Got it.

## 2. Back-of-the-envelope estimates

**Candidate:** Next, let's do some back-of-the-envelope estimates to understand the scale.

**Interviewer:** Go ahead.

**Candidate:** With two hundred million DAU, let's estimate how many times a user refreshes their feed. A typical user might check their feed ten times a day. So, two hundred million users times ten feed loads per day gives us two billion feed loads per day. Dividing that by eighty-six thousand four hundred seconds in a day, we get approximately twenty-three thousand feed requests per second on average. This is a significant read load.

**Interviewer:** That's a good baseline for reads. What about writes?

**Candidate:** For writes, let's assume a user creates a post once every ten days on average. So, two hundred million users divided by ten days gives us twenty million posts per day. Dividing that by eighty-six thousand four hundred seconds, we get roughly two hundred and thirty posts per second. This confirms that the system is heavily read-dominant, with a read-to-write ratio of about one hundred to one.

**Interviewer:** That's a crucial observation.

**Candidate:** For storage, if each post is, say, one kilobyte on average, including metadata and a pointer to an image, and we store posts for five years, that's twenty million posts per day times three hundred and sixty-five days per year times five years. That's about thirty-six point five billion posts. At one kilobyte per post, that's roughly thirty-six point five terabytes of raw post data. This doesn't include image storage, which would be much larger, likely petabytes, but we can offload images to a separate object storage system like Amazon S3 or Google Cloud Storage.

**Interviewer:** Good point on image storage. What about bandwidth?

**Candidate:** For bandwidth, if each feed load retrieves, say, fifty posts, and each post is one kilobyte, that's fifty kilobytes per feed load. Multiplying fifty kilobytes by twenty-three thousand requests per second, we get about one point one five gigabytes per second of outgoing data for the feed content itself. Adding overhead, we're looking at a few gigabytes per second, which is substantial but manageable with distributed systems and CDNs.

## 3. API design

**Candidate:** Moving on to API design. For the core functionality, we'll need two main endpoints.

**Interviewer:** Describe them.

**Candidate:** First, for fetching the feed, I'd propose a `GET /feed` endpoint. It would take optional query parameters like `user_id` to specify whose feed to fetch, `limit` for the number of posts to return, and `before` or `after` for pagination, typically a timestamp or a post ID to fetch older or newer posts. The response would be a JSON array of post objects, each containing the post ID, author ID, author name, content, timestamp, and a URL to the image if present.

**Interviewer:** What about creating posts?

**Candidate:** For creating posts, I'd define a `POST /posts` endpoint. It would take a JSON body containing the `user_id` of the author, the `content` of the post, and optionally an `image_url` if an image is being uploaded. It would return the newly created post ID and a success status. For idempotency, we could also include an `idempotency_key` in the request header, which is a common pattern to ensure that if a client retries a request, it doesn't create duplicate resources.

## 4. Data model and storage choice

**Candidate:** Now, let's discuss the data model and storage choices. We'll need to store users, their follows, and posts.

**Interviewer:** What's your approach?

**Candidate:** I'd use a relational database, like PostgreSQL or MySQL, for `Users` and `Follows` tables. These tables have strong consistency requirements and benefit from relational integrity.
*   The `Users` table would have `user_id` (primary key), `username`, `email`, etc.
*   The `Follows` table would have `follower_id` and `followee_id`, with a composite primary key and indexes to quickly find who a user follows and who follows a user.

For `Posts`, given the high write throughput and the need to scale horizontally, I'd choose a NoSQL wide-column store like Apache Cassandra or Google Cloud Bigtable. These databases are excellent for storing large volumes of data with high write availability and predictable read performance across many nodes.
*   The `Posts` table would store `post_id` (primary key), `user_id`, `content`, `image_url`, `timestamp`, and any other relevant metadata. We'd partition this table by `user_id` to distribute writes and reads.

**Interviewer:** Why not use a relational database for posts as well?

**Candidate:** A relational database would struggle with the write scale for posts and horizontal scaling would be more complex, requiring sharding at the application level. A wide-column store is designed for this kind of scale from the ground up, offering built-in sharding and high availability through replication, which aligns with our four nines availability requirement and eventual consistency model.

## 5. High-level design

**Candidate:** For the high-level design, let's walk through the read and write paths.

**Interviewer:** Let's start with the write path, when a user creates a post.

**Candidate:** The write path begins when a user sends a `POST /posts` request. This hits a load balancer, which distributes it to an API Gateway. The API Gateway authenticates and rate limits the request, then forwards it to a Post Service. The Post Service validates the post content, stores it in our `Posts` NoSQL database, and then publishes a "Post Created" event to a message queue, like Apache Kafka. This is a common pattern for decoupling services and enabling asynchronous processing.

**Interviewer:** What happens after the event is published?

**Candidate:** A dedicated Fanout Service consumes these events from the message queue. This service is responsible for distributing the new post to the feeds of all relevant followers. This is known as the fan-out on write or push model. For each follower, the Fanout Service adds the new post's ID to their personalized "inbox" or feed. These inboxes are stored in a highly performant, low-latency data store, like Redis or a similar in-memory data store, specifically optimized for fast reads.

**Interviewer:** And the read path?

**Candidate:** For the read path, when a user requests their feed via `GET /feed`, the request again goes through the load balancer and API Gateway to a Feed Service. The Feed Service queries the user's pre-generated inbox in Redis, retrieves a list of post IDs, and then fetches the full post details from the `Posts` NoSQL database. This is the cache-aside pattern, where Redis acts as a cache for the feed structure, and the NoSQL database as the source of truth for post content. Finally, the Feed Service aggregates this data, sorts it, and returns it to the user. Images would be served directly from a Content Delivery Network, or CDN, to minimize latency and bandwidth on our backend.

## 6. Deep dives

**Interviewer:** Let's dive deeper into the fan-out mechanism. What are the trade-offs of fan-out on write versus fan-out on read, and why did you choose the push model?

**Candidate:** The choice between fan-out on write, or push model, and fan-out on read, or pull model, is critical. The push model, which I chose, pre-computes each user's feed when a new post is created. This makes feed retrieval very fast, as it's just reading from a pre-populated list. This is ideal for our read-heavy workload and strict two hundred millisecond latency requirement. The main trade-off is the high write amplification: a single post by a celebrity with millions of followers can result in millions of writes to individual inboxes. This is a challenge for the Fanout Service.

**Interviewer:** How would you handle a celebrity user with millions of followers?

**Candidate:** For celebrity users, a pure fan-out on write can become a bottleneck, leading to a "thundering herd" problem on the Fanout Service and Inbox Service. Here, I'd implement a hybrid approach. For users with a very large number of followers, say over a hundred thousand, we could switch to a fan-out on read model for their posts. When a regular user requests their feed, if they follow a celebrity, the Feed Service would merge the pre-computed inbox with a real-time query of the celebrity's recent posts. This reduces the write load for celebrity posts but adds a small amount of read latency for feeds that include them. This is a practical trade-off to balance system load and user experience.

**Interviewer:** What happens if a node in your Fanout Service dies while processing a post?

**Candidate:** If a Fanout Service node dies, the message queue, like Kafka, is crucial. Messages are persisted and acknowledged only after successful processing. If a worker dies, the message remains unacknowledged and can be reprocessed by another worker. To prevent duplicate entries in user inboxes, the Fanout Service must be designed to be idempotent. This means that adding the same post ID to an inbox multiple times should have the same effect as adding it once, for example, by using set operations in Redis or ensuring unique entries.

## 7. Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss bottlenecks, failure modes, and trade-offs.

**Interviewer:** What's the biggest bottleneck you foresee?

**Candidate:** The biggest potential bottleneck is the Fanout Service and the Inbox Service, especially with the hybrid approach for celebrities. Even with optimizations, the write load on Redis for user inboxes can be immense. We'd need to shard the Redis clusters by `user_id` to distribute this load horizontally. This is a form of data partitioning. We'd also need robust monitoring and auto-scaling for the Fanout Service workers.

**Interviewer:** What about data consistency? You mentioned eventual consistency.

**Candidate:** Yes, eventual consistency is a key trade-off. A user might post something, and it might take a few seconds for it to appear in all their followers' feeds. This is generally acceptable for a News Feed, as strict immediate consistency isn't a hard requirement. The alternative, strong consistency, would add significant latency and complexity, making it harder to meet our two hundred millisecond target.

**Interviewer:** How does this behave at ten times the load?

**Candidate:** At ten times the load, meaning two billion DAU, our current design would face significant challenges. The twenty-three thousand reads per second would become two hundred and thirty thousand reads per second, and two hundred and thirty writes per second would become two thousand three hundred writes per second.
*   The `Posts` NoSQL database would need more shards and potentially more powerful nodes.
*   The Fanout Service would require a massive increase in worker instances and more sophisticated load balancing.
*   The Redis clusters for user inboxes would need even more aggressive sharding and potentially a multi-tier caching strategy, perhaps with a flash-backed cache for less active users.
*   The hybrid fan-out strategy would become even more critical, possibly extending the celebrity threshold to more users. We might also need to introduce more sophisticated ranking algorithms earlier in the pipeline to reduce the amount of data fetched for each feed request. This is a principle of "doing less work" to scale.

## 8. Wrap-up

**Candidate:** To summarize, we designed a News Feed system for two hundred million daily active users with a two hundred millisecond latency target. We leveraged a read-heavy architecture with a hybrid fan-out model, combining fan-out on write for most users and fan-out on read for celebrities, to balance read performance and write load. We used a relational database for user and follow data, a NoSQL wide-column store for posts, and Redis for fast user inboxes, all supported by message queues for asynchronous processing and CDNs for media delivery. Key patterns included cache-aside, idempotency, and sharding to ensure scalability and high availability.

## Interviewer's notes

**Interviewer:** That was a strong design. You clearly articulated the trade-offs and scaled the system effectively. What made this answer strong was the methodical approach, breaking down the problem into manageable steps and addressing each with specific technologies and patterns. You correctly identified the fan-out mechanism as the core challenge and proposed a practical hybrid solution, which is a common approach in real-world systems. You also demonstrated a good understanding of how to handle failure modes with idempotency and message queues.

The three to five key terms and patterns to remember from this problem are:
1.  **Fan-out on write (push model) vs. Fan-out on read (pull model) vs. Hybrid model:** Understanding the trade-offs for read-heavy vs. write-heavy systems and how to combine them.
2.  **Sharding and Data Partitioning:** Essential for scaling databases and caches horizontally, especially for user-specific data like inboxes.
3.  **Message Queues (e.g., Kafka):** For decoupling services, handling asynchronous tasks, and ensuring reliability in distributed systems, particularly for fan-out.
4.  **Idempotency:** Crucial for ensuring data consistency and preventing duplicates when retrying operations in a distributed environment.
5.  **Cache-Aside Pattern:** Using a fast cache (like Redis) for frequently accessed data (like feed post IDs) while having a persistent store for the full data.

One common mistake candidates make with this problem is immediately jumping to a pure fan-out on write solution without considering the "celebrity problem" or the write amplification it entails. Your hybrid approach showed a nuanced understanding of real-world constraints.
