**Interviewer:** Hi, welcome! Today's problem is to design a Content Delivery Network, or CDN. We want to build a system that can efficiently deliver static and potentially dynamic content to users globally. How would you approach this?

**Candidate:** Thanks! This is a fascinating problem with many layers. I'll start by clarifying the requirements, then move into back-of-the-envelope estimates, API design, data models, high-level architecture, and finally deep dive into specific components and trade-offs.

## Requirements

**Candidate:** To start, let's define the core functional and non-functional requirements. Functionally, our CDN needs to cache content, serve it quickly to users, and support common protocols like HTTP and HTTPS. It should also allow content providers to upload or "origin pull" their content and manage cache invalidation. Are there any specific types of content we're prioritizing, like large video files, small images, or a mix?

**Interviewer:** Assume a mix of content types, from small images and CSS files to medium-sized videos, up to a few gigabytes. We need to support both static content and potentially some dynamic, but cacheable, content.

**Candidate:** Got it. For non-functional requirements, scale is paramount. What kind of traffic volume are we talking about? How many requests per second or per day? What are our latency and availability targets?

**Interviewer:** We're aiming for a global scale. Let's say we need to handle billions of requests per day, potentially peaking at hundreds of thousands of requests per second. Our latency target for cache hits should be under 50 milliseconds globally, and availability needs to be very high, say 99.99 percent for content delivery. Consistency can be eventual for cached content, but we need mechanisms for timely invalidation.

**Candidate:** Excellent, that gives us concrete numbers to work with. Billions of requests per day, high availability, and low latency are typical for a CDN.

## Back-of-the-envelope estimates

**Candidate:** Let's do some quick back-of-the-envelope calculations.
If we have billions of requests per day, let's say two billion for easier math.
Two billion requests per day divided by 24 hours per day, divided by 60 minutes per hour, divided by 60 seconds per minute, gives us approximately 23,000 requests per second on average.
However, traffic often peaks, so we should design for at least five to ten times that average, pushing us into the range of 100,000 to 200,000 requests per second at peak.

For storage, if we assume an average content size of, say, 100 kilobytes, and we want to cache a significant portion of our popular content, let's say a petabyte of hot data across all edge locations. This is a rough estimate, and actual storage would vary wildly based on content mix and caching strategy.

For bandwidth, if we serve 200,000 requests per second, each averaging 100 kilobytes, that's 200,000 times 100 kilobytes, which is 20 gigabytes per second. This is a significant amount of egress bandwidth that needs to be distributed across many Points of Presence, or PoPs. This also doesn't account for ingress bandwidth from origin servers.

## API design

**Candidate:** Now, let's think about the main APIs. We'll need APIs for content providers to interact with the CDN.

First, an **Ingestion API** for content providers to upload or register their content. This could be a `PUT /content/{provider_id}/{path}` endpoint, where the body is the content itself. More commonly, CDNs use an "origin pull" model, where the CDN fetches content from the provider's origin server on demand. In this case, the provider would configure their domain and origin server, and the CDN would handle the pull. So, an API for **Origin Configuration**: `POST /config/origin` which takes parameters like `domain_name`, `origin_url`, `cache_rules`, `SSL_certs`.

Second, a **Cache Invalidation API**: `POST /invalidate/{provider_id}/{path}`. This would allow providers to explicitly remove or refresh content from the cache. It might take parameters like `exact_match` or `wildcard`.

Third, a **Monitoring and Analytics API**: `GET /metrics/{provider_id}` to retrieve usage statistics, cache hit ratios, and performance data.

The actual content retrieval by end-users doesn't use a direct API in the traditional sense, but rather standard HTTP/HTTPS requests to the CDN's edge servers, like `GET https://cdn.example.com/images/logo.png`.

## Data model and storage choice

**Candidate:** For the data model, we'll need to store configuration metadata and the actual content itself.

For **configuration metadata**, such as origin mappings, cache rules, SSL certificates, and access control lists, a highly available, globally distributed key-value store or a document database would be suitable. Something like DynamoDB, Cassandra, or CockroachDB could work. We need strong consistency for this data, as misconfigurations can have severe impacts. A relational database could also work for smaller scale, but for global distribution and high write availability, a NoSQL solution is often preferred.

For the **actual content**, we'll use a tiered storage approach.
At the **edge PoPs**, content will be stored on local disks, likely SSDs, for maximum read performance. This acts as a local cache.
Behind the edge PoPs, we might have **regional caches** with larger storage capacities, possibly using cheaper, higher-density storage like HDDs, or even object storage within the region.
The ultimate source of truth, the **origin server**, would typically use a highly durable and scalable object storage service, like AWS S3 or Google Cloud Storage. This provides the durability and availability for the canonical content.

The choice of local disk for edge caches is driven by the need for extremely low latency. The choice of object storage for the origin is for its massive scalability, durability, and cost-effectiveness for long-term storage.

## High-level design

**Candidate:** Let's walk through the high-level architecture for a user requesting content.

1.  **DNS Resolution:** When a user requests `https://cdn.example.com/image.jpg`, their local DNS resolver queries the CDN's authoritative DNS servers. This is where a critical component comes in: **Anycast DNS** or **Geo-DNS**. The DNS server doesn't just return an IP address; it intelligently routes the user to the IP address of the closest and healthiest **Point of Presence (PoP)**, or edge server, based on factors like network latency, server load, and geographical location. This is a fundamental part of CDN performance.

2.  **Request to Edge PoP:** The user's browser then sends the HTTP/HTTPS request directly to the IP address of the chosen edge PoP.

3.  **Edge Cache Check:** The edge PoP's server first checks its local cache.
    *   **Cache Hit:** If the content is found and is not expired (based on its Time-to-Live, or TTL, header), the PoP immediately serves the content back to the user. This is the fastest path and the goal of a CDN.
    *   **Cache Miss:** If the content is not found or is expired, the edge PoP needs to fetch it.

4.  **Regional Cache Check (Optional):** For a cache miss, the edge PoP might first check a larger, regional cache if one exists in the architecture. This reduces traffic to the origin.

5.  **Origin Fetch:** If the content is not in the regional cache, or if there's no regional cache layer, the edge PoP then makes a request to the content provider's **Origin Server**. This is often an S3 bucket, a web server, or a custom application. The edge PoP acts as a proxy.

6.  **Content Delivery and Caching:** Once the origin server responds, the edge PoP serves the content to the user. Crucially, it also stores a copy of the content in its local cache for future requests, respecting the cache-control headers provided by the origin. This is an example of the **cache-aside pattern**.

7.  **Control Plane:** All of this is managed by a separate **Control Plane**. This plane handles configuration updates, cache invalidation requests, health checks of PoPs, and routing logic for the DNS system. It's distinct from the **Data Plane** which handles the actual content delivery.

**Interviewer:** That's a clear flow. You mentioned Anycast DNS. Can you elaborate on how that works and why it's so important here? Also, what happens if an edge node fails or becomes overloaded?

## Deep dives

**Candidate:** Absolutely. Let's deep dive into **DNS-based Routing and Anycast**.

**Anycast DNS** is a networking technique where multiple servers around the world announce the same IP address. When a user makes a DNS query, network routers direct the request to the "nearest" server announcing that IP address, typically based on Border Gateway Protocol, or BGP, routing metrics. For a CDN, this means our authoritative DNS servers for `cdn.example.com` would be Anycast. When a user's DNS resolver queries this Anycast IP, it gets routed to the closest DNS server. That DNS server then uses Geo-IP databases and real-time network latency measurements to return the IP address of the *closest and best-performing CDN edge PoP* to the user. This ensures users are always routed to an optimal PoP, minimizing latency. It's a form of **traffic steering**.

If an edge node fails or becomes overloaded, the control plane's health monitoring system detects this. The failed node is then removed from the list of available PoPs that the DNS system can route traffic to. This is a form of **failover**. New requests will be directed to other healthy PoPs. Existing connections might be dropped, but subsequent requests will find a healthy path. This is why high availability requires redundancy at the PoP level. Each PoP itself would likely have multiple servers behind a local load balancer to handle internal failures.

**Interviewer:** Good. You also mentioned cache invalidation. Given the high availability and low latency requirements, how do you ensure that content updates from the origin are quickly reflected across all edge caches? What are the trade-offs there?

**Candidate:** This brings us to **Cache Invalidation and Consistency**. There are a few strategies.

1.  **Time-to-Live (TTL):** This is the simplest. Content is cached for a predefined duration. Once the TTL expires, the cache considers the content stale and fetches a fresh copy on the next request. This provides eventual consistency. The trade-off is that updates might not appear until the TTL expires, which could be minutes or hours.

2.  **Explicit Purge (Hard Invalidation):** This is what the Cache Invalidation API I mentioned is for. When a content provider pushes an update, they can call this API to explicitly mark specific content as invalid across all PoPs. The control plane propagates this invalidation request to all relevant edge servers. Upon receiving the purge command, the edge server immediately removes the content from its cache or marks it as stale. The next request for that content will result in a cache miss and a fetch from the origin. This offers stronger consistency but incurs overhead for propagation and can cause a "thundering herd" problem if many items are purged simultaneously, leading to many cache misses hitting the origin.

3.  **Soft Purge:** Instead of deleting the content, a soft purge marks it as stale but keeps it in the cache. If the origin is unavailable, the CDN can still serve the stale content, providing better availability. This is a **graceful degradation** strategy.

The trade-off is always between consistency and performance/availability. For static assets, a longer TTL is often acceptable. For frequently updated content, explicit purges are necessary. We'd likely offer both options to content providers, allowing them to choose based on their content's needs. We might also use **cache tags** or **surrogate keys** to invalidate groups of related content more efficiently.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks, failure modes, and trade-offs.

**Bottlenecks:**
*   **Network Bandwidth:** The sheer volume of data egress from PoPs and ingress to regional caches/origins can be a bottleneck. This requires robust network infrastructure and peering agreements.
*   **Disk I/O on Edge Servers:** While SSDs are fast, extremely high request rates for diverse content can still saturate disk I/O. This is mitigated by having sufficient RAM for hot content and distributing load across many servers.
*   **Origin Server Load:** If cache hit ratios are low, or during a large-scale cache purge, the origin servers can become overloaded. This is why origin servers need to be highly scalable and robust themselves.
*   **Control Plane Scalability:** The control plane needs to handle configuration updates, health checks, and invalidation requests for potentially thousands of PoPs. This requires a distributed, highly available control plane.

**Failure Modes:**
*   **DNS Misconfiguration:** Incorrect DNS routing can send users to non-existent or overloaded PoPs.
*   **Edge PoP Failure:** Handled by DNS routing and redundancy within the PoP.
*   **Origin Server Failure:** If the origin is down, the CDN can't fetch new content. A strategy like serving stale content (soft purge) can mitigate this.
*   **Network Partitions:** Isolating PoPs from the control plane or origin. PoPs should be designed to operate autonomously for a period, serving cached content even if disconnected. This is a form of **decoupled architecture**.

**Trade-offs:**
*   **Latency vs. Consistency:** As discussed, shorter TTLs or aggressive purging improve consistency but increase origin load and potentially latency for cache misses.
*   **Cost vs. Coverage:** More PoPs mean lower latency for more users but significantly higher infrastructure and operational costs. We'd strategically place PoPs in high-traffic regions.
*   **Cache Hit Ratio vs. Storage Cost:** Caching more content improves hit ratio but increases storage costs at edge and regional layers. Intelligent caching algorithms (e.g., Least Recently Used, or LRU, or Least Frequently Used, LFU) are crucial.

**What changes at ten times the scale?**
At ten times the scale, our 200,000 requests per second becomes two million. This would require:
1.  **More PoPs:** Significantly increasing the number of PoPs globally to distribute load and reduce latency further.
2.  **Deeper Caching Hierarchy:** Potentially adding more layers of caching between edge and origin, like super-PoPs or larger regional caches, to absorb more traffic and reduce origin load.
3.  **Advanced Traffic Steering:** More sophisticated real-time load balancing and routing algorithms, possibly using machine learning, to dynamically shift traffic away from congested or failing nodes.
4.  **Optimized Protocols:** Exploring HTTP/3 (QUIC) for better performance over unreliable networks.
5.  **Distributed Control Plane:** The control plane itself would need to be even more robust, distributed, and possibly sharded to handle the increased volume of health checks, configuration updates, and invalidations.
6.  **Edge Compute:** Potentially integrating serverless functions at the edge (like Lambda@Edge) for dynamic content manipulation closer to the user.

## Wrap-up

**Candidate:** In summary, our CDN design focuses on delivering content with high availability and low latency by leveraging a globally distributed network of edge PoPs. Key components include an intelligent DNS system for routing users to the nearest PoP, a multi-tiered caching strategy from edge to origin, and a robust control plane for configuration and invalidation. We address consistency with TTLs and explicit purges, and we've considered how to scale the system for future growth by adding more PoPs, deeper caching, and advanced traffic steering.

Three to five key terms and patterns to remember from this problem are:
1.  **Point of Presence (PoP):** The edge locations where content is cached and served.
2.  **Anycast DNS / Geo-DNS:** Critical for routing users to the nearest and healthiest PoP.
3.  **Tiered Caching:** Using multiple layers of caches (edge, regional, origin) to optimize performance and cost.
4.  **Cache Invalidation Strategies:** Understanding TTL, explicit purge, and soft purge, and their consistency trade-offs.
5.  **Control Plane vs. Data Plane:** Separating configuration and management from content delivery.

A common mistake candidates make when designing a CDN is underestimating the importance of DNS in routing and traffic management. Many focus solely on the caching aspect, but without an intelligent DNS layer, the "nearest" PoP concept falls apart, severely impacting latency. Another common oversight is not addressing cache consistency and invalidation mechanisms in detail.
