**Interviewer:** Alright, let's design a Notification Service. Imagine you're building this for a large product company. What would be your approach?

## Requirements

**Candidate:** Okay, I'll start by clarifying the requirements, both functional and non-functional.

**Candidate:** For functional requirements, I assume the service needs to send various types of notifications, such as transactional alerts, promotional messages, and system updates. What channels should it support? And can users manage their notification preferences?

**Interviewer:** Yes, it should support common channels like push notifications, email, SMS, and in-app notifications. Users absolutely need to be able to opt-in or opt-out for specific channels or notification types. We also need to store a history of sent notifications for auditing and user review.

**Candidate:** Got it. Regarding non-functional requirements, what kind of scale are we talking about? How many users, and what's the typical and peak notification volume? What are the latency expectations for different notification types, and what are our availability and consistency goals?

**Interviewer:** We have about 100 million active users. On average, we expect to send around 1 billion notifications per day, but this can peak up to five times that during major events. For critical transactional notifications, delivery should be within five seconds. Promotional notifications can have a higher latency, say within ten minutes. We need high availability, aiming for 99.99%, and eventual consistency for delivery status is acceptable, but user preferences should be strongly consistent.

**Candidate:** Excellent, that gives us a clear scope. So, 100 million users, 1 billion notifications daily, peaking at 5 billion, across push, email, SMS, and in-app. Low latency for transactional, higher for promotional, high availability, and strong consistency for preferences.

## Back-of-the-envelope estimates

**Candidate:** Next, let's do some back-of-the-envelope estimates to understand the scale.

**Candidate:** For requests per second, with 1 billion notifications per day, that's 1 billion divided by 24 hours, and then divided by 3,600 seconds per hour. That comes out to roughly 11,500 notifications per second on average. At peak, multiplying by five, we're looking at around 57,500 notifications per second. This is a significant load.

**Candidate:** For storage, let's estimate the size of a single notification record. If we store fields like notification ID, user ID, type, channel, content URL or template ID, status, timestamps, and provider response, that might be around 100 to 200 bytes per record. Let's use 150 bytes as an average. If we keep notification history for, say, 30 days, that's 1 billion notifications per day times 150 bytes per notification, times 30 days. This is approximately 4.5 terabytes of data per month. This suggests we'll need a scalable database solution.

**Candidate:** User preferences would be much smaller. For 100 million users, if each user has, say, ten preferences, and each preference record is 50 bytes, that's about 50 gigabytes in total. This can easily fit in a standard database and likely be heavily cached.

**Candidate:** For bandwidth, assuming an average notification payload size of 500 bytes after templating and rendering, 1 billion notifications per day would mean 500 gigabytes of outgoing data per day. This is manageable but needs to be accounted for, especially when interacting with external providers.

## API design

**Candidate:** Now, let's think about the API design. We'll need a few primary endpoints.

**Candidate:** First, an endpoint for sending notifications. I'd propose a `POST /notifications/send` endpoint. It would take a JSON payload including `user_id`, `notification_type`, `template_id`, `template_parameters` for dynamic content, and an optional `channel_priority_list` if the sender has a preference. Crucially, it should also include an `idempotency_key`.

**Candidate:** The `idempotency_key` is a unique value provided by the client, like a UUID, that ensures that if the same request is sent multiple times due to network issues, the notification is only processed and sent once. This is a common pattern to prevent duplicate actions in distributed systems. The API would return a `notification_id` and a `status` like "ACCEPTED" or "FAILED_VALIDATION".

**Candidate:** Second, for managing user preferences, we'd have `POST /users/{user_id}/preferences` to update settings, taking `channel`, `notification_type`, and `opt_in` as parameters. And a `GET /users/{user_id}/preferences` to retrieve current settings.

**Candidate:** Finally, for retrieving notification history, a `GET /users/{user_id}/notifications/history` endpoint, with query parameters for filtering by `start_date`, `end_date`, `channel`, `type`, and pagination parameters like `limit` and `offset`.

**Interviewer:** Good. How would the `idempotency_key` work internally?

**Candidate:** When a request with an `idempotency_key` comes in, the service would first check if that key has already been processed within a certain timeframe. If it has, it returns the previous result without re-processing. If not, it processes the request, stores the `idempotency_key` along with the result, and then returns the result. This typically involves storing the key in a fast key-value store like Redis, mapping it to the `notification_id` and status.

## Data model and storage choice

**Candidate:** Moving on to the data model and storage choice. I'd define a few key entities.

**Candidate:** The core entity would be `Notification`. This table would store `id` (primary key), `user_id`, `type`, `status` (e.g., PENDING, SENT, DELIVERED, FAILED), `created_at`, `scheduled_at`, `delivered_at`, `channel`, `template_id`, `template_parameters_json`, `external_provider_id` (the ID returned by the external service like FCM or Twilio), `external_provider_response_json`, and `retries_attempted`.

**Candidate:** For detailed logging, we might have a `NotificationEvent` table, storing `id`, `notification_id`, `event_type` (e.g., SENT_TO_PROVIDER, PROVIDER_SUCCESS, PROVIDER_FAILURE, RETRY_SCHEDULED), `timestamp`, and `details_json`.

**Candidate:** For `UserPreferences`, a table with `user_id`, `channel`, `notification_type`, `opt_in` (boolean), and `updated_at`. This allows users to control specific types of notifications on specific channels.

**Candidate:** Finally, a `Template` table to store `id`, `name`, and `content_json` which could hold different content versions for various channels or locales.

**Candidate:** For storage choice, given the need for strong consistency for user preferences and the ability to query notification history with joins, a relational database like PostgreSQL would be a solid choice for all these tables. It offers ACID properties, good indexing capabilities, and is well-suited for structured data. For the sheer volume of notification history, we might consider sharding the `Notification` table later, perhaps by `user_id` or `created_at` range, but PostgreSQL can handle the initial scale.

**Interviewer:** Why not a NoSQL database for the notification history, given the volume?

**Candidate:** That's a valid consideration. A NoSQL document store like MongoDB or Cassandra could definitely handle the volume and offer higher write throughput. However, if we anticipate complex queries on the history, such as filtering by multiple attributes or joining with user data for analytics, a relational database offers more flexibility and power out of the box. For our initial design, PostgreSQL provides a good balance. If history queries become a bottleneck, we could offload them to an analytical store or use a denormalized NoSQL solution specifically for history, but I'd start with a single, well-understood system.

## High-level design

**Candidate:** Let's outline the high-level design, walking through the flow of a notification.

**Candidate:** The system would start with a client service calling our Notification Service API Gateway. This gateway would route requests to a fleet of API Servers, behind a load balancer.

**Candidate:** When an API Server receives a `POST /notifications/send` request, it performs initial validation, checks the `idempotency_key`, creates an initial `Notification` record in the database with a status of PENDING, and then publishes a message to a Message Queue, like Kafka. The message would contain the `notification_id` and other relevant details. The API Server then immediately returns an "ACCEPTED" response to the client. This asynchronous processing is a key pattern for handling high throughput and ensuring low latency for the API caller.

**Candidate:** Kafka acts as a buffer, decoupling the API ingestion from the actual processing and delivery. It handles spikes and ensures durability of messages.

**Candidate:** A fleet of Notification Processors, which are worker services, would consume messages from Kafka. Each processor would:
1. Fetch the `Notification` record from the database using the `notification_id`.
2. Retrieve user preferences from the User Preference Service, which likely caches data from the `UserPreference` database. This is the **cache-aside pattern**, where the service checks the cache first, and if the data isn't there, fetches it from the database and populates the cache.
3. Fetch the appropriate template from the Template Service.
4. Render the notification content using the template and provided parameters.
5. Determine the final delivery channels based on user preferences and the requested `channel_priority_list`.
6. For each chosen channel, it sends the rendered notification to the appropriate Channel Adapter.

**Candidate:** Each Channel Adapter is a specialized service responsible for interacting with external providers. For example, a Push Adapter would integrate with Firebase Cloud Messaging or Apple Push Notification Service. An Email Adapter would use SendGrid or Mailgun. An SMS Adapter would use Twilio. These adapters handle provider-specific APIs, authentication, and error translation.

**Candidate:** After attempting delivery, the Notification Processor updates the `Notification` status in the database (e.g., to SENT_TO_PROVIDER, FAILED_PROVIDER) and logs a `NotificationEvent`. If a provider call fails, the processor might enqueue the message back into a retry topic in Kafka, perhaps with a delay, implementing an **exponential backoff** strategy.

**Candidate:** Finally, external providers often send delivery receipts or webhooks back. We'd have a dedicated endpoint in our Notification Service to receive these callbacks and update the `Notification` status to DELIVERED or FAILED_DELIVERY, and log the corresponding `NotificationEvent`.

## Deep dives

**Interviewer:** That's a solid high-level overview. Let's dive into a few areas. How do you ensure reliable delivery and handle failures with external providers?

**Candidate:** Reliable delivery is critical for a notification service. Since we're using Kafka, we get **at-least-once delivery** guarantees. This means a message might be processed more than once, which is why the `idempotency_key` at the API layer is important to prevent duplicate *sends* from the client's perspective. Internally, our processors must also be idempotent when interacting with external providers.

**Candidate:** For provider failures, the Channel Adapters play a crucial role. They should implement **Circuit Breaker** patterns. If an external provider is consistently failing, the circuit breaker would "trip," preventing further requests to that provider for a short period, allowing it to recover, rather than hammering it with failing requests. This prevents cascading failures.

**Candidate:** When a provider call fails, the Notification Processor won't acknowledge the Kafka message immediately. Instead, it can put the message onto a dedicated retry topic in Kafka. A separate "Retry Scheduler" service would consume from this topic, apply an exponential backoff strategy, and re-enqueue the message for processing after a delay. If a message exhausts all its retries, it's moved to a **Dead Letter Queue (DLQ)** for manual inspection or specific error handling. This ensures no message is silently lost.

**Interviewer:** What about rate limiting calls to external providers? They often have strict limits.

**Candidate:** Absolutely. Each Channel Adapter must implement its own rate-limiting mechanism to avoid exceeding provider quotas. A common pattern for this is the **Token Bucket algorithm**. Each adapter would maintain a virtual "bucket" of tokens. To send a notification, it needs a token. Tokens are added to the bucket at a fixed rate. If the bucket is empty, the request is either queued or rejected. This smooths out bursts of requests and ensures we stay within the provider's limits. We might even have multiple API keys or accounts with providers to increase our aggregate rate limit if needed.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks, failure modes, and trade-offs.

**Candidate:** **Bottlenecks** could include the external provider rate limits, which we address with Channel Adapters and Token Bucket. Another could be the database write throughput for updating notification statuses, especially during high peaks. We can mitigate this by batching status updates where possible, using database sharding, or employing a highly performant database. Kafka itself can be a bottleneck if not properly scaled, but it's designed for high throughput.

**Candidate:** For **failure modes**:
1.  **External Provider Outage:** If an email provider goes down, email notifications will fail and go into retry loops, eventually landing in the DLQ. The system should alert operators. Other channels remain unaffected.
2.  **Database Failure:** If our primary notification database fails, new notifications can't be stored, and status updates can't happen. We'd use database replication and automatic failover mechanisms to minimize downtime.
3.  **Kafka Cluster Failure:** If Kafka goes down, producers can't publish, and consumers can't process. A highly available, multi-broker Kafka cluster across availability zones is essential.
4.  **Notification Processor Crashes:** Since Kafka messages are only acknowledged after successful processing, if a worker crashes, the message will be re-queued and processed by another available worker, ensuring at-least-once delivery.

**Candidate:** Regarding **trade-offs**:
-   We've chosen **at-least-once delivery** over **exactly-once delivery**. Exactly-once is incredibly complex to achieve end-to-end in distributed systems and often not necessary for notifications, as long as idempotency is handled to prevent visible duplicates to the user.
-   **Latency vs. Cost:** Real-time processing for all notifications requires more resources and faster infrastructure. By having different latency targets for transactional versus promotional, we can optimize costs by potentially batching promotional notifications or processing them with lower-priority workers.
-   **Centralized vs. Decentralized Preferences:** We opted for a centralized `UserPreference` database, which ensures strong consistency but could be a bottleneck. Caching with the **cache-aside pattern** helps alleviate this.

**Candidate:** If the system needs to scale to **ten times the load**, we would need:
-   Significantly more Kafka partitions and brokers to handle the increased message throughput.
-   Horizontal scaling of Notification Processors and Channel Adapters.
-   Database sharding for the `Notification` history table, likely by `user_id` or `notification_id` ranges, to distribute write and read load.
-   Potentially multiple accounts or contracts with external providers to increase our aggregate rate limits.
-   Consideration for geo-distribution of services and databases to reduce latency for users across different regions.

## Wrap-up

**Candidate:** To summarize, we've designed a highly scalable and reliable Notification Service. It leverages an asynchronous, message-queue-based architecture with Kafka to handle high throughput and decouple components. We have a clear API for sending and managing preferences, and a robust data model using PostgreSQL. Key patterns like idempotency keys, at-least-once delivery, circuit breakers, token bucket for rate limiting, and cache-aside for preferences ensure reliability and performance. The system is designed with fault tolerance and scalability in mind, ready to handle current and future demands by horizontal scaling and database sharding.

**Interviewer:** Excellent. Thank you.
