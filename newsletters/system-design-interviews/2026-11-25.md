**Interviewer:** Good morning. Today's problem is to design Tinder. We're looking for a system that can handle millions of users, enable them to discover potential matches, swipe on profiles, and chat with their matches. How would you approach this?

**Candidate:** Good morning. This sounds like a fun challenge. I'll start by clarifying the **Requirements**, then move to **Back-of-the-envelope estimates**, followed by **API design**, **Data model and storage choices**, a **High-level design**, and then we can **Deep dive** into some of the harder parts. Finally, I'll discuss **Bottlenecks, failure modes and trade-offs**, and provide a quick **Wrap-up**.

## Requirements

**Candidate:** Let's begin with the functional requirements. Users should be able to create and manage their profiles, including uploading photos and setting preferences like age range and gender. They need to be able to discover other users based on location and preferences, swipe left or right on profiles, and get a match notification if both users swipe right on each other. Finally, matched users should be able to chat in real-time.

**Interviewer:** Those are good core features. What about non-functional requirements? Think about scale, latency, availability, and consistency.

**Candidate:** For non-functional requirements, given Tinder's nature, high availability is crucial. Users expect the service to be up and running constantly. Latency for swiping and seeing new profiles should be low, ideally under a few hundred milliseconds, to provide a smooth user experience. For consistency, profile updates can be eventually consistent, but match detection and chat messages should lean towards strong consistency. As for scale, let's assume we're targeting a global audience with tens of millions of daily active users.

**Interviewer:** That's a good baseline. Let's make it concrete: assume one hundred million daily active users.

## Back-of-the-envelope estimates

**Candidate:** One hundred million daily active users, got it. Let's estimate the scale.
If each user performs, say, one hundred swipes per day on average, that's ten billion swipes daily.
Ten billion swipes per day divided by eighty-six thousand four hundred seconds in a day gives us roughly one hundred and fifteen thousand swipes per second. This is a significant write load.

For storage, let's consider user profiles. If each profile, including a few photos, averages one megabyte, then one hundred million users would require one hundred terabytes of storage just for profiles.
Swipe history records would be much smaller. Each swipe is a record of user ID, target user ID, swipe direction, and a timestamp. If we assume about twenty-five bytes per swipe, ten billion swipes per day would be around two hundred and fifty gigabytes of data written daily. Over a year, that's nearly ninety terabytes.
Chat messages will add to this, but let's assume they are less voluminous than swipes for now.

Bandwidth will primarily be driven by serving images. If a user views one hundred profiles per day, and each profile view involves downloading, say, five hundred kilobytes of images, that's fifty megabytes per user per day. Multiplied by one hundred million users, that's five petabytes of data egress per day. This is a very large number and suggests we'll need a robust content delivery network, or CDN.

## API design

**Candidate:** Next, let's outline the main API endpoints. I'd design a RESTful API.

For user profiles:
*   `POST /users`: To create a new user profile. It would take profile details like name, age, gender, and initial preferences.
*   `GET /users/{id}`: To retrieve a specific user's profile.
*   `PUT /users/{id}`: To update a user's profile or preferences.

For discovery and swiping:
*   `GET /users/discover`: This is a crucial endpoint. It would return a list of potential match profiles for the current user, based on their location, preferences, and users they haven't yet swiped on. It might take query parameters for pagination or filtering.
*   `POST /users/{id}/swipe`: To record a swipe. It would take the target user's ID and the swipe direction, either "left" or "right".

For matches and chat:
*   `GET /matches`: To retrieve a list of the current user's matches.
*   `GET /matches/{id}/messages`: To fetch chat history for a specific match.
*   `POST /matches/{id}/message`: To send a chat message to a matched user. This would ideally be a WebSocket connection for real-time chat, but a REST endpoint could be used for initial message sending or fallback.

**Interviewer:** Good set of APIs. How would you handle authentication and authorization for these?

**Candidate:** I'd use a standard approach like OAuth 2.0 or JWTs, JSON Web Tokens. After a user logs in, they receive a token which they include in the header of subsequent requests. This token would be validated by an API Gateway or authentication service before requests reach the backend services. This is a common security pattern.

## Data model and storage choice

**Candidate:** For the data model, we'll need several distinct entities.

First, `User` profiles. This would include user ID, name, age, gender, location, bio, preferences, and references to their photos. Given the need for flexible schemas for preferences and potentially evolving profile fields, a document database like MongoDB could work well. However, for complex queries involving location and preferences, a relational database like PostgreSQL with PostGIS extensions for geo-spatial indexing is a strong contender. I'd lean towards PostgreSQL with PostGIS for its robust querying capabilities and strong consistency guarantees where needed. Photos themselves would be stored in object storage like Amazon S3, with URLs stored in the user profile.

Second, `Swipe` records. These are high-volume writes. A simple schema of `swiper_user_id`, `swiped_user_id`, `direction` (left/right), and `timestamp`. For this, a wide-column store like Apache Cassandra or a key-value store like Amazon DynamoDB would be excellent choices due to their high write throughput and horizontal scalability. We could partition by `swiper_user_id` to distribute the load.

Third, `Match` records. When two users swipe right on each other, a match is created. This needs strong consistency. A relational database like PostgreSQL, possibly sharded, would be suitable. The schema would be `match_id`, `user_id_1`, `user_id_2`, `created_at`.

Fourth, `Chat Messages`. These are also high-volume and need to be retrieved efficiently for a given match. A document database like MongoDB or a wide-column store like Cassandra could store messages, partitioned by `match_id`. Each message would have `message_id`, `match_id`, `sender_user_id`, `content`, and `timestamp`.

**Interviewer:** You've mentioned a few different database types. How would you connect these, and what's the overall architecture?

## High-level design

**Candidate:** My high-level design would follow a microservices architecture. This allows us to scale different components independently and choose the best database for each specific need.

At the front, users interact with mobile clients. Requests would go through a **Load Balancer** to distribute traffic, then hit an **API Gateway** for authentication, rate limiting, and routing.

Behind the API Gateway, we'd have several services:
1.  **User Service:** Manages user profiles, preferences, and photo uploads to object storage. It would primarily interact with the PostgreSQL database for user data and S3 for images.
2.  **Discovery Service:** This is critical for finding potential matches. It queries the user database, leveraging PostGIS for geo-spatial queries, filters by preferences, and excludes users already swiped on. It might also incorporate a ranking algorithm. This service would heavily use caching, perhaps with Redis, to store frequently accessed profiles or pre-computed discovery lists.
3.  **Swipe Service:** Records swipes into the Cassandra or DynamoDB store. When a right swipe occurs, it publishes an event to a **Message Queue**, like Apache Kafka, for asynchronous processing. This is an example of the publish-subscribe pattern.
4.  **Match Service:** Subscribes to swipe events from Kafka. When two users have mutually swiped right, it creates a `Match` record in the PostgreSQL database and triggers notifications. It also handles the logic for match detection, ensuring atomicity for match creation.
5.  **Chat Service:** Handles real-time messaging using **WebSockets**. It would persist messages to a dedicated chat database, like MongoDB or Cassandra, and fan out messages to connected clients.
6.  **Notification Service:** Subscribes to match events and new message events from Kafka. It then sends push notifications to users via platform-specific services like Apple Push Notification Service, APNS, or Firebase Cloud Messaging, FCM. This is a fan-out pattern for notifications.

All services would communicate internally via gRPC or REST, and asynchronously via Kafka. We'd also have a **CDN** in front of our object storage for efficient image delivery.

**Interviewer:** That's a comprehensive overview. Let's delve into the discovery part. How exactly does the Discovery Service find users efficiently, especially with location as a primary filter?

## Deep dives

**Candidate:** The **Discovery Service** is indeed one of the most challenging parts. The core problem is finding users within a certain radius, who meet specific preference criteria, and haven't been swiped on yet.

My proposed solution involves leveraging **geo-spatial indexing**. With PostgreSQL and PostGIS, we can store user locations as `GEOGRAPHY` points and create spatial indexes, such as GiST indexes. When a user requests potential matches, the Discovery Service can query PostGIS to find all users within a specified radius, say ten miles.

After the initial geo-spatial filter, we apply preference filters, like age range and gender. To exclude already-swiped users, the Discovery Service would query the Swipe database, which is partitioned by `swiper_user_id`, to get a list of IDs the current user has already interacted with. This list is then used to filter out those profiles.

To make this fast, we can cache the results of these discovery queries in Redis for a short period, using the user's ID and location as part of the cache key. This is the **cache-aside pattern**. If the user moves, the cache key changes, and a new query is performed.

For performance at scale, the Discovery Service itself would be horizontally scaled. We could also pre-compute a pool of potential matches for users in popular areas during off-peak hours, storing them in a cache, to reduce real-time query load. This is a form of pre-computation.

Another deep dive is **Match Detection**. When a user A swipes right on user B, the Swipe Service records this. It then publishes an event to Kafka. The Match Service consumes this event. It then queries the Swipe database to check if user B has *also* swiped right on user A. If both conditions are met, a match is confirmed. To ensure atomicity for the match creation and avoid race conditions, the Match Service would use database transactions when inserting into the Match table. We could also use a distributed lock around the match detection logic for a specific pair of users, though this adds complexity. A simpler approach is to rely on the unique constraint on `(user_id_1, user_id_2)` in the Match table. If an insert fails due to a duplicate, it means the match was already created by the other user's swipe.

Finally, for **Real-time Chat and Notifications**, the Chat Service would establish WebSocket connections with clients. When a message is sent, it's broadcast to all active WebSocket connections for that specific `match_id`. This is a classic **fan-out** pattern. Messages are simultaneously persisted to the Chat database. For offline users or those not actively in the chat, the Notification Service, consuming message events from Kafka, would send push notifications via APNS or FCM. This ensures messages are delivered even if the user isn't actively chatting.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks and failure modes.

The **Discovery Service** could become a bottleneck. Geo-spatial queries, especially with complex filtering and exclusion lists, can be CPU and I/O intensive. To mitigate this, we'd aggressively cache results, shard the user database by geographical regions or user ID, and continuously optimize our indexing strategies. If PostGIS becomes a bottleneck at extreme scale, we might consider dedicated geo-spatial databases or custom solutions, but it's a good starting point.

The **Swipe Service** handles extremely high write throughput. Cassandra or DynamoDB are designed for this, but proper partitioning based on `swiper_user_id` is crucial to avoid hot spots. Monitoring partition health is key.

**Database scalability** is a general concern. All databases would need to be sharded and replicated for high availability and read scalability. For PostgreSQL, we'd use read replicas. For Cassandra/DynamoDB, replication is built-in.

**Caching** introduces complexity, specifically cache invalidation. We need a clear strategy for when to invalidate cached discovery results or user profiles when underlying data changes. For example, if a user updates their profile, their cached profile data needs to be invalidated. This can be done by publishing an event to Kafka, and services listening for that event can invalidate relevant cache entries. This is an example of the **eventual consistency** trade-off for cached data.

**Failure modes:** Single points of failure are a major risk. Every component, from load balancers to individual services and databases, needs redundancy. This means multiple instances behind load balancers, database replication with automatic failover, and stateless services where possible. Message queues like Kafka are also critical, so they need to be deployed in a highly available, clustered configuration.

**Trade-offs:** We've already discussed consistency versus availability. For swipes, eventual consistency is acceptable. A swipe might take a few milliseconds to be fully processed and reflected in the system, but the user experience isn't severely impacted. For match creation, strong consistency is preferred to ensure a match is only created once and correctly. Chat messages also need strong consistency for ordering and delivery.

At **ten times the scale**, our current estimates for swipes per second would jump to over a million. This would require more aggressive sharding across all databases. The Discovery Service would need more sophisticated ranking algorithms, potentially involving machine learning models, and might require dedicated clusters for geo-spatial indexing or pre-computation farms. The message queue would need to handle even higher throughput. We'd likely see more specialized services emerge, perhaps a dedicated "Recommendation Engine" service. The CDN would also need to scale significantly to handle fifty petabytes of traffic per day.

## Wrap-up

**Candidate:** In summary, my design for Tinder leverages a microservices architecture for scalability and flexibility. We use specialized databases: PostgreSQL with PostGIS for user profiles and geo-spatial queries, Cassandra or DynamoDB for high-throughput swipe recording, and dedicated databases for matches and chat messages. A robust message queue like Kafka handles asynchronous processing and decouples services, enabling real-time match detection and notifications. The Discovery Service, a core component, uses geo-spatial indexing and caching to efficiently find potential matches. Finally, WebSockets power real-time chat, and a CDN handles image delivery. This distributed system is designed for high availability, low latency, and to scale to hundreds of millions of daily active users.

**Interviewer:** Thank you, that was a very thorough and well-structured answer.

Three to five key terms and patterns to remember from this problem:

2.  **Fan-out (on write/read):** Used for notifications and real-time chat to distribute information efficiently.
