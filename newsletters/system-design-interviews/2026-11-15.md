**Interviewer:** Alright, let's design WhatsApp. You're building a new messaging platform from scratch. How would you approach this?

**Candidate:** Great problem. I'll start by clarifying the **Requirements**, both functional and non-functional, then move to **Back-of-the-envelope estimates**, followed by **API design**, **Data model and storage choices**, a **High-level design** walking through a core flow, then **Deep dives** into specific challenges, discuss **Bottlenecks, failure modes and trade-offs**, and finally a **Wrap-up**.

## Requirements

**Candidate:** Let's begin with functional requirements. I assume we need one-to-one chat, group chat, sending and receiving text messages, and sharing media like photos and videos. Do we also need features like read receipts, typing indicators, or online status?

**Interviewer:** Yes, let's include read receipts, typing indicators, and online status. For media, assume users share photos and short videos, up to say, 100 megabytes per file.

**Candidate:** Understood. Now for non-functional requirements. What kind of scale are we targeting? How many active users, and how many messages per day?

**Interviewer:** Let's aim for a global scale, supporting two billion daily active users. On average, each user sends about ten messages per day. Latency is critical: messages should be delivered within 500 milliseconds end-to-end, and online status updates should be near real-time, within a second. Availability must be extremely high, say, four nines, meaning less than an hour of downtime per year.

**Candidate:** Four nines availability and sub-500 millisecond latency for two billion users is a significant challenge. For consistency, I'd prioritize strong consistency for message ordering within a conversation, especially group chats, to ensure messages appear in the correct sequence. For things like read receipts or online status, eventual consistency is acceptable. Are there any specific security or privacy requirements, like end-to-end encryption?

**Interviewer:** Yes, end-to-end encryption for all messages is a must-have. We won't delve into the cryptography details today, but assume it's handled at the client level. Focus on the infrastructure.

**Candidate:** Excellent. So, core features: 1:1 chat, group chat, text, media, read receipts, typing indicators, online status. Non-functional: 2 billion DAU, 10 messages/user/day, 500ms latency, 99.99% availability, strong consistency for message order, eventual for status/receipts, and end-to-end encryption.

## Back-of-the-envelope estimates

**Candidate:** Let's estimate the load.
For messages per second: Two billion daily active users, each sending ten messages per day, gives us twenty billion messages daily. Dividing that by eighty-six thousand four hundred seconds in a day, we get approximately two hundred thirty-one thousand messages per second. Let's round that up to about two hundred fifty thousand messages per second to account for peak times.

For storage, let's assume an average text message is about one hundred bytes. Media files are larger. If ten percent of messages are media, and the average media file is one megabyte, then for twenty billion messages daily, we have two billion media messages. That's two petabytes of new media data per day. Over five years, that's three thousand six hundred fifty petabytes, or 3.65 exabytes, just for media. Text messages, at one hundred bytes each, for twenty billion messages daily, is two terabytes per day, or about 3.65 petabytes over five years. So, media storage will dominate.

For bandwidth, at two hundred fifty thousand messages per second, if each message, including metadata and encryption overhead, is about one kilobyte, that's two hundred fifty megabytes per second just for text. If ten percent are media, and each media transfer is one megabyte, that's twenty-five thousand megabytes per second, or twenty-five gigabytes per second. This is substantial, especially for media. We'll need a Content Delivery Network, or CDN, for media.

## API design

**Candidate:** I'll define a few core APIs. These would likely be exposed through a single API Gateway.

First, for sending messages:
`POST /messages/send`
Request body:
`sender_id`: string
`receiver_id` or `group_id`: string
`message_content`: string (encrypted)
`message_type`: enum (TEXT, IMAGE, VIDEO)
`timestamp`: long
`client_message_id`: string (for idempotency and deduplication)
Response: `message_id`: string, `status`: string (e.g., "SENT")

Second, for receiving messages:
`GET /messages/receive` (or more likely, a persistent connection like WebSockets)
This would return a list of new messages for the authenticated user, including:
`message_id`: string
`sender_id`: string
`receiver_id` or `group_id`: string
`message_content`: string (encrypted)
`message_type`: enum
`timestamp`: long

Third, for media upload:
`POST /media/upload`
Request body:
`user_id`: string
`file_content`: binary data
`file_type`: string
Response: `media_url`: string

Fourth, for status updates:
`POST /status/update`
Request body:
`user_id`: string
`status`: enum (ONLINE, OFFLINE, TYPING)
`last_seen`: long (optional)

**Interviewer:** Good, the `client_message_id` for idempotency is a smart addition. How would a client get new messages if not by polling `GET /messages/receive`?

**Candidate:** That's a great point. Polling is inefficient for real-time systems. For receiving messages and status updates, we'd use a persistent connection, likely **WebSockets**. This allows the server to push messages to the client immediately, reducing latency and overhead compared to long polling or frequent short polling. This is a common pattern for real-time communication.

## Data model and storage choice

**Candidate:** Let's design the core data models.

**User Profile:**
`user_id`: Primary Key, string (UUID)
`phone_number`: string (unique)
`username`: string
`profile_picture_url`: string
`status_message`: string
`last_seen`: timestamp
`online_status`: enum (ONLINE, OFFLINE)
This would be stored in a **NoSQL document database** like MongoDB or DynamoDB, as user profiles are self-contained and flexible.

**Message:**
`message_id`: Primary Key, string (UUID, globally unique, possibly time-ordered like a UUIDv7)
`sender_id`: string (FK to User)
`receiver_id` or `group_id`: string (FK to User or Group)
`conversation_id`: string (derived from sender/receiver IDs, for quick lookup)
`content`: string (encrypted text or media URL)
`message_type`: enum
`timestamp`: long
`status`: enum (SENT, DELIVERED, READ)
This is the core of the system. Given the immense write volume and need for high availability and horizontal scalability, a **wide-column store** like Apache Cassandra or Google Cloud Bigtable would be ideal. It handles high throughput writes well and allows for flexible querying by `conversation_id` and `timestamp`. We'd partition by `conversation_id` or `receiver_id`.

**Group:**
`group_id`: Primary Key, string (UUID)
`group_name`: string
`creator_id`: string (FK to User)
`members`: Set of `user_id` strings
`created_at`: timestamp
This data is more relational and requires strong consistency for membership updates. A **relational database** like PostgreSQL, sharded, could work here. Alternatively, a strongly consistent NoSQL database like DynamoDB in a transactional mode could also serve, if we need to keep all data in NoSQL. For simplicity, let's assume a sharded PostgreSQL for group metadata.

**Candidate:** The choice of Cassandra for messages is because it excels at high-volume writes and reads for specific keys, which aligns with fetching messages for a conversation. Its eventual consistency model is fine for global replication, as long as we ensure strong ordering within a partition, which can be done using a combination of `timestamp` and `message_id`.

## High-level design

**Candidate:** Let's walk through the `sendMessage` flow.

1.  **Client:** The sender's client encrypts the message end-to-end.
2.  **API Gateway:** The client sends the encrypted message to an API Gateway. This acts as a single entry point, handles authentication, rate limiting, and routes requests to appropriate microservices.
3.  **Load Balancer:** Requests are distributed across multiple instances of our backend services.
4.  **Message Service:** This is the core service. It receives the message, validates the sender and receiver, and generates a `message_id`.
5.  **Message Queue (Kafka):** The Message Service publishes the message to a distributed message queue, like Apache Kafka. This provides durability, decouples the sender from the delivery mechanism, and allows for asynchronous processing. This is a crucial **asynchronous communication pattern**.
6.  **Message Storage:** A consumer from the Kafka queue persists the message into our Cassandra cluster. The `message_id`, `sender_id`, `receiver_id`, `content`, and `timestamp` are stored.
7.  **Notification Service:** Another consumer from the Kafka queue picks up the message. It checks the receiver's online status via the User Service.
    *   If the receiver is online and connected via WebSockets, the Notification Service pushes the message directly to their client. This is a **real-time push notification** mechanism.
    *   If the receiver is offline, the Notification Service sends a push notification through platform-specific services like FCM (Firebase Cloud Messaging) or APNs (Apple Push Notification service). The message itself isn't sent via FCM/APNs, only a notification to wake up the app and fetch new messages.
8.  **Media Service & CDN:** If the message includes media, the client first uploads the media to a dedicated Media Service, which stores it in an object storage like S3 and serves it via a **CDN (Content Delivery Network)**. The `message_content` then contains the CDN URL for the media.

**Interviewer:** That's a good high-level overview. What happens if the Message Service or the Notification Service goes down? How do you ensure messages aren't lost or duplicated?

## Deep dives

**Candidate:** That brings us to failure modes and consistency.

**Deep Dive 1: Ensuring Message Delivery and Handling Offline Users.**
When a message is sent, it's first persisted in Cassandra. This ensures durability. The Kafka queue also provides durability, as messages are retained for a configurable period.
If the Notification Service fails, messages remain in Kafka and can be processed by another instance or when the service recovers. This is a key benefit of using a **message queue** for reliability.
For offline users, the message is stored in Cassandra, marked as 'SENT'. When the user comes online, their client would initiate a `GET /messages/receive` (or more accurately, the WebSocket connection would re-establish and the server would push pending messages). The Notification Service, upon detecting the user's online status, would query Cassandra for all messages for that user with status 'SENT' or 'DELIVERED', and push them.
To handle message status updates (Delivered, Read), the client sends an acknowledgment back to the Message Service, which updates the message status in Cassandra. This is an **eventual consistency** model for message status.

**Deep Dive 2: Message Ordering in Group Chats.**
For strong consistency in message ordering, especially in group chats, we need a mechanism beyond just `timestamp`. Clocks can drift.
One approach is to use a globally unique, monotonically increasing ID for messages within a conversation. A common pattern is to use **Lamport timestamps** or a similar logical clock mechanism, or a hybrid logical clock. Each message would get a `sequence_number` per conversation. The Message Service would be responsible for assigning these sequence numbers. To ensure this, we could have a single, sharded service responsible for assigning sequence numbers for each conversation, acting as a leader for that specific conversation. This is a form of **sharding by conversation ID**. When a message comes in for a group, the Message Service instance responsible for that group would assign the next sequence number before publishing to Kafka. Clients then display messages ordered by this `sequence_number`.

**Interviewer:** Okay, so a sharded service for sequence numbering. What if that specific shard's leader fails? How do you maintain availability and correct ordering?

**Candidate:** If a leader for a conversation shard fails, we'd need a robust **leader election mechanism**, such as Apache ZooKeeper or etcd, to elect a new leader. During the election, message ordering for that specific conversation might be temporarily paused or messages would be buffered until a new leader is established. This ensures that when the service resumes, the sequence numbers continue monotonically without gaps or duplicates. This is a classic **consensus algorithm** problem.

## Bottlenecks, failure modes and trade-offs

**Candidate:**
**Bottlenecks:**
1.  **Cassandra cluster:** With 250,000 writes/sec and reads for billions of messages, the Cassandra cluster will be a bottleneck. This requires careful sharding, replication, and tuning. We'd use **consistent hashing** for data distribution across nodes.
2.  **Kafka cluster:** High message throughput means a large Kafka cluster. Monitoring consumer lag is critical.
3.  **Network bandwidth:** Especially for media, the egress bandwidth from our data centers and CDN will be massive.

**Failure Modes:**
1.  **Service failures:** Individual microservices can fail. Using **Kubernetes** for orchestration and **health checks** for automatic restarts helps. Kafka and Cassandra's distributed nature provide resilience.
2.  **Database failures:** Cassandra's replication ensures data durability even if nodes fail. For PostgreSQL, we'd use **leader-follower replication** with automatic failover.
3.  **Network partitions:** Clients might temporarily lose connection. Messages are stored and delivered upon reconnection.

**Trade-offs:**
*   **Consistency vs. Availability:** We chose strong consistency for message order within a conversation, but eventual consistency for read receipts and online status. This is a common **CAP theorem** trade-off, prioritizing availability and partition tolerance for the overall system while ensuring message integrity.
*   **Complexity vs. Scale:** Using microservices, message queues, and distributed databases adds significant operational complexity but is necessary to achieve WhatsApp's scale and availability requirements.

**What changes at ten times the scale:**
At two trillion messages daily, we'd need:
1.  **More aggressive sharding:** Even more granular sharding for Cassandra and Kafka topics.
2.  **Regional deployments:** Deploying infrastructure in multiple geographical regions to reduce latency for users worldwide and provide disaster recovery. This introduces challenges with cross-region data synchronization and consistency.
3.  **Caching:** More extensive use of in-memory caches like Redis for frequently accessed data like user profiles and online status, employing the **cache-aside pattern**.
4.  **Optimized protocols:** Further optimization of network protocols, potentially using custom binary protocols over WebSockets for maximum efficiency.
5.  **Dedicated hardware:** Potentially moving to custom hardware or highly optimized cloud instances for specific high-throughput services.

## Wrap-up

**Candidate:** To summarize, we designed a highly scalable, available, and low-latency messaging system for two billion users. We started with clear functional and non-functional requirements, including end-to-end encryption. Our estimates showed massive scale, especially for media. The design leverages an API Gateway, microservices, and WebSockets for real-time communication. Data is stored in a Cassandra cluster for messages and a sharded PostgreSQL for group metadata, with Kafka acting as a reliable message queue. We deep-dived into ensuring message delivery for offline users and maintaining strong message ordering in group chats using sequence numbers and leader election. Finally, we addressed potential bottlenecks, failure modes, and trade-offs, outlining how the system would evolve to handle ten times the load through more aggressive sharding, regional deployments, and caching.

**Interviewer:** Thank you. That's a comprehensive design.

Key terms and patterns to remember from this problem:
1.  **WebSockets:** For real-time, bidirectional communication.
2.  **Message Queue (Kafka):** For asynchronous processing, decoupling services, and ensuring message durability/reliability.
3.  **Wide-Column Store (Cassandra/Bigtable):** Ideal for high-volume writes, horizontal scalability, and time-series data like messages.
4.  **CDN (Content Delivery Network):** For efficient distribution of static assets like media files.
5.  **Sharding & Consistent Hashing:** Essential for distributing data and load across many nodes.
6.  **Leader Election (ZooKeeper/etcd):** For maintaining strong consistency and availability in distributed systems, especially for sequence numbering.
7.  **CAP Theorem & Consistency Models:** Understanding the trade-offs between consistency, availability, and partition tolerance.

One common mistake candidates make:
*   **Ignoring non-functional requirements:** Many candidates jump straight into functional features without first clarifying scale, latency, and availability, leading to designs that wouldn't hold up in a real-world scenario. The candidate here correctly prioritized these early on.
