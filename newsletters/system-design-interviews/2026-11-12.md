**Interviewer:** Welcome. Today, we're designing an Authentication System. Imagine you're building this for a new platform. How would you approach it?

**Candidate:** Thank you. I'll start by clarifying the **1. Requirements**, then move to **2. Back-of-the-envelope estimates**, **3. API design**, **4. Data model and storage choice**, **5. High-level design**, **6. Deep dives** into specific components, **7. Bottlenecks, failure modes, and trade-offs**, and finally a **8. Wrap-up**.

## Requirements

**Candidate:** First, for functional requirements, I'd expect the system to handle user registration, user login, password management including resets, and session management, which involves issuing, validating, and revoking user sessions. Are there any other core functional aspects I should consider?

**Interviewer:** That covers the basics. Let's focus on those. Now, for non-functional requirements, how many users are we talking about, and what's the expected load?

**Candidate:** For scale, what's our target? How many registered users, and what's the peak login rate?

**Interviewer:** We anticipate a hundred million registered users within a year. Peak login attempts could hit ten thousand requests per second, with an average of around one thousand requests per second.

**Candidate:** Got it. One hundred million users, ten thousand peak QPS. What about latency for a login request?

**Interviewer:** Login should feel snappy, so under one hundred milliseconds for the user-facing part.

**Candidate:** And availability?

**Interviewer:** High availability, aiming for four nines, or 99.99%.

**Candidate:** Excellent. For consistency, I'd argue that strong consistency is crucial for user creation and password changes, ensuring that once a user is registered or a password updated, it's immediately reflected across the system. For session revocation, we might tolerate eventual consistency for a very short period, say a few seconds. Does that sound right?

**Interviewer:** That sounds reasonable. And security, of course, is paramount.

**Candidate:** Absolutely. We'll need robust protection against common attacks like brute force, credential stuffing, replay attacks, and secure handling of tokens to prevent XSS and CSRF.

## Back-of-the-envelope estimates

**Candidate:** With one hundred million users, let's estimate storage. Each user record might contain a user ID, username, hashed password, salt, email, creation timestamp, and last login timestamp. If we assume about two hundred bytes per user record, that's roughly twenty gigabytes for all user data. This is very manageable for a modern database.

**Candidate:** For sessions, if we assume one percent of users are concurrently active, that's one million active sessions. Each session record might include a session ID, user ID, expiry time, issued time, and some device information. Let's say one hundred bytes per session. That's about one hundred megabytes of session data. Again, quite manageable.

**Candidate:** For bandwidth, a login request and response are small, perhaps a few kilobytes. At ten thousand requests per second, that's about ten to twenty megabytes per second of traffic, which is well within typical network capacities.

**Candidate:** Database operations will be the main concern. We're looking at ten thousand reads per second for user lookups during login, and ten thousand writes per second for creating or updating sessions. These numbers suggest we need a database that can handle high read and write throughput, potentially requiring scaling strategies like sharding or read replicas.

## API design

**Candidate:** For the external-facing APIs, I'd propose the following:

**Candidate:** First, for user registration:
`POST /register`
This would take `username` and `password` in the request body. On success, it returns `201 Created`. If the username already exists, it returns `409 Conflict`.

**Candidate:** Next, for user login:
`POST /login`
This also takes `username` and `password`. On successful authentication, it returns `200 OK` with a `session_token` in the response body, perhaps as a JSON object. If credentials are incorrect, it returns `401 Unauthorized`.

**Candidate:** For user logout:
`POST /logout`
This would take the `session_token` in the request header. It returns `200 OK` on success, effectively invalidating the session.

**Candidate:** For password reset, we'd need a two-step process:
`POST /password/reset/request`
This takes an `email` address. It sends a password reset link to the user's email. It returns `200 OK` regardless of whether the email exists, to avoid leaking user information.

**Candidate:** And then:
`POST /password/reset/confirm`
This takes a `reset_token` received via email and the `new_password`. It returns `200 OK` on successful password update.

**Candidate:** Finally, for internal services that need to verify a user's session, we'd have an internal API:
`POST /validate`
This takes a `session_token` and returns `200 OK` with the `user_id` and potentially user roles or permissions, or `401 Unauthorized` if the token is invalid or expired.

## Data model and storage choice

**Candidate:** For our data model, I'd define three main entities: Users, Sessions, and Password Reset Requests.

**Candidate:** The `Users` table would store:
*   `user_id` (Primary Key, UUID)
*   `username` (Unique Index, string)
*   `email` (Unique Index, string)
*   `password_hash` (string)
*   `salt` (string)
*   `created_at` (timestamp)
*   `last_login_at` (timestamp)

**Candidate:** The `Sessions` table would store:
*   `session_id` (Primary Key, UUID)
*   `user_id` (Foreign Key to Users table)
*   `token_hash` (string, if using opaque tokens, or a hash of the JWT for blacklisting)
*   `expires_at` (timestamp)
*   `issued_at` (timestamp)
*   `device_info` (string, e.g., browser, OS)
*   `ip_address` (string)

**Candidate:** The `Password_Resets` table would store:
*   `reset_token` (Primary Key, UUID)
*   `user_id` (Foreign Key to Users table)
*   `expires_at` (timestamp)
*   `is_used` (boolean)

**Candidate:** For storage choice, given the need for strong consistency, ACID properties, and the relational nature of our data, a relational database like PostgreSQL or MySQL would be an excellent choice. It handles complex queries, transactions, and relationships well. We can easily scale it with read replicas for user lookups and sharding if necessary.

**Interviewer:** Why not a NoSQL database, like Cassandra or MongoDB, especially with your high QPS estimates?

**Candidate:** That's a good question. While NoSQL databases offer high scalability and availability, they often trade off strong consistency and complex querying capabilities. For core user authentication data, strong consistency is paramount. A user's password change must be immediately consistent. While we could use a NoSQL database for sessions, I prefer starting with a relational database for both users and sessions to maintain data integrity and simplify the initial design. We can always introduce a high-performance key-value store like Redis for session caching or blacklisting later as an optimization, if the relational database becomes a bottleneck for session lookups. This follows the principle of "start simple, then optimize."

## High-level design

**Candidate:** At a high level, our system would consist of several components:

**Candidate:** First, the **Client**, which could be a web browser or a mobile application, making requests to our system.

**Candidate:** These requests would first hit a **Load Balancer**, which distributes traffic across multiple instances of our Authentication Service for high availability and scalability. This is a standard **load balancing pattern**.

**Candidate:** The core component is the **Authentication Service**, a stateless microservice responsible for handling all authentication-related API endpoints. It encapsulates the business logic for registration, login, session management, and password resets.

**Candidate:** The Authentication Service interacts with two primary databases:
1.  A **User Database**, which is our relational database storing user credentials and profiles. This would likely be a PostgreSQL cluster with read replicas.
2.  A **Session Database**, which could initially be part of the same PostgreSQL cluster, or a separate, optimized store like Redis for faster session lookups and expiry.

**Candidate:** We would also integrate with an **Email Service** for sending password reset links and potentially other notifications.

**Candidate:** Let's walk through a login request.
1.  The client sends a `POST /login` request with username and password.
2.  The Load Balancer forwards it to an available instance of the Authentication Service.
3.  The Authentication Service first applies **rate limiting** based on the IP address and username to prevent brute-force attacks. This is a **security pattern** to protect against malicious attempts.
4.  It then queries the User Database to fetch the user record, specifically the stored `password_hash` and `salt` associated with the provided username.
5.  Using a strong, adaptive hashing algorithm like bcrypt or scrypt, it hashes the password provided by the user with the retrieved salt. This is the **salted password hashing pattern**.
6.  It compares the newly computed hash with the stored `password_hash`.
7.  If they match, the user is authenticated. The Authentication Service then generates a session token. I'd lean towards using **JSON Web Tokens, or JWTs**, for access tokens. These are self-contained and signed, allowing for stateless validation by other services without hitting the database on every request. This is a **stateless authentication pattern**.
8.  It stores relevant session details in the Session Database, particularly if we're using refresh tokens, which are typically opaque and stored in the database for easier revocation.
9.  Finally, the Authentication Service returns the JWT to the client.

**Candidate:** If the hashes don't match, or if rate limits are exceeded, it returns an appropriate error response like `401 Unauthorized`.

## Deep dives

**Interviewer:** You mentioned JWTs. Can you elaborate on how you'd manage sessions with JWTs, especially regarding revocation and security?

**Candidate:** Absolutely. This is a crucial deep dive. JWTs are powerful because they are self-contained and signed. Once issued, any service with the public key can verify its authenticity and extract user information without needing to query a central session store. This significantly reduces database load on subsequent requests, which is a performance optimization.

**Candidate:** However, the challenge with JWTs is revocation. Since they're stateless, there's no central "off switch" once issued until they expire. To handle revocation, for example, when a user logs out or an admin forces a logout, we'd implement a **JWT Blacklist**. This is a **security pattern** for immediate revocation.

**Candidate:** When a token needs to be revoked, its unique ID, or JTI, is added to a fast, in-memory store like Redis, along with its original expiry time. Any subsequent validation of that token would first check the Redis blacklist. If found, the token is considered invalid. This introduces a slight delay for revocation propagation, but Redis is very fast, so it's typically in milliseconds.

**Candidate:** For longer sessions, I would use a **hybrid approach**: a short-lived JWT as an access token, and a longer-lived opaque **refresh token**. The access token is used for most API calls and has a short expiry, say fifteen minutes. The refresh token, which is stored in the Session Database, is used to obtain new access tokens when the current one expires. When a user logs out, we revoke the refresh token in the database and add the active access token's JTI to the blacklist. This provides a balance between statelessness for common operations and stateful control for revocation and long-term sessions. This is a common **token-based authentication pattern**.

**Interviewer:** What about the password hashing you mentioned? Can you explain why bcrypt or scrypt are preferred over simpler hashes like MD5 or SHA-256?

**Candidate:** That's another critical security deep dive. Simpler hash functions like MD5 or SHA-256 are designed to be fast. While they're one-way, meaning you can't reverse them to get the original password, their speed makes them vulnerable to **brute-force attacks** and **rainbow table attacks**. A rainbow table is a precomputed table of hashes for common passwords.

**Candidate:** Cryptographic hash functions like bcrypt, scrypt, or Argon2 are specifically designed to be *slow* and computationally intensive. They achieve this by using a configurable "cost factor" or "work factor," which determines how many rounds of hashing are performed. This makes it prohibitively expensive for attackers to generate rainbow tables or brute-force passwords, even with powerful hardware.

**Candidate:** Additionally, these functions inherently incorporate a **salt**, which is a unique, random string generated for each password. The salt is stored alongside the hash. This is the **salting pattern**. The salt ensures that even if two users have the same password, their hashes will be different, preventing attackers from using rainbow tables across multiple users and making dictionary attacks much harder. So, in summary, they are slow by design and use salts, which are two key security features.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks. The primary bottleneck would be the **User Database** for read operations during login, and the **Session Database** for write operations when creating or updating sessions, especially at peak load. To mitigate this, we'd use read replicas for the User Database to distribute read load. For the Session Database, we could shard it by `user_id` or `session_id` to distribute write load. If we use Redis for sessions, it's inherently designed for high throughput.

**Candidate:** Another potential bottleneck is the **rate limiting service** itself. If it's a single point of failure or contention, it could become a bottleneck. We'd need a distributed rate limiting solution, perhaps using Redis clusters to store counters across multiple nodes.

**Candidate:** For failure modes, if an **Authentication Service instance crashes**, the Load Balancer will detect it and route traffic to healthy instances, ensuring high availability. If the **database fails**, we rely on replication and automated failover mechanisms to promote a replica to primary, minimizing downtime.

**Candidate:** A critical failure mode is the **compromise of the JWT signing key**. If an attacker gains access to this key, they could forge valid JWTs. To mitigate this, we must store the signing key securely, rotate it regularly using a **key rotation pattern**, and use robust key management systems like HashiCorp Vault or AWS Key Management Service.

**Candidate:** Let's consider some trade-offs. There's always a **trade-off between security and performance**. Strong hashing algorithms like bcrypt are CPU-intensive, adding latency to login. However, the security benefits far outweigh the minor performance hit. Similarly, while JWTs offer fast, stateless validation, their revocation mechanism adds complexity and a slight delay.

**Candidate:** Another trade-off is **consistency versus availability**. We chose strong consistency for user data, which can sometimes impact availability during database failures. For session revocation, we accepted a brief period of eventual consistency with our blacklist approach, prioritizing performance and availability for the majority of requests.

**Interviewer:** What changes if we scale this to ten times the current load, say a billion users and one hundred thousand QPS?

**Candidate:** At ten times the scale, our current design would need significant enhancements. The **database sharding** for both User and Session data would become absolutely essential. We'd likely move from a few shards to hundreds or even thousands, potentially using a sharding proxy or a database-as-a-service solution that handles sharding automatically.

**Candidate:** The number of **Authentication Service instances** would increase dramatically. We'd need a highly elastic infrastructure, perhaps leveraging auto-scaling groups in the cloud.

**Candidate:** The **Redis cluster** for JWT blacklisting and potentially for session storage would become even more critical, requiring careful sizing and partitioning. We might even consider a dedicated, highly optimized **distributed rate limiting service** rather than embedding it directly in the Auth Service.

**Candidate:** At this scale, we might also re-evaluate the choice of a relational database for sessions. A purpose-built, highly scalable NoSQL database like DynamoDB or Cassandra could be considered for session storage, trading off some relational features for extreme write throughput and availability, especially if session data becomes very large and access patterns are simple key-value lookups. This would be a **data store specialization pattern**.

## Wrap-up

**Candidate:** To summarize, we've designed a robust Authentication System capable of handling one hundred million users and ten thousand peak QPS. It features a stateless Authentication Service, backed by a relational database for strong consistency of user credentials, and a hybrid JWT and refresh token approach for session management, leveraging a Redis blacklist for efficient revocation. We've incorporated critical security measures like salted password hashing and rate limiting, and discussed scaling strategies like database sharding and distributed caching to handle future growth and maintain high availability and performance.

The three to five key terms and patterns to remember from this problem are:
1.  **Salted Password Hashing**: Using algorithms like bcrypt or scrypt with unique salts for each password to prevent rainbow table and brute-force attacks.
2.  **JSON Web Tokens (JWTs)**: For stateless authentication, enabling other services to validate tokens without hitting a central database.
3.  **JWT Blacklisting**: A mechanism, often using a fast cache like Redis, to revoke JWTs before their natural expiry.
4.  **Hybrid Token Approach**: Combining short-lived access tokens (JWTs) with longer-lived, opaque refresh tokens for better security and user experience.
5.  **Rate Limiting**: A crucial security measure to protect against brute-force and denial-of-service attacks on authentication endpoints.

One common mistake candidates make when designing an authentication system is confusing authentication with authorization. Authentication is about verifying *who* a user is, while authorization is about determining *what* that user is allowed to do. It's important to keep these concerns separate in the initial design, focusing solely on the authentication aspect as per the problem statement.
