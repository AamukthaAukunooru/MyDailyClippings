**Interviewer:** Alright, let's design a URL shortening service, something like TinyURL or Bitly. The core functionality is to take a long URL and return a much shorter one, and then when someone accesses the short URL, they're redirected to the original long URL.

**Candidate:** Got it. This sounds like a fun problem. I'll start by clarifying the **Requirements**, both functional and non-functional, to ensure we're aligned on the scope.

## Requirements

**Candidate:** For functional requirements, the primary ones are:
1.  Given a long URL, generate a unique, short URL.
2.  When a user accesses the short URL, redirect them to the original long URL.
3.  The short URLs should be reasonably short, ideally six to eight characters.

Are there any other functional aspects we should consider, like custom short URLs, expiration dates, or analytics?

**Interviewer:** Yes, let's add a few.
4.  Allow users to specify a custom short URL if available.
5.  Support optional expiration for short URLs.
6.  We don't need full-blown analytics, but let's track the total number of clicks for each short URL.

**Candidate:** Excellent. Now, for non-functional requirements, let's talk scale, latency, availability, and consistency.
For scale, how many new short URLs do we expect to create per day? And how many redirections per day?

**Interviewer:** We're aiming for a service that can handle a significant load. Let's say one million new short URLs created per day. For redirections, assume a hundred times that, so one hundred million redirections per day.

**Candidate:** Okay, so one million creations and one hundred million redirections daily. That's a good scale target.
What about latency? For redirection, I assume we want very low latency, perhaps under 50 milliseconds, as it's directly in the user's critical path. For creation, it can be slightly higher, maybe a few hundred milliseconds.

**Interviewer:** That sounds reasonable. Under 50 milliseconds for redirects, and under 500 milliseconds for creation.

**Candidate:** And for availability? Redirection must be highly available, say 99.99% or even 99.999%. If our redirect service is down, many links across the internet break. Creation can have slightly lower availability, perhaps 99.9%.

**Interviewer:** Agreed. High availability for redirects is critical.

**Candidate:** Finally, consistency. For the mapping between a short URL and a long URL, we need strong consistency. Once a short URL is created, it should immediately redirect to the correct long URL. For click counts, eventual consistency is acceptable. A slight delay in updating the total count isn't critical.

**Interviewer:** Strong consistency for mapping, eventual for click counts. Perfect.

## Back-of-the-envelope estimates

**Candidate:** With those numbers, let's do some **Back-of-the-envelope estimates**.
First, requests per second.
For creations: One million creations per day, divided by 24 hours, divided by 60 minutes, divided by 60 seconds. That's roughly 1,000,000 / 86,400, which is about 12 new URLs per second. This is a relatively low write load.
For redirections: One hundred million redirections per day. That's 100,000,000 / 86,400, which is approximately 1,157 redirections per second. Let's round that up to about 1,200 requests per second. This is a significant read load.

Next, storage.
Each short URL needs to store:
*   The short key: Let's assume six to eight characters. If we use base62 encoding, six characters gives us 62^6 unique keys, which is over 56 billion. Eight characters gives us 62^8, which is over 218 trillion. Six characters should be plenty for our scale. So, six to eight bytes for the key.
*   The long URL: URLs can be quite long. Let's assume an average of 255 characters, or 255 bytes.
*   Creation date, expiration date: Say 8 bytes each for timestamps.
*   Click count: An integer, say 4 bytes.
*   User ID (if applicable, for custom URLs): Say 8 bytes.
*   Some overhead for indexing, etc. Let's estimate around 300 to 400 bytes per entry.

If we have one million new URLs per day, over five years, that's 1,000,000 * 365 * 5, which is about 1.8 billion URLs.
At 400 bytes per entry, 1.8 billion entries * 400 bytes/entry = 720 billion bytes, or about 720 gigabytes. This is a manageable amount of data for a single database, but it will grow.

Finally, bandwidth.
For redirections, each request involves a small short key lookup and then a 301 or 302 HTTP redirect, which sends back a `Location` header. The response size is very small, perhaps a few hundred bytes.
1,200 redirects per second * 400 bytes/response = 480,000 bytes/second, or about 0.5 megabytes per second. This is very low. The main bandwidth concern will be the actual traffic to the long URLs after redirection, but that's outside our service's direct responsibility.

So, the key takeaways from estimates are:
*   Read-heavy workload, about 1,200 reads per second.
*   Relatively low write workload, about 12 writes per second.
*   Total storage for five years is under a terabyte, which is significant but manageable.

## API design

**Candidate:** Now let's define the **API design**. We'll need at least two main endpoints.

First, for creating a short URL:
`POST /shorten`
This endpoint would accept a JSON body:
```
{
  "long_url": "https://www.example.com/very/long/path/to/resource",
  "custom_key": "mycustomlink", // Optional
  "expiration_date": "2025-12-31T23:59:59Z" // Optional
}
```
It would return a JSON response:
```
{
  "short_url": "https://mydomain.com/abcde"
}
```
If the `custom_key` is already taken, or `long_url` is invalid, it would return an appropriate HTTP error code, like 400 Bad Request or 409 Conflict.

Second, for redirection:
`GET /{short_key}`
This endpoint would take the `short_key` as a path parameter.
It would perform an HTTP 301 (Permanent Redirect) or 302 (Found/Temporary Redirect) to the `long_url`. For general purposes, 302 is safer as it allows the target to change. We should also consider how to handle expired or non-existent keys, returning a 404 Not Found.

**Interviewer:** That looks solid. How would you handle the click tracking?

**Candidate:** Good point. For click tracking, we could increment a counter associated with the short key *after* the redirect has been issued. This way, it doesn't add latency to the critical redirect path. We could do this asynchronously.

## Data model and storage choice

**Candidate:** Moving on to the **Data model and storage choice**.
Based on our requirements, we need to store:
*   `short_key` (String, primary key)
*   `long_url` (String)
*   `creation_date` (Timestamp)
*   `expiration_date` (Timestamp, nullable)
*   `click_count` (Integer, default 0)
*   `user_id` (String, nullable, for custom URLs)

Given the read-heavy nature, simple key-value lookups, and the need for high availability and scalability, a NoSQL key-value store like Amazon DynamoDB or Apache Cassandra would be a strong candidate. These databases are designed for high throughput reads and writes, and scale horizontally well.

Let's consider DynamoDB for this design. Its managed nature simplifies operations, and it offers single-digit millisecond latency at any scale. The primary key would be `short_key`. We would configure provisioned throughput or use on-demand capacity to handle the read and write loads.

Why not a relational database like PostgreSQL? While it could handle the initial scale, especially with proper indexing and read replicas, scaling beyond a certain point for 1,200 reads per second and potentially billions of rows would eventually require sharding, which adds operational complexity. For the simple key-value access pattern, a NoSQL store is generally a better fit for high scale.

**Interviewer:** What about the uniqueness constraint for custom keys? How would DynamoDB handle that efficiently?

**Candidate:** That's a great question. For custom keys, when a user requests `mycustomlink`, we'd first try to write that specific `short_key` to DynamoDB. DynamoDB has a conditional write feature. We can attempt to put an item only if an item with that `short_key` does not already exist. This is an **optimistic concurrency control** mechanism. If the write fails because the key already exists, we return a 409 Conflict. This is efficient for handling custom key uniqueness.

## High-level design

**Candidate:** Let's outline the **High-level design**.

At a high level, users interact with our service through a load balancer.

1.  **Clients:** Browsers or applications.
2.  **Load Balancer:** Distributes incoming requests across our service instances.
3.  **API Gateway / Web Servers:** These handle both creation and redirection requests. We could have separate services or a single service with different endpoints. For simplicity, let's assume a single service for now, but we'd likely split them for better isolation and scaling.

**Creation Flow (POST /shorten):**
*   A client sends a `POST /shorten` request with the `long_url` and optional `custom_key` and `expiration_date`.
*   The request hits a web server.
*   If a `custom_key` is provided, the service attempts to use it. If not, it calls a `Key Generation Service` to get a unique `short_key`.
*   The service then attempts to store the `short_key`, `long_url`, and metadata in our `DynamoDB` table. For custom keys, it uses a conditional write.
*   If successful, it returns the `short_url` to the client. If there's a collision with a custom key, it returns an error.

**Redirection Flow (GET /{short_key}):**
*   A client sends a `GET /{short_key}` request.
*   The request hits a web server.
*   The service first checks a `Distributed Cache` (like Redis or Memcached) for the `short_key`. This is the **cache-aside pattern**.
*   If the `short_key` is found in the cache and is not expired, it retrieves the `long_url` and issues an HTTP 302 redirect.
*   If not in cache, or expired, it queries `DynamoDB` using the `short_key`.
*   If found in DynamoDB, it stores the `long_url` in the cache for future requests and then issues the HTTP 302 redirect.
*   If not found in DynamoDB, it returns an HTTP 404 Not Found.
*   Asynchronously, after the redirect, the service increments the `click_count` for that `short_key` in DynamoDB. This is an **asynchronous update** to avoid impacting redirect latency.

## Deep dives

**Interviewer:** Let's dive deeper into a few areas. How exactly would you design the `Key Generation Service` to ensure unique, short keys at scale, and handle collisions effectively?

**Candidate:** The **Key Generation Service** is crucial. There are a few approaches.

One common method is to use a distributed unique ID generator, like Twitter's Snowflake, to generate a 64-bit integer ID. Then, we can convert this integer ID into a base62 string. Base62 uses 0-9, a-z, A-Z, giving 62 characters. This is a **deterministic encoding**. A 64-bit integer can be encoded into a string of about 11 characters in base62. We could then truncate or ensure it's within our 6-8 character range. The advantage is that the IDs are globally unique, and we avoid database lookups for uniqueness during generation.

Another approach, simpler for our scale, is to generate random strings of a fixed length, say six characters, using base62 characters. For example, `random(62^6)`. The probability of collision with 56 billion possible keys is extremely low for our current 12 writes per second. However, we still need to check for collisions.

My preferred approach for this problem is a hybrid:
1.  **Pre-generate keys:** The Key Generation Service could pre-generate a large batch of unique short keys, store them in a dedicated table in DynamoDB, or even a distributed queue like Kafka or SQS. These keys would be marked as "available".
2.  **Key Allocation:** When a new short URL request comes in *without* a custom key, the service picks an available key from this pool, marks it as "used", and then proceeds with the storage. This ensures uniqueness without contention at the time of request. This is a form of **producer-consumer pattern**.
3.  **Collision Handling:**
    *   For pre-generated keys, collisions are avoided because they are pulled from a unique pool. If a key is picked and then the write to the main URL mapping table fails for some reason, we'd need a mechanism to return the key to the pool or mark it as invalid.
    *   For custom keys, as I mentioned, we use DynamoDB's conditional write. If the `short_key` already exists, the write fails, and we inform the user. If the write succeeds, the custom key is now owned.

**Interviewer:** What happens if the Key Generation Service itself goes down, or if the pool of pre-generated keys runs out?

**Candidate:** That's a critical failure mode.
If the Key Generation Service goes down, new URL creation requests without custom keys would fail. We'd need to ensure this service is highly available, perhaps running multiple instances behind a load balancer, and using a robust key generation algorithm that can tolerate individual node failures, like a distributed ID generator.
If the pool of pre-generated keys runs out, new creation requests would also fail. To prevent this, the Key Generation Service would monitor the pool size and continuously replenish it when it falls below a certain threshold. This is a **circuit breaker pattern** for the key generation, where we fail fast if no keys are available, but also ensure proactive replenishment. We could also have a fallback mechanism to generate a random key on the fly and handle collisions via retries, though this adds latency.

Let's also dive into **Redirection Performance**.
The 1,200 reads per second and 50ms latency requirement mean our read path must be extremely fast. The `Distributed Cache` is key here.
We'd use a **cache-aside pattern** with Redis Cluster or Memcached.
*   When a request for a `short_key` comes in, we first check the cache.
*   If it's a cache hit, we return the `long_url` immediately. This is our fast path.
*   If it's a cache miss, we query DynamoDB.
*   After retrieving from DynamoDB, we populate the cache before returning the `long_url`.
*   We'd set a Time-To-Live (TTL) for cache entries, perhaps 24 hours or longer, depending on how frequently URLs change or expire. This handles cache invalidation for non-expiring URLs. For expiring URLs, we can set the cache TTL to match the URL's expiration date.

We could also use a **Content Delivery Network (CDN)**, but for redirects, it's less straightforward. CDNs are great for caching static content. While they can cache HTTP redirects, the primary benefit of a URL shortener is the dynamic lookup. However, a CDN could sit in front of our web servers to handle TLS termination and distribute initial connection load, which improves overall performance and security.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Now, let's discuss **Bottlenecks, failure modes, and trade-offs**.

**Bottlenecks:**
1.  **DynamoDB:** While highly scalable, if not provisioned correctly, it can become a bottleneck for both reads and writes. Our read load is 1,200 RPS, and writes are 12 RPS. DynamoDB can handle this, but monitoring and scaling read/write capacity units is crucial.
2.  **Key Generation Service:** As discussed, if it fails or runs out of keys, creation requests suffer.
3.  **Distributed Cache (Redis/Memcached):** If the cache cluster goes down, all redirect requests will hit DynamoDB, potentially overwhelming it and increasing latency significantly. This is a **cascading failure** scenario.

**Failure Modes:**
*   **Database Failure:** If DynamoDB experiences an outage, both creation and redirection fail (unless the cache can serve all requests, which is unlikely for a full outage). We'd mitigate this with multi-region deployments and backups.
*   **Cache Failure:** As mentioned, this leads to increased load on the database. We'd mitigate with redundant cache nodes and automatic failover.
*   **Web Server Failure:** Individual web servers can fail; the load balancer will route around them. We'd ensure autoscaling groups replace failed instances.
*   **Expired/Invalid URLs:** Our service needs to gracefully handle these, returning 404s.

**Trade-offs:**
*   **Key Length vs. Collision Probability:** Shorter keys are more desirable but increase collision probability. Our 6-8 character base62 keys offer a good balance for scale.
*   **Strong vs. Eventual Consistency for Click Counts:** We chose eventual consistency for click counts to prioritize redirect latency, which is a common and acceptable trade-off.
*   **Custom Keys vs. Random Keys:** Custom keys add complexity (collision handling, user management) but provide user value. Random keys are simpler to implement.
*   **Pre-generating Keys vs. On-the-fly Generation:** Pre-generating reduces latency for key generation during a request but adds complexity to manage the key pool. On-the-fly generation is simpler but might involve retries on collision.

**What changes at ten times the scale?**
If we go to ten million creations and one billion redirections per day:
*   **RPS:** 120 creations/sec, 12,000 redirections/sec.
*   **Storage:** 7.2 terabytes over five years.
*   **Database:** DynamoDB would still be a good choice, but we'd need to significantly increase its provisioned capacity. We might consider sharding our data if we were using a relational database, but DynamoDB handles this internally.
*   **Cache:** The distributed cache would need to be much larger and more robust, potentially spanning multiple clusters or regions.
*   **Key Generation Service:** The pre-generated key pool would need to be much larger, and the generation rate would need to increase. We might lean more towards a truly distributed ID generation system like Snowflake to avoid centralizing key generation.
*   **Service Architecture:** We'd likely split the creation and redirection services into separate microservices for independent scaling and deployment. This is the **separation of concerns** principle.
*   **Monitoring and Alerting:** Becomes even more critical to detect and respond to issues quickly.

## Wrap-up

**Candidate:** To wrap up, we've designed a highly available and scalable URL shortening service. It handles one million creations and one hundred million redirections daily, with low latency. The core components include a web service layer, a distributed cache for fast redirects using the cache-aside pattern, and a NoSQL key-value store like DynamoDB for persistent storage. Key generation can be handled by a dedicated service, potentially pre-generating keys to ensure uniqueness and performance. We've considered trade-offs like key length and consistency for click counts, and discussed how the system would scale to ten times the load by increasing capacity and potentially further decoupling services.

Three to five key terms and patterns to remember from this problem:
