**Interviewer:** Hi, thanks for coming in. Today, let's design a system for rate limiting. Imagine we need to protect our various APIs from abuse and ensure fair usage. How would you approach designing a distributed rate limiter?

**Candidate:** Absolutely. This is a classic problem with many interesting trade-offs. I'll start by clarifying the **1. Requirements**.

First, for functional requirements:
What entities do we want to rate limit? Is it per user, per IP address, per API key, or perhaps per specific API endpoint?
What are typical rate limits? For example, a certain number of requests per second, per minute, or per hour?
What should happen when a request exceeds the limit? Should it be rejected, queued, or something else?

**Interviewer:** Good questions. Let's assume we need to support rate limiting by user ID and by API endpoint. For example, a user might be limited to one hundred requests per minute on a specific `POST /items` endpoint, and also to five thousand requests per hour across all endpoints. When a limit is exceeded, the request should be immediately rejected with an HTTP 429 Too Many Requests status code.

**Candidate:** Got it. So, user ID and endpoint-specific limits, with immediate rejection. This implies we need a fast check.

Now, for non-functional requirements:
What kind of scale are we talking about? How many total requests per second does our platform handle?
What's the acceptable latency overhead for the rate limiting check?
How important are availability and consistency? For example, is it acceptable for a few requests to slip through if a rate limiter node fails, or do we need strict enforcement even under failure?

**Interviewer:** Our platform handles about one hundred thousand requests per second on average, with peaks up to five hundred thousand requests per second. The rate limiting check should add no more than five milliseconds of latency. Availability is paramount; the rate limiter should not become a single point of failure. For consistency, it's acceptable if a user slightly exceeds their limit during a brief period of system inconsistency, say, for a few seconds, but it should self-correct quickly.

**Candidate:** Okay, five hundred thousand requests per second peak, five milliseconds latency, high availability, and eventual consistency is acceptable. This gives us some flexibility.

## Back-of-the-envelope estimates

**Candidate:** Next, I'll do some **2. Back-of-the-envelope estimates**.
At five hundred thousand requests per second, we need a system that can handle this throughput.
If we're tracking limits per user and per endpoint, let's assume we have one hundred million active users and one thousand distinct API endpoints.
Each user might have multiple limits, say, one hundred requests per minute for `POST /items` and five thousand requests per hour for all APIs. So, for each active user, we might need to track a few counters.
If we use a Sliding Window Counter algorithm, which I'll explain later, we'd need to store a timestamp and a counter for each window. For a minute-long window, we'd have one counter. For an hour-long window, we'd have another.
Let's say, on average, each user has five active rate limits. That's one hundred million users times five limits per user, which is five hundred million distinct counters.
Each counter needs a key, a value, and potentially a timestamp. A key might be fifty bytes, a counter eight bytes, and a timestamp eight bytes. That's about sixty-six bytes per counter.
Five hundred million counters times sixty-six bytes is roughly thirty-three gigabytes of data. This is a manageable amount to keep in memory for a distributed cache like Redis.
For bandwidth, at five hundred thousand requests per second, each request involves at least one read and potentially one write to update the counter. If each operation is, say, one hundred bytes of network traffic, that's fifty megabytes per second, which is also well within typical network capacities.

## API design

**Candidate:** Now, let's think about the **3. API design**. The rate limiter will likely be a service that other backend services call before processing a request.
I envision a simple API:
`check_limit(user_id, endpoint_name, client_ip)`
This API would take the `user_id`, the `endpoint_name` (like `POST /items`), and optionally the `client_ip` if we also wanted to rate limit by IP.
It would return a boolean indicating `allowed` or `denied`, and potentially a `retry_after` timestamp if denied, which is useful for clients.

**Interviewer:** Why pass `user_id` and `endpoint_name` explicitly? Couldn't the rate limiter service infer this from the request context?

**Candidate:** That's a good point. The rate limiter could indeed infer some context if it were deployed as a gateway or a proxy. However, for maximum flexibility and to allow different services to define their own specific rate limiting policies, it's often better for the calling service to explicitly provide the context. This adheres to the **Principle of Least Astonishment** by making the inputs clear and explicit. It also simplifies the rate limiter service itself, as it doesn't need to parse HTTP requests or understand application-specific routing.

## Data model and storage choice

**Candidate:** Moving on to the **4. Data model and storage choice**.
Given the low latency requirement and the need for atomic increments, an in-memory key-value store is ideal. Redis is a perfect fit here.
The data model would be simple:
Key: `rate_limit:{policy_name}:{entity_id}:{window_start_timestamp}`
Value: `counter`
For example, `rate_limit:user:123:post_items:1678886400` could store the count for user 123 on `POST /items` for a specific time window.
The `policy_name` would encode the specific limit, like `user_post_items_per_minute` or `user_all_apis_per_hour`.
Redis's `INCR` command is atomic, which is crucial for correctly updating counters in a concurrent environment. We can also use `EXPIRE` to automatically remove old window counters, preventing unbounded memory growth.

**Interviewer:** Why Redis over, say, Cassandra or a relational database?

**Candidate:** That's an excellent question. While Cassandra or a relational database could store the data, they introduce significant latency.
Relational databases like PostgreSQL would struggle with the high write throughput and the need for atomic increments across many keys per second. Their disk-based nature and transaction overhead would make it difficult to meet the five-millisecond latency requirement.
Cassandra, a NoSQL wide-column store, offers high write throughput and scalability, but its eventual consistency model might make atomic increments tricky without careful design, and it's still generally slower than an in-memory store for single-key operations.
Redis, being an in-memory data structure store, provides sub-millisecond latency for `INCR` operations and supports automatic expiration, which is exactly what we need for time-windowed counters. Its single-threaded nature means operations are atomic by default, which simplifies concurrent access. This is a classic use case for Redis.

## High-level design

**Candidate:** Let's outline the **5. High-level design**.
Clients make requests to our services. These requests first hit a **Load Balancer**, which distributes them to our various **Application Services**.
Before an Application Service processes a request, it will make an internal call to our new **Rate Limiter Service**.
The Rate Limiter Service itself will consist of multiple instances to ensure high availability and scalability. These instances will communicate with a distributed **Redis Cluster**.
When a request comes into the Rate Limiter Service:
1. It identifies the relevant rate limiting policies based on the `user_id`, `endpoint_name`, and other parameters.
2. For each policy, it constructs the appropriate Redis key for the current time window.
3. It performs an atomic `INCR` operation on the Redis key.
4. It checks if the new counter value exceeds the defined limit for that policy. If it's the first increment in a new window, it also sets an `EXPIRE` time on the key.
5. If any policy limit is exceeded, the Rate Limiter Service returns `denied`. Otherwise, it returns `allowed`.
If `denied`, the Application Service immediately returns a 429 response to the client. If `allowed`, the Application Service proceeds to handle the request.

## Deep dives

**Candidate:** For **6. Deep dives**, let's focus on the rate limiting algorithm and distributed aspects.

I'd propose using the **Sliding Window Counter** algorithm. This algorithm offers a good balance between accuracy and resource usage, especially compared to the Fixed Window algorithm, which suffers from burstiness at window edges.
Here's how it works for a limit of `N` requests per `T` seconds:
When a request arrives at time `current_time`:
1. Calculate the current window's counter key: `key_current = {entity_id}:{policy}:{floor(current_time / T) * T}`.
2. Calculate the previous window's counter key: `key_previous = {entity_id}:{policy}:{floor(current_time / T - 1) * T}`.
3. Fetch the counts for `key_current` and `key_previous` from Redis.
4. The effective count for the current sliding window is calculated as: `(count_previous * (time_remaining_in_previous_window / T)) + count_current`.
5. If this effective count is less than `N`, increment `key_current` atomically in Redis and allow the request. Otherwise, deny it.
This approach smooths out traffic more effectively than Fixed Window by considering a weighted average of the previous window's activity. The `INCR` operation in Redis ensures atomicity, which is critical.

**Interviewer:** That's a solid choice. What about the distributed nature of the Redis cluster? How do you ensure consistency and prevent race conditions when multiple rate limiter service instances are updating the same counter?

**Candidate:** That's where Redis Cluster comes in. Redis Cluster automatically shards data across multiple Redis nodes. When our Rate Limiter Service makes an `INCR` request for a specific key, Redis Cluster ensures that request is routed to the correct node responsible for that key's hash slot. Because Redis operations are single-threaded, `INCR` on a specific key is atomic on that node.

However, we must consider the distributed nature of the rate limiter service instances themselves. If multiple instances simultaneously try to increment the same counter, Redis's atomicity handles this. The challenge comes if we need to *read* the current count, *decide* if it's allowed, and *then* increment. This read-modify-write pattern can lead to race conditions if not handled carefully.
The Sliding Window Counter algorithm mitigates this by always incrementing first and then checking. We use a Redis Lua script for this. A **Lua script** in Redis runs atomically, meaning the entire script executes as a single, uninterruptible operation on the Redis server. This allows us to fetch the current count, calculate the effective count, check the limit, and then increment, all within a single atomic operation, completely eliminating race conditions at the Redis level.

**Interviewer:** What happens if a Redis node dies? Our requirement was high availability.

**Candidate:** If a Redis node dies, Redis Cluster's replication mechanism kicks in. Each master node in a Redis Cluster has one or more replica nodes. If a master fails, one of its replicas is automatically promoted to master. This ensures that our data remains available and our rate limiter service can continue functioning without interruption. This is an example of **Leader-Replica Replication** for high availability. The failover process is usually quite fast, minimizing downtime. During the brief failover, some requests might experience slightly higher latency, but the system remains available.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss **7. Bottlenecks, failure modes and trade-offs**.

A potential bottleneck could be the **Redis Cluster itself**. While Redis is very fast, a single shard might become a hot spot if one user or endpoint generates an extremely high volume of requests. We can mitigate this by:
1. **Sharding**: Redis Cluster already shards data, but we can design our keys to distribute load more evenly. For example, if a single `user_id` is a hot spot, we might need to consider a different sharding key or even a different rate limiting strategy for such extreme cases, perhaps using a client-side rate limiter or a more aggressive firewall rule.
2. **Dedicated Redis instances**: For very high-volume policies, we could use dedicated Redis instances or clusters.

Another bottleneck could be **network latency** between the Application Service and the Rate Limiter Service, or between the Rate Limiter Service and Redis. We can minimize this by:
1. **Co-locating services**: Deploying the Rate Limiter Service and Redis Cluster in the same data center or availability zone as the Application Services.
2. **Batching**: If a single request needs to check multiple limits, we could potentially batch these checks into a single call to the Rate Limiter Service, reducing network round trips.

**Failure Modes:**
- **Redis Cluster failure**: As discussed, replication and failover handle node failures. A complete cluster outage would be catastrophic, but highly unlikely with proper setup.
- **Rate Limiter Service instance failure**: The Load Balancer would detect failed instances and route traffic to healthy ones. This is standard **horizontal scaling** and **load balancing**.
- **Network partitions**: If the Rate Limiter Service loses connection to Redis, it can't perform checks. We'd likely fail open (allow requests) or fail closed (deny all requests) depending on the business criticality. Given our requirement for high availability and eventual consistency, failing open for a short period might be acceptable to prevent service disruption, but this is a critical trade-off to discuss with product teams.

**Trade-offs**:
- **Consistency vs. Availability**: We chose eventual consistency, allowing for slight overages during transient issues, in favor of high availability. Strict consistency would require distributed transactions or consensus protocols, adding significant latency and complexity.
- **Accuracy vs. Resource usage**: Sliding Window Counter is a good compromise. Sliding Window Log (storing every request timestamp) would be perfectly accurate but consume much more memory and bandwidth. Fixed Window is less accurate but simpler.
- **Latency vs. Robustness**: The five-millisecond latency target pushes us towards in-memory solutions. If higher latency was acceptable, a persistent store could offer stronger durability guarantees.

**What changes at ten times the scale?**
At five million requests per second, our Redis Cluster would need significantly more shards and potentially more powerful instances. We'd need to carefully monitor hot spots and potentially re-shard data. The network bandwidth would also increase proportionally, requiring careful network design. We might also consider pushing some rate limiting logic closer to the edge, perhaps using a CDN or API Gateway with built-in rate limiting capabilities, to offload some traffic from our internal services. This is an example of **Edge Computing** or **API Gateway Pattern**. The core design principles, however, would remain largely the same.

## Wrap-up

**Candidate:** To wrap up, my design for a distributed rate limiter uses a dedicated **Rate Limiter Service** that interacts with a **Redis Cluster**. We'd employ the **Sliding Window Counter** algorithm, implemented atomically using Redis Lua scripts, to enforce limits per user and per endpoint. The system prioritizes high availability and low latency, accepting eventual consistency for counters. We've considered scaling to five hundred thousand requests per second, with strategies for handling ten times that load, and discussed key trade-offs and failure modes.

## Interviewer's notes

This was a strong answer. The candidate clearly articulated the problem, asked excellent clarifying questions, and followed the structured approach effectively.

Three to five key terms and patterns to remember from this problem:
1.  **Sliding Window Counter Algorithm**: A good balance of accuracy and resource usage for rate limiting, superior to Fixed Window.
2.  **Redis for Distributed Counters**: Its atomic `INCR` operation and `EXPIRE` functionality, combined with its in-memory performance, make it ideal for rate limiting.
3.  **Lua Scripts for Atomicity**: Crucial for ensuring read-modify-write operations on Redis are atomic in a distributed environment, preventing race conditions.
4.  **Eventual Consistency Trade-off**: Acknowledging that strict consistency for rate limits is often too costly and that eventual consistency is a pragmatic choice for many applications.
5.  **High Availability with Redis Cluster**: Understanding how replication and failover mechanisms ensure the rate limiter remains operational even if nodes fail.

One common mistake candidates make:
Many candidates jump straight into a specific algorithm like Token Bucket or Leaky Bucket without first clarifying the requirements. The candidate here correctly started with requirements, which then informed the choice of algorithm and data store. Another common mistake is not addressing the distributed nature of the problem, especially how to handle concurrent updates and consistency across multiple nodes. The candidate correctly brought up Redis Cluster and Lua scripts to address these.
