**Interviewer:** Alright, let's design Pastebin. Imagine you're building a service similar to Pastebin, where users can store and share text snippets. How would you approach designing this system?

**Candidate:** This sounds like a fun problem. I'll start by clarifying the requirements, then move into estimates, API, data model, high-level design, deep dives, and finally, bottlenecks and trade-offs.

## Requirements

**Candidate:** First, let's nail down the functional requirements. What core features do we need? I'm thinking:
One, users can create a new paste by providing text content.
Two, each paste should have a unique, short, and shareable identifier, like `d4fg5h6j`.
Three, users should be able to retrieve a paste using its identifier.
Are there any other must-have features?

**Interviewer:** That's a good start. Let's add a few more. Users should also be able to specify an expiration time for their pastes, such as ten minutes, one hour, one day, or never. And for privacy, they should be able to set a paste as public, unlisted, or private with a password.

**Candidate:** Excellent. So, expiration and visibility options, including password protection. For non-functional requirements, how many pastes are we expecting, and what are our latency and availability targets?

**Interviewer:** We're aiming for high availability, say four nines, and low latency, under two hundred milliseconds for both reads and writes. For scale, let's assume we need to support creating one million new pastes per day. What about the read-to-write ratio?

**Candidate:** A million pastes a day is a good number. For read-to-write, a typical Pastebin-like service often has a higher read volume. I'll assume a ten-to-one read-to-write ratio. For consistency, strong consistency for writes is crucial, meaning once a paste is created, it should be immediately available. For reads, eventual consistency is usually acceptable, where a new paste might take a moment to propagate across all systems, but it will eventually be consistent. Does that sound right?

**Interviewer:** Yes, that works.

## Back-of-the-envelope estimates

**Candidate:** Great. Let's do some quick back-of-the-envelope calculations to understand the scale.
For writes, one million pastes per day translates to roughly twelve pastes per second on average. If we consider peak traffic, which can be ten times the average, we're looking at around one hundred and twenty writes per second.
For reads, with our ten-to-one ratio, that's one thousand two hundred reads per second on average, and up to twelve thousand reads per second at peak.

Now, for storage. What's a reasonable average size for a paste? Let's assume ten kilobytes per paste, including some metadata.
One million pastes a day, multiplied by ten kilobytes per paste, means ten gigabytes of new data every day.
Over a year, that's ten gigabytes per day times three hundred and sixty-five days, which is about three point six five terabytes.
Over five years, we're looking at roughly eighteen terabytes of data. This is a significant amount but manageable with appropriate storage solutions.

Finally, bandwidth.
For writes, one hundred and twenty writes per second times ten kilobytes per write is one point two megabytes per second.
For reads, twelve thousand reads per second times ten kilobytes per read is one hundred and twenty megabytes per second.
So, total bandwidth is around one hundred and twenty-one megabytes per second, which is roughly one gigabit per second. This is well within typical data center capabilities.

## API design

**Candidate:** With those numbers in mind, let's define the core API endpoints. I'll use a RESTful approach.

For creating a paste, we'll have a `POST` request:
`POST /api/v1/paste`
The request body would contain:
- `content`: a string, the actual text of the paste.
- `expiration`: an optional enum, like 'never', '10m', '1h', '1d', '1w', '2w', '1m'.
- `visibility`: an optional enum, 'public', 'unlisted', or 'private'.
- `password`: an optional string, if `visibility` is 'private'.
The response would return a JSON object with the generated `paste_id` and the full `url` to access the paste.

For retrieving a paste, we'll use a `GET` request:
`GET /api/v1/paste/{paste_id}`
The `paste_id` would be a path parameter.
If the paste is private, the client would need to include a `password` as a query parameter or in the request body, depending on how we handle sensitive data.
The response would be a JSON object containing the `content`, `creation_date`, `expiration_date`, and `visibility`.
We'd also need appropriate error handling, like a 404 Not Found if the paste ID doesn't exist or has expired, and a 401 Unauthorized if a password-protected paste is accessed without the correct password.

## Data model and storage choice

**Candidate:** Now, let's think about how we'd store this data. Based on our requirements, we need a `Paste` entity.

The data model for a `Paste` would look something like this:
- `id`: This will be our unique paste identifier, a short string, say eight to ten characters, base62 encoded for URL friendliness. This will be the primary key.
- `content`: The actual text of the paste. Given our ten kilobyte average, this can be stored directly.
- `creation_timestamp`: A datetime field, automatically set when the paste is created.
- `expiration_timestamp`: A nullable datetime field, calculated based on the `expiration` option. Null means 'never expires'.
- `visibility`: An enum field, 'public', 'unlisted', or 'private'.
- `password_hash`: A nullable string field to store a securely hashed password if the paste is private. We'd also need a `salt` field for proper password hashing.
- `views_count`: An optional integer field, useful for analytics or trending pastes.

For storage choice, given the structured nature of our metadata and the need for strong consistency for writes, a relational database like PostgreSQL or MySQL would be a solid choice. It handles indexing, transactions, and relationships well. For the `content` itself, storing it directly in a TEXT or BLOB column within PostgreSQL is fine for our estimated ten-kilobyte average. If pastes were much larger, say megabytes, I'd consider storing the content in an object storage service like AWS S3 and just keeping a reference (the S3 key) in the database. But for now, a single PostgreSQL database simplifies the design.

**Interviewer:** Why not a NoSQL database, like Cassandra or MongoDB, especially with the high read volume?

**Candidate:** That's a good question. While NoSQL databases like Cassandra excel at high write throughput and horizontal scaling for certain access patterns, our primary access pattern is by a unique `paste_id`. A relational database with proper indexing can handle this very efficiently. The data is also fairly structured and fits well into a relational schema. For the read volume, we'll rely heavily on caching to offload the database, and read replicas can handle scaling reads from the database itself. If our data model became highly denormalized or we had extremely complex, high-volume analytical queries, then a NoSQL solution might be more compelling. But for this specific problem, PostgreSQL offers a good balance of features, consistency, and operational simplicity to start.

## High-level design

**Candidate:** Let's walk through the high-level architecture.

At the front, we'll have clients, typically web browsers or API consumers.
All requests will first hit a **Load Balancer**, such as Nginx or an AWS ELB. This distributes traffic across our application servers and provides health checks.
Behind the load balancer, we'll have a fleet of **Web Servers** or an API Gateway. These handle HTTP requests, authentication, and potentially rate limiting.
The core business logic will reside in a **Paste Service**. This service interacts with our data stores.
Our primary data store will be a **PostgreSQL Database** for both metadata and paste content.
To handle the high read volume and low latency requirement, we'll introduce a **Cache**, likely Redis or Memcached, sitting in front of the database.
Finally, we'll need a **Background Worker** or a cron job to handle tasks like expiring old pastes.

Let's trace a `POST` request to create a paste:
1.  A client sends a `POST /api/v1/paste` request to the Load Balancer.
2.  The Load Balancer forwards it to an available Web Server.
3.  The Web Server validates the request, performs any necessary authentication, and then calls the Paste Service.
4.  The Paste Service needs to generate a unique `paste_id`. I'll dive into the ID generation strategy later, but for now, assume it gets a unique ID.
5.  The Paste Service then stores the `paste_id`, `content`, `creation_timestamp`, `expiration_timestamp`, `visibility`, and `password_hash` into the PostgreSQL database.
6.  Upon successful storage, the Paste Service returns the generated `paste_id` and the full URL to the Web Server.
7.  The Web Server sends the success response back to the client.

Now, for a `GET` request to retrieve a paste:
1.  A client sends a `GET /api/v1/paste/{paste_id}` request to the Load Balancer.
2.  The Load Balancer forwards it to a Web Server.
3.  The Web Server calls the Paste Service, passing the `paste_id`.
4.  The Paste Service first checks the **Cache** (e.g., Redis) using the `paste_id` as the key. This is the **cache-aside pattern**: the application code is responsible for interacting with the cache directly before hitting the database.
5.  If the paste is found in the cache, and it's not expired or password-protected, the Paste Service returns the content immediately.
6.  If not found in the cache, or if it's password-protected, the Paste Service queries the PostgreSQL database for the `paste_id`.
7.  If the paste is found in the database and is password-protected, the Paste Service verifies the provided password.
8.  If valid, the Paste Service retrieves the content, stores it in the cache for future requests, and returns it.
9.  If the paste is not found in the database, or if the password is incorrect, it returns an appropriate error, like a 404 or 401.
10. The Paste Service returns the content or error to the Web Server.
11. The Web Server sends the response back to the client.

## Deep dives

**Candidate:** Let's dive into a couple of critical areas: unique ID generation and paste expiration.

First, **Unique ID Generation**. We need short, unique, and URL-friendly IDs.
One simple approach is to generate a random string, say eight to ten characters long, using base62 encoding (which includes alphanumeric characters). We'd then check if this ID already exists in the database. If it does, we regenerate and retry. The probability of collision is low with enough characters, but this approach adds a database lookup to the write path.
A more robust approach, especially at scale, is to use a **pre-generated ID pool**. A separate, dedicated ID generation service could continuously generate unique IDs and store them in a queue or a dedicated database table. When the Paste Service needs a new ID, it simply fetches one from this pre-generated pool. This avoids real-time collision checks and ensures IDs are always available quickly. This is an example of a **producer-consumer pattern**, where the ID service produces IDs and the Paste Service consumes them. This also allows us to make IDs sequential or random as needed without impacting the write latency of the Paste Service.

**Interviewer:** What happens if the ID generation service fails or the pool runs out?

**Candidate:** That's a great point. If the ID generation service fails, new IDs won't be produced. However, if we maintain a sufficiently large buffer in the ID pool, the Paste Service can continue to operate for some time. We'd need monitoring and alerting to detect low ID pool levels or failures in the ID generation service. If the pool truly runs out, new paste creation would fail. To mitigate this, we could have multiple ID generation services for redundancy, or fall back to the random string generation with collision check as a last resort, accepting the higher latency in that failure mode.

Second, **Paste Expiration and Deletion**. We have pastes with expiration times.
There are two main strategies:
1.  **Lazy Deletion**: When a paste is requested, check its `expiration_timestamp`. If it's expired, delete it from the database and cache, then return a 404. This is simple but means expired pastes might linger in the database, and the deletion logic adds latency to the read path.
2.  **Active Deletion**: A **Background Worker** or cron job periodically scans the database for expired pastes (`expiration_timestamp < NOW()`) and deletes them in batches. This keeps the database clean and ensures the read path is fast. This is essentially a **garbage collection** pattern.
I'd recommend active deletion with a background worker. It can run, say, every five to ten minutes, query for expired pastes, and delete them. It should delete in batches to avoid locking the table for too long and to manage resource consumption. After deleting from the database, it should also invalidate any corresponding entries in the cache.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's consider potential bottlenecks, how the system might fail, and the trade-offs we've made.

**Bottlenecks:**
1.  **Database:** A single PostgreSQL instance will eventually become a bottleneck for both storage capacity and I/O operations, especially with eighteen terabytes over five years and thousands of reads per second.
    *   **Solution:** We'd implement **read replicas** for PostgreSQL. All reads would go to the replicas, and writes to the primary. This is the **read-write splitting** pattern. For even higher scale, we'd need to **shard** the database, partitioning data across multiple database instances based on the `paste_id`. This distributes both storage and query load.
2.  **Cache:** The Redis cache could also become a bottleneck if not scaled. A single Redis instance has limits.
    *   **Solution:** We'd use a **Redis Cluster**, which shards data across multiple Redis nodes, providing horizontal scalability and high availability.
3.  **ID Generation Service:** As discussed, if using a centralized counter or a small pre-generated pool, it could be a single point of failure or a bottleneck.
    *   **Solution:** The pre-generated ID pool with a large buffer, and potentially redundant ID generation services, addresses this.
4.  **Network Bandwidth:** While our initial estimates are manageable, at much higher scales, network bandwidth could become an issue.
    *   **Solution:** Optimizing data transfer, using compression, and potentially a Content Delivery Network (CDN) for very popular, static pastes (though less common for dynamic text snippets) would help.

**Failure Modes:**
1.  **Database Failure:** If the primary PostgreSQL instance fails, our read replicas can continue serving reads. A failover mechanism would promote one of the replicas to become the new primary, ensuring high availability for writes after a brief interruption. This requires robust monitoring and automated failover.
2.  **Cache Failure:** If Redis goes down, requests would bypass the cache and hit the database directly. This would significantly increase database load, but the system would still function, albeit with higher latency. This is a characteristic of the **cache-aside pattern** – the system is resilient to cache failures.
3.  **Web Server Failure:** The Load Balancer would detect unresponsive web servers and route traffic to healthy ones, ensuring continuous service.
4.  **ID Generation Service Failure:** As discussed, the pre-generated pool provides a buffer. Without it, new paste creation would halt.

**Trade-offs:**
1.  **Consistency vs. Availability (CAP Theorem):** We chose strong consistency for writes to ensure data integrity, and eventual consistency for reads, which allows for higher availability and scalability through caching and replicas. This is a common trade-off in distributed systems.
2.  **Complexity vs. Performance/Scalability:** Adding components like a cache, ID generation service, read replicas, and sharding increases system complexity but is necessary to meet our performance and scalability requirements. We've tried to start simpler and scale up.
3.  **Cost vs. Durability/Performance:** Storing content in PostgreSQL is simpler but can be more expensive and less scalable for very large content than object storage. We made the initial choice for simplicity, with the understanding that we might migrate to object storage if paste sizes grow significantly.

**What changes at ten times the scale?**
At ten times the scale, our numbers would be one thousand two hundred writes per second and one hundred twenty thousand reads per second.
1.  **Database:** Sharding would become absolutely essential, not just an option. We'd likely need a more sophisticated sharding key and potentially more shards.
2.  **Cache:** The Redis Cluster would need to be significantly larger, potentially distributed across multiple data centers or regions to reduce latency for geographically dispersed users.
3.  **ID Generation:** The pre-generated ID pool would need to be much larger, and the ID generation service itself would need to be highly available and potentially sharded.
4.  **Background Workers:** We might need multiple background workers, possibly using a message queue like Kafka or SQS to distribute tasks for paste expiration, ensuring they can keep up with the increased volume of expired pastes.
5.  **Monitoring and Alerting:** These would become even more critical to detect and react to issues quickly across a much larger and more complex infrastructure.

## Wrap-up

**Candidate:** To summarize, our Pastebin design leverages a layered architecture with a Load Balancer, stateless Web Servers, and a core Paste Service. We've chosen PostgreSQL for reliable data storage, scaled with read replicas and eventual sharding. A Redis cache significantly boosts read performance using the cache-aside pattern. Unique IDs are managed through a robust pre-generation strategy, and paste expiration is handled efficiently by a background worker. This design prioritizes high availability and low latency for both reads and writes, while making conscious trade-offs between consistency, complexity, and scalability to meet the specified requirements.

You didn't just say "we'll use a cache," but specified "cache-aside pattern" and explained its implications for resilience. Three to five key terms and patterns to remember from this problem are:
1.  **Cache-aside pattern:** Essential for read-heavy workloads, balancing performance and data consistency.
2.  **Read-write splitting and Sharding:** Critical for scaling relational databases horizontally.
3.  **Producer-consumer pattern:** Useful for decoupling components and managing resource-intensive tasks like ID generation.
4.  **Active vs. Lazy Deletion:** Different strategies for handling data expiration, each with its own trade-offs.
5.  **CAP Theorem:** Explicitly discussing consistency versus availability trade-offs for different parts of the system.

A common mistake candidates make with this problem is underestimating the scale of storage and bandwidth, or not thinking deeply enough about how to generate truly unique and short IDs at high volume without creating a bottleneck. Also, many forget to address the expiration and cleanup of old data, which can lead to runaway storage costs and performance degradation over time. You covered all these points well.
