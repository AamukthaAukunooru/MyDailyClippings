**Interviewer:** Good morning. Today, I'd like you to design a URL shortener, similar to TinyURL. Think about how it would work at scale.

**Candidate:** Good morning. I'd be happy to. I'll start by clarifying the requirements, then move to estimates, API design, data model, high-level architecture, deep dives, and finally, discuss bottlenecks and trade-offs.

## Requirements

**Candidate:** First, let's nail down the functional requirements. What are the core features we need? I assume we need to:
1.  Take a long URL and return a short URL.
2.  When a user accesses a short URL, redirect them to the original long URL.
Are there any other must-haves, like custom aliases, expiration dates, or analytics?

**Interviewer:** Yes, those two are primary. Let's add custom aliases as a nice-to-have, and basic click analytics for each short URL. Expiration dates are not required for the initial version.

**Candidate:** Got it. Now, for non-functional requirements. What kind of scale are we talking about? How many new short URLs per day, and how many redirections? What are our latency and availability targets?

**Interviewer:** We anticipate around 10 million new short URLs created per day. For redirections, assume each short URL is accessed, on average, ten times a day. Latency for redirection should be very low, ideally under 50 milliseconds. Shortening can be a bit slower, say, under 500 milliseconds. Availability for redirection should be extremely high, at least four nines, or 99.99 percent. Consistency for the URL mapping should be strong, but for click counts, eventual consistency is acceptable.

**Candidate:** Excellent, those numbers give us a solid foundation. Strong consistency for mapping, eventual for analytics, high availability for redirects, and low latency for both, especially redirects.

## Back-of-the-envelope estimates

**Candidate:** Let's do some quick math to understand the scale.
For new short URLs: 10 million per day means 10,000,000 new URLs divided by 24 hours divided by 3,600 seconds. That's roughly 116 new short URLs per second on average. Let's round up to 120 requests per second for shortening, and assume peak could be ten times that, so 1,200 requests per second.

For redirections: If each short URL is accessed ten times a day, that's 100 million redirections per day. 100,000,000 divided by 24 hours divided by 3,600 seconds gives us about 1,160 redirections per second on average. Again, let's assume a peak of ten times that, so about 12,000 redirections per second. This is a read-heavy system, with reads being about 100 times more frequent than writes.

Now, storage. If we store 10 million new URLs per day, over five years, that's 10,000,000 * 365 * 5, which is about 18.25 billion records. Each record would need to store the short URL key, the long URL, creation date, and click count. Let's estimate the average long URL length at 100 characters. A short URL key is typically 7 characters. Add some overhead for metadata, say 200 bytes per record.
So, 18.25 billion records multiplied by 200 bytes per record is about 3.65 terabytes of data over five years. This is a manageable amount for a distributed database.

Bandwidth: For writes, 120 RPS times 200 bytes per record is about 24 kilobytes per second. For reads, 12,000 RPS times, say, 100 bytes for the long URL redirect, is 1.2 megabytes per second. These are average numbers, and peak will be higher, but overall, bandwidth doesn't seem to be a primary concern compared to throughput and storage.

## API design

**Candidate:** Based on our requirements, I envision two primary API endpoints.

First, for shortening a URL:
**`POST /shorten`**
*   This endpoint would accept a JSON body.
*   Input:
    *   `longUrl`: A string, the URL to be shortened. This is mandatory.
    *   `customAlias`: An optional string, if the user wants a specific short key.
*   Output:
    *   Returns a JSON object containing the generated `shortUrl` string.
    *   If a `customAlias` is provided and already taken, it would return an appropriate error message and HTTP status code, like 409 Conflict.

Second, for redirecting a short URL:
**`GET /{shortUrlKey}`**
*   This endpoint takes the `shortUrlKey` as a path parameter.
*   Output:
    *   It performs an HTTP 302 Found redirect to the original `longUrl`. This is the standard way to handle temporary redirects, which is appropriate here as the mapping might change or expire.

Optionally, for analytics:
**`GET /stats/{shortUrlKey}`**
*   Input: `shortUrlKey` as a path parameter.
*   Output: A JSON object with `clickCount`, `creationDate`, and potentially other metrics. This would likely require authentication.

## Data model and storage choice

**Candidate:** For our data model, we'll need a table or collection to store the mapping between short and long URLs.
The core fields would be:
*   `short_url_key` (Primary Key, String): The unique identifier for the short URL.
*   `long_url` (String): The original URL.
*   `created_at` (Timestamp): When the short URL was created.
*   `click_count` (Integer): The number of times the short URL has been accessed.

Given the scale, especially 18 billion records over five years and 12,000 reads per second, a traditional relational database like PostgreSQL or MySQL would face significant challenges with horizontal scaling and throughput without extensive sharding. While possible, it's not the most natural fit.

Instead, I would opt for a NoSQL key-value store. Specifically, I'd lean towards something like **Apache Cassandra** or **Amazon DynamoDB**. These databases are designed for high-volume reads and writes, offer excellent horizontal scalability, and provide low-latency access for simple key-value lookups, which is exactly what our redirection service needs. They handle sharding and replication natively.

For the `short_url_key`, we need to ensure uniqueness. The key-value store's primary key constraint will enforce this. For click counts, an eventually consistent counter is fine, which most NoSQL databases handle well.

**Interviewer:** Why not just use a simple relational database like PostgreSQL and shard it? What makes a NoSQL key-value store a better choice here?

**Candidate:** That's a great question. While sharding PostgreSQL is certainly an option, it introduces operational complexity. You'd need to manage the sharding logic, potentially a sharding layer, and schema migrations across many instances. For a system primarily doing simple key-value lookups and insertions at this scale, a NoSQL key-value store like Cassandra or DynamoDB offers several advantages:
1.  **Native horizontal scalability:** They are built from the ground up to distribute data across many nodes, handling replication and fault tolerance automatically.
2.  **High throughput and low latency:** Optimized for high read/write operations, which is crucial for our 12,000 RPS redirection requirement.
3.  **Simpler data model:** Our data is largely unstructured key-value pairs, which fits the NoSQL model perfectly.
4.  **Operational overhead:** Managed services like DynamoDB further reduce operational burden, allowing us to focus on the application logic.

So, while a sharded relational database could work, a NoSQL key-value store is a more natural and operationally simpler fit for the specific access patterns and scale of a URL shortener.

## High-level design

**Candidate:** Let's walk through the high-level architecture for both shortening and redirection.

At the front, we'll have a **Load Balancer** to distribute traffic across our services.

For shortening a URL:
1.  A client sends a `POST /shorten` request to the Load Balancer.
2.  The Load Balancer routes it to our **Shortening Service**. This service is responsible for generating the short URL key, validating custom aliases, and persisting the mapping.
3.  The Shortening Service interacts with a **Key Generation Service** to obtain a unique short URL key.
4.  It then stores the `(short_url_key, long_url, metadata)` in our chosen **Key-Value Store**, like Cassandra.
5.  Finally, it returns the generated `shortUrl` back to the client.

For redirecting a short URL:
1.  A client accesses a short URL, which translates to a `GET /{shortUrlKey}` request, hitting the Load Balancer.
2.  The Load Balancer routes it to our **Redirection Service**. This service is optimized for speed.
3.  The Redirection Service first checks a **Distributed Cache** (e.g., Redis or Memcached) using the `shortUrlKey` as the cache key. This is the **Cache-Aside pattern**: the service looks for data in the cache first, and if not found, fetches it from the database.
4.  If the `longUrl` is found in the cache, the service immediately issues an HTTP 302 redirect.
5.  If not in the cache, the Redirection Service queries the **Key-Value Store** for the `longUrl` associated with the `shortUrlKey`.
6.  Once retrieved, it stores this `(shortUrlKey, longUrl)` pair in the Distributed Cache for future requests.
7.  It then issues the HTTP 302 redirect to the client.
8.  Asynchronously, it sends a message to a **Message Queue** (like Kafka) to increment the `click_count` for that `shortUrlKey`. This ensures the redirection latency isn't affected by database writes for analytics. A dedicated **Analytics Service** consumes these messages and updates the `click_count` in the Key-Value Store.

## Deep dives

**Candidate:** Now, let's deep dive into two critical components: short URL key generation and optimizing redirection performance.

**Interviewer:** Good. Let's start with key generation. How would you ensure uniqueness and handle collisions at scale?

**Candidate:** The **Short URL Key Generation Service** is crucial. We need unique, short, and non-sequential keys.
There are a few approaches:
1.  **Hashing the Long URL:** We could take a hash like MD5 or SHA256 of the long URL and use a portion of it, say, the first 7 characters, potentially Base62 encoded. The problem here is hash collisions: different long URLs could produce the same short key. While unlikely for 7 characters, it's not impossible and difficult to resolve without a database check.
2.  **Random String Generation:** Generate a random string of 7 characters (e.g., Base62 encoded alphanumeric characters), then check if it exists in the database. If it does, retry. This involves a database lookup for every key, which can be a bottleneck at 1,200 writes per second.
3.  **Distributed Counter + Base62 Encoding:** Use a distributed counter (e.g., managed by ZooKeeper or a dedicated service) to generate unique, sequential IDs. Then, convert these numerical IDs to Base62. For example, ID 1000 becomes "g8". This guarantees uniqueness but makes the counter a single point of contention and bottleneck. Also, sequential keys are less desirable as they are predictable.

My preferred approach for high scale and non-predictability is **Pre-generated Keys**.
We would have a dedicated **Key Generation Service** that generates a large pool of unique, random 7-character Base62 keys offline. These keys are stored in a separate table in our Key-Value Store, marked as "available".
When the Shortening Service needs a key, it requests one from the Key Generation Service, which fetches an "available" key, marks it as "used" or deletes it, and returns it. If the pool of available keys falls below a threshold, the Key Generation Service asynchronously generates more. This is a **producer-consumer pattern**.
This approach avoids real-time database lookups for uniqueness during the shortening process, making it very fast. It ensures uniqueness by design and provides non-sequential, random keys.
A 7-character Base62 string (using 0-9, a-z, A-Z) provides 62^7 unique keys, which is approximately 3.5 trillion. This is more than enough for our 18 billion records over five years.

**Interviewer:** That's a solid strategy for key generation. Now, let's talk about redirection performance. You mentioned caching and asynchronous click counts. How exactly would you ensure the "under 50 milliseconds" latency target for redirects, especially at 12,000 requests per second? What happens if your cache goes down?

**Candidate:** To achieve under 50 milliseconds for redirection at 12,000 RPS, caching is absolutely critical. We're implementing the **Cache-Aside pattern**.
1.  **Massive Caching Layer:** We'd deploy a large, distributed cache cluster, like Redis or Memcached. Redis is often preferred for its data structures and persistence options. We'd allocate sufficient memory to cache the most frequently accessed URLs, which typically follow a power-law distribution.
2.  **Cache Hit Ratio:** Our goal is to achieve a very high cache hit ratio, ideally over 95%, so most requests don't even touch the database.
3.  **Time-to-Live (TTL):** Cache entries would have a TTL. Since URL mappings don't change, we could set a long TTL, or even an indefinite one, and only invalidate if a URL is explicitly deleted.
4.  **Asynchronous Analytics:** As discussed, click count updates are pushed to a message queue. This is a **fire-and-forget** mechanism from the perspective of the Redirection Service, ensuring that the database write latency for analytics doesn't impact the critical path of the redirect. The Analytics Service can process these messages in batches, further optimizing database writes.
5.  **Stateless Redirection Service:** The Redirection Service itself would be stateless, allowing for easy horizontal scaling by simply adding more instances behind the load balancer.

Regarding cache failure: If the Distributed Cache goes down, the Redirection Service would fall back to querying the Key-Value Store directly. This is a **fail-open strategy**. Latency would significantly increase, likely exceeding our 50-millisecond target, but the service would remain available. To mitigate this, the cache itself would be highly available, with replication and sharding. For example, a Redis cluster with master-replica setups and sentinel monitoring. If a cache node fails, traffic would failover to a replica, or the application would route to other healthy cache nodes. This ensures that a single cache node failure doesn't bring down the entire cache layer.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks, failure modes, and trade-offs.

**Bottlenecks:**
*   **Key Generation Service:** If not designed with pre-generation, a real-time key generation and uniqueness check could become a bottleneck. Our pre-generation strategy mitigates this.
*   **Key-Value Store:** Despite its scalability, if not properly sharded or provisioned, the database could become a bottleneck, especially during peak write times or if the cache hit ratio is low.
*   **Cache:** While improving performance, a misconfigured or undersized cache could lead to thrashing, or high eviction rates, reducing its effectiveness.

**Failure Modes:**
*   **Load Balancer Failure:** Redundant load balancers are essential.
*   **Service Failures:** Individual instances of the Shortening or Redirection Services can fail. Being stateless and deployed in auto-scaling groups ensures new instances can quickly replace failed ones. This is the **self-healing pattern**.
*   **Key-Value Store Failure:** Data loss or unavailability. This is mitigated by the database's built-in replication and fault tolerance (e.g., Cassandra's replication factor, DynamoDB's multi-AZ setup).
*   **Cache Failure:** As discussed, redirection falls back to the database, increasing latency but maintaining availability.
*   **Message Queue Failure:** Click counts might be delayed or lost if the queue or consumer fails. This is acceptable due to eventual consistency for analytics.

**Trade-offs:**
*   **Key Length vs. Address Space:** We chose 7 characters for short URLs. Shorter keys are more user-friendly but reduce the total number of unique keys and increase collision probability. 7 characters offers a good balance.
*   **Consistency vs. Latency:** We chose strong consistency for URL mapping (critical for correct redirection) and eventual consistency for click counts (acceptable for analytics). This allows us to achieve low latency for the core redirection path.
*   **Custom Aliases:** Allowing custom aliases adds complexity, as we need to check for uniqueness in real-time, which can add latency to the shortening process. We accept this small latency trade-off for the added user feature.

**What changes at ten times the scale:**
At ten times the scale, we'd be looking at 12,000 RPS for shortening and 120,000 RPS for redirection.
*   **More Instances:** We'd scale out all services horizontally: more instances of Shortening, Redirection, and Key Generation Services.
*   **Larger Database Cluster:** The Key-Value Store would need more nodes and potentially more aggressive sharding strategies.
*   **Larger Cache Cluster:** The cache would need significantly more memory and nodes to maintain a high hit ratio. We might consider multiple cache tiers.
*   **Geographical Distribution:** To reduce latency for global users, we might deploy the system across multiple geographical regions, using a global load balancer and potentially replicating the database and cache across regions. This introduces complexity around cross-region data consistency.
*   **Optimized Data Serialization:** We might look into more efficient data serialization formats for inter-service communication to reduce network overhead.

## Wrap-up

**Candidate:** To summarize, we've designed a highly scalable URL shortener. The core components include a Shortening Service and a Redirection Service, both stateless and horizontally scalable. We leverage a Key-Value Store like Cassandra or DynamoDB for durable storage, chosen for its high throughput and scalability with a simple data model. A critical aspect is the Key Generation Service, which uses a pre-generation strategy to ensure unique, random keys without real-time database lookups. For redirection, a massive distributed cache, like Redis, is deployed using the Cache-Aside pattern to achieve extremely low latency. Click analytics are handled asynchronously via a message queue to avoid impacting redirection performance. This architecture prioritizes high availability, low latency for redirects, and strong consistency for URL mappings, while gracefully handling eventual consistency for analytics.

Third, the candidate demonstrated a strong understanding of performance optimization for reads, specifically with the detailed explanation of the Cache-Aside pattern, asynchronous analytics updates via a message queue, and how to handle cache failures. Finally, the discussion of bottlenecks, failure modes, trade-offs, and scaling to ten times the load showed a holistic understanding of system resilience and evolution.

Here are three to five key terms and patterns to remember from this problem:
1.  **Base62 Encoding:** A standard way to represent numbers using 62 characters (0-9, a-z, A-Z) for short, URL-friendly keys.
2.  **Pre-generated Keys:** Generating unique identifiers in advance and storing them in a pool, to avoid real-time contention and database lookups during high-volume write operations. This is an application of the **producer-consumer pattern**.
3.  **Cache-Aside Pattern:** A caching strategy where the application directly manages cache reads and writes, checking the cache first and falling back to the database on a miss.
4.  **NoSQL Key-Value Store:** Ideal for high-throughput, low-latency key-value lookups, offering horizontal scalability for systems with simple data access patterns.
5.  **Asynchronous Processing with Message Queues:** Decoupling non-critical operations, like analytics updates, from the critical request path to maintain low latency.

One common mistake candidates make with this problem is focusing too much on hashing the long URL for key generation, without adequately addressing collision resolution or the performance implications of real-time uniqueness checks at scale. Another is underestimating the read load and not emphasizing caching enough, or failing to explain how to handle cache misses and failures gracefully.
