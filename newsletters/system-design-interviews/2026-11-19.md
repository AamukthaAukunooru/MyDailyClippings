**Interviewer:** Alright, let's design Reddit. Imagine you're building a new social news aggregation and discussion platform. Tell me how you'd approach this.

**Candidate:** Absolutely. I'll start by clarifying the requirements, then move to back-of-the-envelope estimates, API design, data model, high-level architecture, deep dives into key components, and finally discuss bottlenecks and trade-offs.

## 1. Requirements

**Candidate:** First, let's define the functional requirements. Users should be able to:
*   Create posts, which can be text, links, images, or videos.
*   Upvote and downvote posts and comments.
*   Comment on posts, and reply to comments, creating a nested discussion structure.
*   Create and subscribe to subreddits, which are communities focused on specific topics.
*   View different feeds: a personalized home feed (posts from subscribed subreddits), a subreddit-specific feed, and a global popular feed.
*   Search for posts and subreddits.
*   Manage their user profile.
*   Moderators can manage content within their subreddits.

**Interviewer:** That covers the core functionality. What about non-functional requirements? Think about scale, latency, availability, and consistency.

**Candidate:** For non-functional requirements:
*   **Scale:** Let's aim for a large user base, say 50 million daily active users. We should expect billions of posts and comments over time.
*   **Latency:** Feeds should load quickly, ideally under 200 milliseconds. Post and comment creation should be under 100 milliseconds.
*   **Availability:** High availability is crucial, aiming for 99.99% for core features like viewing feeds and creating content.
*   **Consistency:** For vote counts and feed updates, eventual consistency is acceptable to prioritize performance and availability. However, for critical user data or financial transactions, strong consistency would be required, though Reddit doesn't have financial transactions.

**Interviewer:** Good. 50 million daily active users, 200 milliseconds for feeds, 99.99% availability, and eventual consistency for feeds and votes sounds like a solid starting point.

## 2. Back-of-the-Envelope Estimates

**Candidate:** Now, let's do some back-of-the-envelope estimates to understand the scale.
With 50 million daily active users, let's assume a typical read-to-write ratio of around 10:1 to 20:1, meaning reads will dominate.

**Candidate:** For writes:
*   **Posts:** Let's estimate 1 million new posts per day.
*   **Comments:** Perhaps 10 million new comments per day.
*   **Votes:** A user might vote multiple times, so let's say 100 million votes per day.
Total writes per second (average): (1M posts + 10M comments + 100M votes) / (24 hours * 3600 seconds/hour) is roughly 111 million / 86,400, which is about 1,280 writes per second. Peak could be 3 to 4 times that, so around 4,000 to 5,000 writes per second.

**Candidate:** For reads:
*   **Feed views:** If each of our 50 million daily active users views their feed, say, 10 times a day, that's 500 million feed views per day.
Total reads per second (average): 500 million / 86,400 seconds is approximately 5,780 reads per second. Peak could easily be 2 to 3 times that, so 12,000 to 18,000 reads per second.

**Interviewer:** That's a significant read load. What about storage and bandwidth?

**Candidate:** For storage:
*   **Posts:** Let's assume an average post is 1 kilobyte for text/links, but images are 1 megabyte and videos 10 megabytes. If 10% of posts are media (images/videos, averaging 5 megabytes), and 90% are text (1 kilobyte), then 1 million posts per day would be roughly 1 million * (0.9 * 1KB + 0.1 * 5MB) which is about 500 gigabytes per day.
*   **Comments:** 10 million comments per day, averaging 500 bytes each, is about 5 gigabytes per day.
*   **Votes:** 100 million votes per day, each record containing `user_id`, `post_id`, `vote_type` (around 20 bytes), is about 2 gigabytes per day.
So, total daily storage is around 500 to 600 gigabytes. Over five years, that's roughly 1 petabyte of data. This doesn't include raw media files.

**Candidate:** For bandwidth, media content will dominate. If we serve 500 gigabytes of new media daily, and it's read, say, 5 times on average, that's 2.5 terabytes of outbound data per day, plus all the text content. A Content Delivery Network, or CDN, will be essential here.

## 3. API Design

**Candidate:** Next, let's outline the main API endpoints for core functionality. We'll use a RESTful approach.

**Candidate:**
*   `POST /api/v1/posts`: To create a new post. It would take parameters like `title`, `content_type` (text, link, image, video), `content` (text, URL), `subreddit_id`, and `user_id`. It would return a `post_id`.
*   `GET /api/v1/posts/{post_id}`: To retrieve a specific post, including its comments.
*   `POST /api/v1/posts/{post_id}/vote`: To vote on a post. Parameters would be `vote_type` (upvote/downvote) and `user_id`.
*   `POST /api/v1/comments`: To add a new comment. Parameters: `post_id`, `parent_comment_id` (optional, for nested comments), `content`, `user_id`. Returns `comment_id`.
*   `GET /api/v1/subreddits/{subreddit_id}/feed`: To get posts for a specific subreddit. Takes `sort_by` (new, hot, top) and pagination parameters like `limit` and `offset` or `before_id`/`after_id`.
*   `GET /api/v1/users/{user_id}/home_feed`: To get the personalized home feed for a user. Also takes `sort_by` and pagination parameters.
*   `GET /api/v1/search?query=...`: For searching posts and subreddits.

**Interviewer:** That set of APIs covers the main interactions. How would you ensure idempotency for write operations like voting or creating a post?

**Candidate:** That's a great point. For write operations that might be retried, like creating a post or casting a vote, I would use an **idempotency key**. The client would generate a unique key, typically a UUID, and send it with the request. The server would store this key and, if it sees the same key again within a certain timeframe, it would return the original response without re-processing the request. This prevents duplicate posts or votes if a client retries due to a network issue.

## 4. Data Model and Storage Choice

**Candidate:** For the data model, we'll need several entities. I'll describe them and then discuss storage choices.

**Candidate:**
*   **Users:** `user_id` (PK), `username`, `email`, `password_hash`, `created_at`, `profile_data`.
*   **Subreddits:** `subreddit_id` (PK), `name`, `description`, `created_by_user_id`, `created_at`, `subscriber_count`.
*   **Posts:** `post_id` (PK), `title`, `content_type`, `content_url` (for links/media), `content_text`, `user_id`, `subreddit_id`, `created_at`, `upvotes`, `downvotes`, `comment_count`.
*   **Comments:** `comment_id` (PK), `post_id`, `parent_comment_id` (nullable), `user_id`, `content`, `created_at`, `upvotes`, `downvotes`.
*   **Votes:** `user_id`, `post_id` (or `comment_id`), `vote_type`, `created_at`. This will be a composite key.
*   **User Subscriptions:** `user_id`, `subreddit_id`.

**Candidate:** For storage choices:
*   **Core Structured Data (Users, Subreddits, Posts, Comments):** Given the need for relationships and potentially strong consistency for certain aspects like user profiles or subreddit metadata, a **relational database** like PostgreSQL or MySQL would be a good fit. To handle the scale, we would shard these databases. We could shard posts and comments by `post_id` or `subreddit_id` to distribute the load. For users, sharding by `user_id` would be appropriate.
*   **Votes:** This is a very high write volume. While a relational database could work with heavy sharding, a **NoSQL key-value store** or a **column-family database** like Cassandra or DynamoDB would be more suitable due to its high write throughput and ability to scale horizontally. We'd store `(user_id, post_id)` or `(user_id, comment_id)` as the key, with the `vote_type`.
*   **Media (Images, Videos):** These binary large objects should be stored in **object storage**, like Amazon S3 or Google Cloud Storage. This is highly scalable, durable, and cost-effective. A **Content Delivery Network (CDN)** would then be used to serve these media files globally, reducing latency and offloading traffic from our origin servers.
*   **Feeds:** The actual personalized feeds can be generated and stored in a fast **key-value store or cache** like Redis or Memcached for active users, or a specialized NoSQL store for longer-term storage.
*   **Search:** For full-text search capabilities, an inverted index system like **Elasticsearch** or Apache Solr would be used.

## 5. High-Level Design

**Candidate:** Let's walk through the high-level architecture.

**Candidate:**
At the front, users interact with our **client applications** (web, mobile). These requests go through a **Load Balancer**, which distributes traffic to our **API Gateway**. The API Gateway handles authentication, rate limiting, and routes requests to the appropriate backend services.

**Candidate:** We'll adopt a **microservices architecture** for scalability and independent development. Key services would include:
*   **User Service:** Manages user registration, authentication, profiles.
*   **Subreddit Service:** Manages subreddit creation, subscriptions, and metadata.
*   **Post Service:** Handles post creation, retrieval, and updates.
*   **Comment Service:** Manages comments and their nested structure.
*   **Vote Service:** Records and aggregates votes.
*   **Feed Service:** Generates and serves different types of feeds (home, subreddit, popular).
*   **Media Service:** Manages media uploads to object storage and provides URLs.
*   **Search Service:** Interfaces with our search index.

**Candidate:** These services would interact with their respective data stores: sharded relational databases for core entities, a NoSQL store for votes, object storage for media, and Elasticsearch for search.
A **caching layer**, like Redis or Memcached, would sit in front of databases to reduce load and improve read latency for frequently accessed data, like popular posts or user sessions. This is the **cache-aside pattern**, where the application is responsible for reading from and writing to the cache.

**Candidate:** For asynchronous processing, especially for high-volume operations like vote aggregation or feed generation, we'd use a **message queue** like Apache Kafka. Services would publish events to Kafka, and other services would consume them. This decouples components and improves resilience.

**Interviewer:** Can you walk me through what happens when a user creates a new post with an image?

**Candidate:** Certainly.
1.  The client sends a `POST /api/v1/posts` request to the API Gateway.
2.  The API Gateway authenticates the user and routes the request to the Post Service.
3.  The Post Service first interacts with the Media Service to get a pre-signed URL to upload the image directly to object storage (S3). This offloads the heavy media upload from our application servers.
4.  Once the image is uploaded, the Post Service receives the image URL. It then writes the post metadata (title, content type, image URL, user ID, subreddit ID) to the sharded Post Database.
5.  The Post Service then publishes a "Post Created" event to our Kafka message queue.
6.  Multiple consumers would react to this event:
    *   The **Feed Service** would start processing to update relevant user feeds (more on this in the deep dive).
    *   The **Search Service** would index the new post for searchability.
    *   The **Subreddit Service** might update the `last_post_time` for the subreddit.
7.  Finally, the Post Service returns the `post_id` to the client.

## 6. Deep Dives

**Candidate:** I'd like to deep dive into two critical and complex parts: **Feed Generation** and **Vote Counting**.

**Candidate:** Let's start with **Feed Generation**, especially the personalized home feed. This is a classic fan-out problem. We have two main patterns: **fan-out on write (push model)** and **fan-out on read (pull model)**.
*   **Fan-out on write (push):** When a new post is created in a subreddit, we immediately push that post's ID into the feed of all users subscribed to that subreddit. This ensures low read latency for users but can be very write-heavy if a popular subreddit has millions of subscribers.
*   **Fan-out on read (pull):** When a user requests their home feed, we query all subreddits they subscribe to, fetch the latest posts, and then merge and rank them. This shifts the load to read time, which can be slow if a user subscribes to many subreddits.

**Candidate:** For Reddit, a **hybrid approach** is best.
1.  When a user creates a post, the Post Service publishes a "Post Created" event to Kafka.
2.  A **Feed Generator Service** consumes this event. For active users subscribed to the subreddit, it will fan out on write, pushing the `post_id` into a dedicated, highly optimized feed store, like a Redis sorted set or a Cassandra table partitioned by `user_id`. This ensures their feed is always fresh.
3.  For less active users, or for very popular subreddits with millions of subscribers where a full fan-out on write is too expensive, we can use a fan-out on read approach. When these users request their feed, the Feed Service queries the relevant subreddits directly, merges the results, and applies ranking.
4.  The Feed Service also handles ranking. Posts can be ranked by "new" (simple timestamp sort), "hot" (a decaying popularity algorithm considering votes and time), or "top" (highest votes over a period). This ranking logic can be implemented as a separate ranking service that continuously updates scores, storing them in a cache or specialized database.

**Interviewer:** That's a good hybrid strategy. What happens if the Feed Generator Service fails or falls behind? How do you ensure users still get their feed?

**Candidate:** That's where the hybrid nature provides resilience. If the push-based Feed Generator Service fails or lags, active users might see slightly delayed updates in their pre-generated feed. However, the pull-based fallback ensures that even if the pre-generated feed is stale or unavailable, the user can still get a functional, albeit potentially slower, feed by directly querying the underlying post data and merging it. We'd also have multiple instances of the Feed Generator Service running, behind a consumer group for Kafka, to provide high availability and parallel processing. We'd also monitor the consumer lag to detect issues early.

**Candidate:** My second deep dive is **Vote Counting**. This is challenging due to the high write volume and potential for race conditions when updating counts.
1.  When a user votes, the client sends a request to the Vote Service.
2.  The Vote Service first records the individual vote (`user_id`, `post_id`/`comment_id`, `vote_type`) in a high-throughput NoSQL database like Cassandra. This ensures the vote is persisted quickly. This is also where we'd check for duplicate votes from the same user on the same item, ensuring a user can only vote once in a direction.
3.  The Vote Service then publishes a "Vote Cast" event to a Kafka topic.
4.  An **Aggregator Service** consumes these "Vote Cast" events. This service batches votes for a given post or comment and periodically updates the `upvotes` and `downvotes` columns in the main Post/Comment relational database. This is an **eventual consistency** model: the vote count displayed might lag slightly behind the actual votes, but it will eventually be accurate.
5.  To display real-time feedback to the user, the client can optimistically update the UI, and the API can return the user's vote status from the Cassandra store, while the global count updates asynchronously. For very popular posts, we could also maintain a hot cache (e.g., Redis) for vote counts that the Aggregator Service updates more frequently.

**Interviewer:** Why not just update the relational database directly for each vote?

**Candidate:** Directly updating the relational database for every single vote would lead to very high contention on the `upvotes` and `downvotes` columns, especially for popular posts. This would cause lock contention, slow down write operations, and put immense pressure on the database, making it a significant bottleneck. By using a message queue and an asynchronous aggregator, we decouple the voting request from the count update, allowing the Vote Service to respond quickly and the database to handle updates in batches, greatly improving overall system throughput and responsiveness. This is a common pattern for high-volume counters.

## 7. Bottlenecks, Failure Modes and Trade-offs

**Candidate:** Let's discuss potential bottlenecks, failure modes, and trade-offs.

**Candidate:**
**Bottlenecks:**
*   **Database write throughput:** Especially for popular posts/comments receiving many votes, mitigated by asynchronous processing and sharding.
*   **Feed generation:** For users subscribed to many popular subreddits, mitigated by the hybrid push/pull model and aggressive caching.
*   **Media serving:** Handled by CDN.
*   **Ranking algorithms:** Can be computationally intensive, requiring dedicated services and optimized data structures.

**Candidate:**
**Failure Modes:**
*   **Database shard failure:** We'd use replication (e.g., primary-replica setup) with automatic failover to ensure high availability.
*   **Message queue failure:** Kafka is designed for fault tolerance with replication and consumer groups. We'd also implement dead-letter queues for messages that cannot be processed.
*   **Cache invalidation issues:** Using Time-To-Live (TTL) for cached items and the cache-aside pattern helps, but stale data is always a risk with caching.
*   **Service failures:** Each microservice should be deployed with redundancy, health checks, and auto-scaling. We'd implement **circuit breakers** to prevent cascading failures.

**Candidate:**
**Trade-offs:**
*   **Consistency vs. Performance/Availability:** We chose eventual consistency for vote counts and feed updates to prioritize performance and availability, accepting a small delay in data freshness. Strong consistency is reserved for critical data like user authentication.
*   **Fan-out on write vs. Fan-out on read:** The hybrid approach balances the cost of writes with the latency of reads.
*   **Microservices vs. Monolith:** Microservices offer scalability, independent deployment, and technology flexibility but introduce operational complexity, distributed transaction challenges, and increased network overhead. We accept this complexity for the benefits of scale.

**Interviewer:** How would this design change if the load increased by ten times?

**Candidate:** At ten times the scale, many of our existing strategies would need to be scaled up significantly.
*   We would need **more database shards** and potentially re-evaluate our sharding keys to ensure even distribution and prevent hot spots.
*   **More instances of all services** would be required, with more aggressive auto-scaling policies.
*   **Caching would become even more critical**, with potentially multiple layers of caching (e.g., local caches on service instances, distributed caches). We might pre-compute and cache even more feed segments.
*   The **Feed Service** would likely become more sophisticated, potentially incorporating machine learning for personalized ranking and content recommendations, requiring specialized infrastructure.
*   **Vote aggregation** might need to move to a more dedicated time-series database or stream processing framework for real-time analytics and more granular updates.
*   **Monitoring and alerting** would need to be extremely robust to quickly identify and address issues across a much larger distributed system. We might also explore using a **graph database** for complex social relationships, though Reddit's primary structure is less graph-like than other social networks.

## 8. Wrap-up

**Candidate:** To summarize, my design for Reddit involves a microservices architecture behind an API Gateway and Load Balancer. We use sharded relational databases for core structured data, a high-throughput NoSQL store for votes, and object storage with a CDN for media. Key challenges like feed generation are addressed with a hybrid fan-out model and caching, while vote counting uses asynchronous processing via Kafka to ensure scalability and eventual consistency. We prioritize availability and performance, making trade-offs on consistency where appropriate, and the system is designed with horizontal scalability and fault tolerance in mind for future growth.

Here are three to five key terms and patterns to remember from this problem:
1.  **Fan-out on write / Fan-out on read:** Crucial patterns for designing news feeds or social timelines, often combined into a hybrid approach.
2.  **Asynchronous processing with Message Queues:** Essential for handling high-volume, non-critical operations like vote counting or event distribution, decoupling services and improving responsiveness.
3.  **Eventual Consistency:** A common trade-off in distributed systems, especially for high-scale, read-heavy applications, where immediate consistency is sacrificed for performance and availability.
4.  **Sharding and Caching:** Fundamental techniques for scaling databases and reducing latency in read-heavy systems.
5.  **Content Delivery Network (CDN) and Object Storage:** Standard solutions for efficiently storing and serving large volumes of static media content globally.

One common mistake candidates make when designing Reddit is underestimating the complexity of feed generation and vote counting. They might propose a simple database query for feeds or direct database updates for votes, which would quickly become bottlenecks at scale. This candidate correctly identified these as deep dive areas and proposed scalable, resilient solutions.
