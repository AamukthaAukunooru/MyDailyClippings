**Interviewer:** Hi, thanks for coming in. Today, let's design a Load Balancer. I'm interested in how you'd approach this problem from first principles.

**Candidate:** Absolutely. I'd love to. I'll follow my standard system design template, starting with requirements.

## Requirements

**Candidate:** First, for **functional requirements**, a load balancer needs to distribute incoming network traffic across multiple backend servers. It should ensure high availability of the service by routing requests only to healthy servers. It also needs to support different load balancing algorithms, like Round Robin or Least Connections.

**Interviewer:** Good start. What about non-functional requirements? Let's talk about scale.

**Candidate:** For **non-functional requirements**, scale is critical. How many requests per second should this system handle? And how many backend servers are we talking about?

**Interviewer:** Let's aim for a high-traffic scenario. Say, ten million requests per second, and up to ten thousand backend servers.

**Candidate:** Ten million RPS is significant. That implies high throughput and low latency. We'll need minimal added latency from the load balancer itself, ideally in the low single-digit milliseconds. For availability, the load balancer itself must be highly available, meaning no single point of failure. Consistency isn't a primary concern for the core load balancing function, but if we consider features like sticky sessions, then consistent routing to the same backend server would be important. For now, let's assume sticky sessions are a potential future enhancement, not a core initial requirement.

## Back-of-the-envelope estimates

**Candidate:** With ten million requests per second, let's do some quick **back-of-the-envelope estimates**.
If an average request and response size is about one kilobyte, then the total bandwidth would be ten million requests per second times one kilobyte per request, which is ten gigabytes per second. This is a substantial amount of network traffic.
For ten thousand backend servers, if each can handle, say, one thousand requests per second, then ten thousand servers could collectively handle ten million requests per second, matching our target.
These numbers confirm that a single machine cannot act as the load balancer; we'll need a distributed system for the load balancer itself.

## API design

**Candidate:** When we talk about **API design** for a load balancer, it's a bit different from a typical application. The primary "API" is the virtual IP address, or VIP, that clients connect to. This VIP abstracts away the backend servers.
Internally, there would be a configuration API. This API allows operations teams or automated systems to add or remove backend servers, change load balancing algorithms, and configure health checks. For example, an endpoint like `/backends` might allow listing or updating server configurations, and `/algorithms` to select the routing strategy. This would likely be an internal REST API or managed via a configuration management system.

## Data model and storage choice

**Candidate:** For the **data model and storage choice**, we need to store configuration data: the list of backend servers, their current health status, the chosen load balancing algorithm, and parameters for health checks.
This data needs to be highly available and consistent across all load balancer instances. For this kind of metadata, a distributed key-value store like ZooKeeper or etcd would be an excellent choice. These systems provide strong consistency, high availability, and are designed for storing configuration data that changes infrequently but must be reliably distributed. They use consensus algorithms like Paxos or Raft to ensure data integrity.
Runtime state, like session stickiness information, if we were to implement it, could either be stored in a distributed cache like Redis, or perhaps managed via a stateless approach like IP hash, which I'll discuss later. For now, the core configuration goes into our consistent key-value store.

## High-level design

**Candidate:** Let's move to the **high-level design**.
Clients will resolve a domain name, say `api.example.com`, which points to our Virtual IP, or VIP. This VIP is not tied to a single physical machine.
To handle ten million RPS, we'll need a cluster of load balancer instances. The traffic *to* this load balancer cluster itself needs to be distributed. This can be achieved using techniques like DNS Round Robin, which distributes clients across multiple load balancer VIPs, or more robustly, using Anycast routing, where the same VIP is advertised from multiple geographic locations, and network routing directs clients to the nearest healthy load balancer instance. Another option is ECMP, Equal-Cost Multi-Path routing, where routers can distribute traffic across multiple paths to the same destination IP.
Each load balancer instance in our cluster will maintain a list of healthy backend servers. This list is populated by **health checks**, which periodically ping backend servers to ensure they are responsive.
When a request arrives at a load balancer instance, it applies a chosen **load balancing algorithm** to select a backend server. Common algorithms include Round Robin, which cycles through servers; Least Connections, which sends traffic to the server with the fewest active connections; or IP Hash, which uses the client's IP address to consistently route to the same server, useful for sticky sessions without explicit state.
Finally, the load balancer forwards the request to the selected backend. This forwarding can be done using **Network Address Translation, or NAT**, where the load balancer rewrites the destination IP address. Alternatively, for high-performance Layer 4 load balancing, **Direct Server Return, or DSR**, can be used. With DSR, the request goes through the load balancer, but the response bypasses it, going directly from the backend server to the client. This significantly reduces the load balancer's outbound traffic.

**Interviewer:** That's a solid overview. Let's dive deeper into some of those points. Tell me more about health checks. What happens when a node dies?

## Deep dives

**Candidate:** Absolutely. Let's do a **deep dive** into **health checks**.
There are two main types: active and passive.
**Active health checks** involve the load balancer proactively sending probes, like HTTP requests or TCP pings, to backend servers at regular intervals. If a server fails to respond within a timeout, or returns an error status code, it's marked as unhealthy and removed from the pool of available servers. This is a **fail-fast mechanism**.
**Passive health checks** involve the load balancer observing the responses from backend servers to actual client requests. If a backend consistently returns errors or takes too long to respond, it can be marked as unhealthy. This is more reactive but can catch issues that active checks might miss, as it tests the server under real load.
When a backend node dies, the health check mechanism detects its unresponsiveness. The load balancer then immediately stops sending new requests to that server. Existing connections might be gracefully terminated or allowed to complete, depending on the configuration. The server remains marked unhealthy until it passes a configured number of consecutive health checks, indicating it's recovered. This ensures high availability by automatically adapting to backend failures.

**Interviewer:** Why not just use DNS Round Robin for load balancing? It's simpler.

**Candidate:** That's a good question and a common pattern, but it has significant limitations for our scale and availability requirements.
**DNS Round Robin** simply returns a different IP address from a list for each DNS query. The client then connects directly to that IP. The problem is that DNS caches entries, so clients might not get the updated list quickly. More critically, DNS has no awareness of server health. If a backend server dies, DNS will continue to hand out its IP address, leading to failed requests for clients until the DNS record's Time-To-Live, or TTL, expires and clients query again. This directly violates our high availability requirement.
A dedicated load balancer, on the other hand, actively monitors server health and immediately stops routing traffic to unhealthy servers, providing much faster failure detection and recovery. It also allows for more sophisticated load balancing algorithms than simple round robin, like Least Connections, which optimizes for server utilization.

**Interviewer:** You mentioned Layer 4 and Layer 7 load balancing. Can you elaborate on the differences and when you'd choose one over the other for this design?

**Candidate:** Certainly. This is a crucial **deep dive**.
**Layer 4 load balancing**, or L4, operates at the transport layer of the OSI model. It primarily uses IP addresses and port numbers to make routing decisions. It inspects the TCP or UDP packets and forwards them based on the destination IP and port, usually using NAT. It's fast and efficient because it doesn't need to inspect the application-level content of the packets. It's essentially a packet forwarder.
**Layer 7 load balancing**, or L7, operates at the application layer. It inspects the actual content of the HTTP, HTTPS, or other application protocol requests. This allows for more intelligent routing decisions based on URL paths, HTTP headers, cookies, or even the content of the request body. L7 load balancers can also perform SSL termination, allowing backend servers to handle unencrypted traffic, and can modify requests or responses, like adding HTTP headers.
For our design, given the ten million RPS, we'd likely start with **Layer 4 load balancing** for its raw performance and lower latency. It's simpler to implement and scale horizontally. We could use DSR to maximize throughput.
However, if requirements evolve to include features like content-based routing, SSL termination at the load balancer, or advanced request manipulation, then **Layer 7 load balancing** would be necessary. This adds more processing overhead per request, requiring more powerful or more numerous load balancer instances. A common pattern is to have an L4 load balancer distribute traffic to a cluster of L7 load balancers, which then distribute to backend application servers. This is a **layered architecture** approach.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss **bottlenecks, failure modes, and trade-offs**.
**Bottlenecks** for a load balancer typically include network I/O, especially with ten gigabytes per second of traffic. If we perform SSL termination at L7, CPU utilization becomes a significant factor. Memory can also be a bottleneck if we're maintaining a large number of active connections or session state.
**Failure modes** include the load balancer itself becoming a single point of failure. We mitigate this with our cluster of load balancer instances and techniques like Anycast or ECMP. If all backend servers fail, the load balancer should gracefully return an error to clients, rather than holding connections open indefinitely. If the configuration store, like etcd, fails, load balancer instances should continue operating with their cached configurations, a **cache-aside pattern** for configuration, until the store recovers.
**Trade-offs** are inherent. Choosing L4 over L7 is a trade-off between raw performance and advanced features. Using DSR improves throughput but requires specific network configuration on backend servers. Implementing sticky sessions adds complexity and state management challenges, which can impact scalability if not designed carefully.
Finally, what changes at **ten times the scale**? At one hundred million RPS, our current design would need significant scaling. We'd need even more load balancer instances, potentially deploying them globally using a sophisticated Anycast network. We might need to optimize our networking stack further, perhaps moving to specialized hardware or kernel bypass techniques like DPDK for extreme throughput. Our health check system would need to be highly optimized to avoid overwhelming the backend servers with probes, perhaps using a hierarchical approach or more passive checks. Distributed configuration management with etcd would become even more critical to manage the larger number of load balancer instances and backend servers.

## Wrap-up

**Candidate:** To **wrap up**, our load balancer design addresses high scale and availability. It uses a cluster of load balancer instances fronted by a Virtual IP, with traffic distributed to them via Anycast or ECMP. Each instance uses active and passive health checks to maintain a list of healthy backend servers, applying algorithms like Least Connections or Round Robin. We chose a distributed key-value store for robust configuration management. The design allows for a flexible choice between high-performance Layer 4 and feature-rich Layer 7 load balancing, with the ability to scale to extreme loads by adding more instances and optimizing network paths.

**Interviewer:** Excellent. Thank you.

Three to five key terms and patterns to remember from this problem:
1.  **Virtual IP (VIP):** The single entry point for clients, abstracting backend complexity.
2.  **Anycast / ECMP:** Techniques for distributing traffic to a cluster of load balancers themselves, ensuring their own high availability.
3.  **Health Checks:** Essential for identifying and isolating unhealthy backend servers rapidly.
4.  **Layer 4 vs. Layer 7 Load Balancing:** The fundamental distinction between traffic forwarding based on network information versus application-level content.
5.  **Direct Server Return (DSR):** A high-performance L4 technique where responses bypass the load balancer.

One common mistake candidates make when designing a load balancer is not considering the load balancer itself as a distributed system. They often focus solely on distributing traffic to backend servers, but neglect how to make the load balancer layer itself highly available and scalable. This candidate addressed that explicitly with Anycast and ECMP.
