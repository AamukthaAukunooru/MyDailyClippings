**Interviewer:** Alright, let's design Spotify. Imagine we're building the core components of a global music and podcast streaming service. How would you approach this?

**Candidate:** Great problem. As always, I'll start by clarifying the **requirements**, then move to **back-of-the-envelope estimates**, **API design**, **data model and storage**, a **high-level design**, **deep dives** into specific components, discuss **bottlenecks and trade-offs**, and finally, summarize the design.

## Requirements

**Candidate:** To begin, let's nail down the functional requirements. I'm thinking core features like:
1.  Users can stream music and podcasts.
2.  Users can search for tracks, artists, and albums.
3.  Users can create, edit, and share playlists.
4.  Users can follow artists and friends.
5.  Users can get personalized recommendations.
6.  Users can download content for offline playback.
Are there any other key functional areas we should prioritize, or any specific features we should de-prioritize for this exercise?

**Interviewer:** That list sounds good for a start. Let's assume we're focusing on the core streaming, search, playlist, and recommendation features. Offline playback is a good stretch goal, but not the primary focus today. Now, for non-functional requirements: what kind of scale, latency, availability, and consistency are we aiming for?

**Candidate:** For scale, I'd assume we're targeting hundreds of millions of monthly active users, perhaps a hundred million daily active users, and peak concurrent users in the tens of millions. Does that sound right?

**Interviewer:** Yes, let's use those numbers. For peak concurrent users, let's say ten million.

**Candidate:** Excellent. For latency, streaming playback should start almost instantly, ideally under one hundred milliseconds. Search results should appear quickly, say, under two hundred milliseconds. Playlist operations like adding a song can be a bit more relaxed, maybe under five hundred milliseconds.
For availability, the core streaming service must be highly available, targeting four nines, or 99.99 percent, meaning less than an hour of downtime per year. Other services, like playlist management or user profiles, can tolerate slightly less, perhaps three nines.
Regarding consistency, for critical user data like billing information or playlist ownership, we'll need strong consistency. For things like follower counts or recommendation updates, eventual consistency is perfectly acceptable, prioritizing availability and performance. Does that align with your expectations?

**Interviewer:** Those are solid targets. Let's proceed with those assumptions.

## Back-of-the-envelope estimates

**Candidate:** Alright, let's do some quick back-of-the-envelope calculations.
With one hundred million daily active users and ten million concurrent users:
*   **Requests per second (QPS):** If each of the ten million concurrent users makes, say, one hundred requests per hour on average (searching, playing, skipping, playlist actions), that's ten million users times one hundred requests per hour, divided by three thousand six hundred seconds per hour. That's roughly two hundred and seventy-seven thousand requests per second for application-level interactions. Playback requests will be more sustained. Let's assume an average song length of three minutes. If ten million users are actively streaming, that's ten million concurrent streams. Each stream will initiate a request, and then data chunks will be requested. So the initial playback QPS would be a fraction of the total concurrent users, maybe one million QPS for initiating streams, plus chunk requests.
*   **Storage:** Let's assume we have one hundred million unique songs and podcasts. If an average song, encoded at a decent bitrate, is about five megabytes, that's one hundred million songs times five megabytes per song, which is five hundred thousand terabytes, or five hundred petabytes, just for the audio files. We'll also need storage for metadata, user data, playlists, and recommendations, but the audio files are by far the largest component.
*   **Bandwidth:** If ten million concurrent users are streaming, and assuming an average bitrate of two hundred and fifty-six kilobits per second, that's ten million users times two hundred and fifty-six kilobits per second. This translates to about two thousand five hundred and sixty gigabits per second, or roughly three hundred and twenty gigabytes per second of egress bandwidth. This is a massive number and immediately tells me that a Content Delivery Network, or CDN, will be absolutely critical.

## API design

**Candidate:** Moving on to API design. We'll need a set of RESTful APIs, likely exposed through an API Gateway. Here are some core endpoints:

1.  **Stream Content:**
    *   `GET /tracks/{track_id}/stream`: Returns the audio stream for a given track ID. This would likely return a redirect to a CDN URL or a pre-signed URL to object storage, rather than streaming directly from our backend.
2.  **Search:**
    *   `GET /search?q={query}&type={track|artist|album|playlist}`: Searches across different content types. Returns a list of matching items with metadata.
3.  **Playlists:**
    *   `POST /users/{user_id}/playlists`: Creates a new playlist. Takes a playlist name and optional description. Returns the new playlist ID.
    *   `GET /playlists/{playlist_id}`: Retrieves details of a specific playlist, including its tracks.
    *   `PUT /playlists/{playlist_id}/tracks`: Adds or removes tracks from a playlist. Takes track IDs and an action (add/remove).
    *   `DELETE /playlists/{playlist_id}`: Deletes a playlist.
4.  **User Interactions:**
    *   `PUT /users/{user_id}/follow/{target_id}?type={artist|user}`: Allows a user to follow an artist or another user.
    *   `GET /users/{user_id}/feed`: Retrieves personalized activity feed or recommendations.
5.  **Metadata:**
    *   `GET /tracks/{track_id}`: Retrieves detailed metadata for a track.
    *   `GET /artists/{artist_id}`: Retrieves artist details and discography.

These APIs would be authenticated, likely using OAuth 2.0 tokens.

## Data model and storage choice

**Candidate:** For the data model, we'll have several core entities:

1.  **Users:** `user_id`, `username`, `email`, `password_hash`, `profile_info`, `subscription_status`.
2.  **Tracks:** `track_id`, `title`, `artist_id`, `album_id`, `duration`, `release_date`, `genre`, `audio_file_url`, `metadata_json`.
3.  **Artists:** `artist_id`, `name`, `bio`, `image_url`.
4.  **Albums:** `album_id`, `title`, `artist_id`, `release_date`, `cover_image_url`.
5.  **Playlists:** `playlist_id`, `user_id` (owner), `name`, `description`, `created_at`, `updated_at`.
6.  **Playlist_Tracks (join table):** `playlist_id`, `track_id`, `position_in_playlist`.
7.  **Follows:** `follower_id`, `followed_id`, `followed_type`.
8.  **User Activity:** `user_id`, `track_id`, `timestamp`, `event_type` (play, skip, like).

For storage choices:
*   **Audio Files:** Given the five hundred petabytes estimate, a highly scalable and cost-effective **Object Storage service** like Amazon S3, Google Cloud Storage, or Azure Blob Storage is ideal. It provides high durability and availability, and integrates well with CDNs.
*   **Metadata (Users, Tracks, Artists, Albums, Playlists):** For these structured, relational data types, a **relational database** like PostgreSQL or MySQL would be a good fit. It offers strong consistency, complex query capabilities, and ACID properties, which are important for managing user accounts and playlist integrity. We would need to shard these databases as we scale.
*   **User Activity & Recommendations:** This data is high-volume, append-only, and often queried in a distributed fashion. A **NoSQL wide-column store** like Apache Cassandra or Amazon DynamoDB would be suitable here. It provides high write throughput, horizontal scalability, and eventual consistency, which is acceptable for activity logs and recommendation inputs.
*   **Search Index:** For fast full-text search, a specialized search engine like **Elasticsearch** is the standard choice. It builds an inverted index over track titles, artist names, and album names, allowing for very fast, relevant searches.

## High-level design

**Candidate:** Let's walk through a high-level design, focusing on the "play a song" request.

1.  **Client:** The user interacts with the Spotify application on their device.
2.  **API Gateway:** All client requests first hit an API Gateway. This handles authentication, rate limiting, and routes requests to the appropriate microservice. This is an example of the **Gateway pattern**.
3.  **Load Balancer:** Behind the API Gateway, requests are distributed to various microservices by a load balancer.
4.  **Microservices:** We'd have several specialized services:
    *   **User Service:** Manages user profiles, authentication, and subscriptions.
    *   **Catalog Service:** Stores and serves metadata for tracks, artists, and albums from the relational database.
    *   **Playlist Service:** Manages user playlists, interacting with the relational database.
    *   **Search Service:** Queries the Elasticsearch cluster.
    *   **Streaming Service:** Orchestrates the delivery of audio content. This service would interact with the Catalog Service to get track metadata, and then generate a pre-signed URL for the audio file from the Object Storage.
    *   **Recommendation Service:** Processes user activity data to generate recommendations.
    *   **Analytics/Activity Service:** Ingests user playback and interaction events into a NoSQL store.
5.  **Content Delivery Network (CDN):** This is crucial. Our audio files stored in Object Storage would be distributed to CDN edge locations globally. When a user requests to stream a track, the Streaming Service provides a CDN URL. The client then fetches the audio directly from the nearest CDN edge server. This uses the **CDN pattern** to reduce latency and bandwidth costs.
6.  **Databases:** As discussed, a mix of relational databases (PostgreSQL), NoSQL databases (Cassandra/DynamoDB), Elasticsearch, and Object Storage (S3).

Let's trace playing a song:
1.  User taps "Play" on a track in the client.
2.  Client sends a `GET /tracks/{track_id}/stream` request to the API Gateway.
3.  API Gateway authenticates the request and forwards it to the Streaming Service.
4.  The Streaming Service queries the Catalog Service (which in turn queries the relational database) to verify the track ID and retrieve its `audio_file_url` from the metadata.
5.  The Streaming Service then generates a temporary, pre-signed URL for the `audio_file_url` from the Object Storage. This pre-signed URL might point directly to S3 or, more likely, to a CDN endpoint configured to pull from S3. This is an example of the **Delegated Access pattern**.
6.  The Streaming Service returns this pre-signed CDN URL to the client.
7.  The client then directly requests the audio chunks from the CDN. The CDN serves the content from its nearest edge cache. If not cached, the CDN fetches it from the origin (Object Storage) and caches it.
8.  Simultaneously, the client sends playback events (start, progress, end) to the Analytics/Activity Service, which records them in the NoSQL database for recommendations and analytics.

## Deep dives

**Interviewer:** That's a clear high-level overview. Let's dive deeper into a couple of areas. First, tell me more about the streaming architecture. How would you handle variable network conditions and ensure a smooth playback experience?

**Candidate:** Excellent question. This is where **Adaptive Bitrate Streaming**, or ABS, comes into play. The audio files wouldn't be stored as single large files. Instead, each track would be encoded into multiple versions at different bitrates and resolutions, and then segmented into small, fixed-duration chunks, typically two to ten seconds long. This is the **Chunking pattern**.
When the client requests a stream, it receives a manifest file, like an M3U8 for HLS or an MPD for DASH. This manifest lists all available bitrates and the URLs for their respective chunks. The client then dynamically chooses which bitrate chunk to request next based on its current network conditions, buffer levels, and device capabilities. If the network degrades, it requests a lower bitrate chunk; if it improves, it switches to a higher quality one. This ensures continuous playback with minimal buffering, even with fluctuating network quality.
The CDN plays a critical role here, caching these individual chunks at edge locations.

**Interviewer:** What happens if a CDN node serving a particular chunk dies or becomes unresponsive? How do you ensure high availability for streaming?

**Candidate:** That's a critical failure mode. We'd implement several layers of resilience.
First, the client's streaming player would be designed with **retry logic and fallback mechanisms**. If a request for a chunk to one CDN edge node fails or times out, the client would automatically retry the request, potentially to a different CDN edge node within the same CDN provider, or even switch to a different CDN provider if we use a multi-CDN strategy. This is an example of the **Circuit Breaker pattern** at the client level, preventing continuous requests to a failing endpoint.
Second, using **multiple CDN providers** is a common strategy for very high availability and resilience against a single CDN provider outage. We could have a primary CDN and a fallback CDN, or even distribute traffic across multiple CDNs simultaneously using a CDN load balancer.
Third, the pre-signed URLs provided by our Streaming Service could include information about alternative endpoints or be short-lived, allowing us to quickly revoke or update them if an origin or CDN issue is detected.

**Interviewer:** Good. Let's shift to search. You mentioned Elasticsearch. How would you ensure search results are fresh and relevant, especially for new content?

**Candidate:** For search, Elasticsearch is a powerful choice because it's built on Apache Lucene, providing fast full-text search capabilities.
To ensure freshness, when new tracks or podcasts are uploaded and processed by our ingestion pipeline, their metadata would be immediately pushed to the Catalog Service. The Catalog Service would then asynchronously update the Elasticsearch cluster. This could be done via a message queue like Kafka. When a new track is added to the relational database, a message is published to Kafka. A consumer service then picks up this message and indexes the new track's metadata in Elasticsearch. This is the **Change Data Capture pattern** combined with a **Message Queue pattern**.
For relevance, Elasticsearch allows for complex queries, including fuzzy matching, boosting certain fields (like exact title matches), and incorporating user-specific signals. The Search Service would handle constructing these queries. Over time, we could integrate machine learning models to personalize search results based on user listening history, similar to how recommendations work. This would be an iterative improvement.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss bottlenecks, failure modes, and trade-offs.
**Bottlenecks:**
1.  **CDN Egress Costs:** With hundreds of petabytes of storage and hundreds of gigabytes per second of egress, CDN costs will be enormous. Optimizing content encoding, using efficient codecs, and negotiating favorable CDN contracts are crucial.
2.  **Database Hotspots:** For relational databases, popular artists or playlists could lead to hotspots on specific database shards. We'd need careful sharding strategies, potentially using consistent hashing on `artist_id` or `user_id`, and caching frequently accessed metadata using a distributed cache like Redis. This is the **Cache-Aside pattern**.
3.  **Recommendation Engine Compute:** Building and serving personalized recommendations for millions of users requires significant computational resources, especially for machine learning models. This would likely involve batch processing for model training and potentially real-time inference for immediate updates.

**Failure Modes:**
1.  **CDN Outage:** As discussed, multi-CDN strategy and client-side retry logic are essential.
2.  **Database Failure:** For relational databases, high availability is achieved through replication (primary-replica setup) and automated failover. For NoSQL stores like Cassandra, built-in replication across multiple nodes and data centers provides resilience.
3.  **Service Dependencies:** A failure in one microservice, like the Catalog Service, could impact others. We'd use **bulkheads** to isolate failures, **circuit breakers** to prevent cascading failures, and robust monitoring and alerting.

**Trade-offs:**
1.  **Consistency vs. Availability (CAP Theorem):** We explicitly chose strong consistency for critical user data and eventual consistency for less critical data like recommendations or follower counts. This is a fundamental trade-off.
2.  **Performance vs. Cost:** Using powerful servers, extensive caching, and multiple CDNs improves performance but increases cost. We'd need to continuously optimize resource allocation.
3.  **Data Freshness vs. Query Latency:** For search and recommendations, there's a trade-off between how quickly new content or activity is reflected and the latency of serving queries. Asynchronous updates via message queues help balance this.

**What changes at ten times the scale:**
At ten times the scale, we'd be looking at billions of users and petabytes of data per day.
*   **More aggressive sharding:** All databases would need more granular sharding, potentially multi-level sharding.
*   **Global distribution:** We'd likely move to a truly global multi-region architecture, replicating data across continents to reduce latency for users worldwide.
*   **Advanced caching:** More layers of caching, including edge caching at the CDN level for metadata, and client-side caching for frequently accessed data.
*   **Asynchronous processing everywhere:** Almost all non-critical operations would become asynchronous, heavily relying on message queues and stream processing frameworks like Apache Flink or Spark Streaming for real-time analytics and recommendations.
*   **Specialized hardware:** For recommendation engines, we might invest in GPUs or custom AI accelerators.
*   **Automated operations:** Infrastructure as Code, advanced auto-scaling, and self-healing systems would be paramount to manage complexity.

## Wrap-up

**Candidate:** To summarize, we designed a scalable Spotify-like service. We established clear functional and non-functional requirements, estimating significant storage and bandwidth needs. The design leverages a microservices architecture, with a CDN for efficient audio streaming, Object Storage for media files, relational databases for core metadata, NoSQL for activity logs, and Elasticsearch for search. We discussed adaptive bitrate streaming for smooth playback and a message queue-driven approach for fresh search results. Finally, we addressed critical bottlenecks like CDN costs, database hotspots, and the trade-offs between consistency and availability, outlining how the system would evolve to handle ten times the load.

**Interviewer:** Excellent. That's a comprehensive design.

**Key terms and patterns to remember from this problem:**
1.  **Content Delivery Network (CDN):** Essential for distributing large media files globally, reducing latency, and offloading origin servers.
2.  **Adaptive Bitrate Streaming (ABS):** A technique using multiple encodings and chunking to provide smooth playback over variable network conditions.
3.  **Microservices Architecture:** Decomposing a large application into smaller, independently deployable services for scalability and maintainability.
4.  **Object Storage (e.g., S3):** Highly scalable, durable, and cost-effective storage for unstructured data like audio files.
5.  **Elasticsearch (Inverted Index):** A specialized search engine for fast, full-text search and analytics over large datasets.
6.  **Message Queue (e.g., Kafka):** For asynchronous communication, decoupling services, and handling high-throughput event streams (e.g., user activity, search index updates).
7.  **Consistent Hashing:** A technique for distributing data or requests across a dynamic set of servers to minimize remapping when nodes are added or removed.

**One common mistake candidates make:**
A common mistake is to focus too heavily on a single database technology or a monolithic architecture, failing to recognize the diverse data storage and processing needs of a system like Spotify. The candidate here correctly identified the need for a polyglot persistence approach, using different databases for different workloads, which is a hallmark of scalable system design.
