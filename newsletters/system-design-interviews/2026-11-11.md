**Interviewer:** Hi there. Today, let's design a distributed cache. Imagine we're building this for a large-scale application, like a popular e-commerce platform. How would you approach designing such a system?

**Candidate:** Absolutely. Designing a distributed cache is a classic problem with many interesting trade-offs. I like to start by clarifying the **1. Requirements**, both functional and non-functional, to ensure we're solving the right problem.

## Requirements

**Candidate:** Functionally, I envision a simple key-value store. Users should be able to `set` a value for a given key, `get` a value by its key, and `delete` a key. We'll also need to consider eviction policies, like Time-To-Live, Least Recently Used, or Least Frequently Used, to manage memory. Are there any other specific functional requirements, like atomic operations or support for complex data structures?

**Interviewer:** For now, basic key-value operations are sufficient. We can assume values are opaque byte arrays. Regarding non-functional requirements, let's target about one terabyte of cached data in total. Peak load can hit around one hundred thousand reads per second and ten thousand writes per second. Latency for reads should be under five milliseconds, ideally under one millisecond. Availability should be very high, say four nines, meaning 99.99%. Losing some cached data temporarily is acceptable, as the source of truth exists elsewhere. Consistency-wise, eventual consistency is fine; stale data for a few seconds is acceptable, but not minutes.

**Candidate:** Great, those numbers give us a solid foundation. One terabyte of data, one hundred thousand reads per second, ten thousand writes per second, sub-five-millisecond latency, and high availability with eventual consistency. This clearly points towards an in-memory, distributed solution.

## Back-of-the-envelope estimates

**Candidate:** Next, let's do some **2. Back-of-the-envelope estimates** to understand the scale.
With one terabyte of data and assuming an average item size of, say, one kilobyte, we're looking at approximately one billion individual key-value pairs. This immediately tells us we can't fit it on a single machine, so distribution is essential.

For network bandwidth, at one hundred thousand reads per second, each returning one kilobyte, that's one hundred megabytes per second of outbound traffic from our cache cluster. For writes, ten thousand writes per second, each one kilobyte, is ten megabytes per second of inbound traffic. These numbers are well within the capabilities of modern network interfaces, but distributed across many nodes, it becomes manageable. The key takeaway here is the need for many nodes to collectively hold one terabyte of data and serve the high request volume.

## API design

**Candidate:** Moving on to **3. API design**, based on our functional requirements, the core API would be quite simple:

First, a `get` operation: `get(key string) (value []byte, error)`. This takes a string key and returns the associated byte array value, or an error if not found or on failure.

Second, a `set` operation: `set(key string, value []byte, ttlSeconds int) error`. This stores a byte array value for a given string key, with an optional time-to-live in seconds. This `ttlSeconds` parameter is crucial for managing cache freshness and eviction.

Third, a `delete` operation: `delete(key string) error`. This removes a key-value pair from the cache.

These three operations form the core of our cache interaction.

## Data model and storage choice

**Candidate:** For the **4. Data model and storage choice**, given our requirements for low latency, high throughput, and a simple key-value interface, an in-memory key-value store is the obvious choice. We need something designed for speed, not for durability as the primary source of truth.

I would lean towards using a technology like Redis or Memcached. Redis offers more advanced features like various data structures, atomic operations, and optional persistence, which could be useful for more complex caching scenarios or faster recovery. Memcached is simpler and often faster for pure key-value storage. Given the potential for future needs like atomic increments for session counters, I'd suggest Redis. It’s highly optimized for in-memory operations and scales horizontally.

Why not a traditional database? A relational database or even a disk-backed NoSQL store would introduce too much latency due to disk I/O, and wouldn't be able to handle the one hundred thousand reads per second requirement without significant over-provisioning and cost. The cache's role is to offload the primary database, so it must be significantly faster.

## High-level design

**Candidate:** Now, let's outline the **5. High-level design**. Our system will consist of multiple cache nodes, each running an instance of Redis. Clients, which are our application servers, will interact with this distributed cache.

The core challenge in a distributed cache is how to distribute the one billion key-value pairs across many nodes and how clients find the correct node for a given key. We'll use a technique called **Consistent Hashing** for this.

Here’s how it works:
When an application wants to `get` or `set` a key, it will use a client library. This client library will take the key, apply a hash function to it, and then use **Consistent Hashing** to determine which specific cache node is responsible for that key. The client then sends the request directly to that node. This avoids a central bottleneck and allows for horizontal scaling.

For data management, we'll primarily use the **Cache-Aside pattern**. This means the application code is responsible for checking the cache first. If the data is found in the cache (a cache hit), it's returned immediately. If it's not found (a cache miss), the application fetches the data from the primary database, stores it in the cache for future requests, and then returns it to the user. This pattern keeps the cache simple and the source of truth with the database.

To ensure high availability and fault tolerance, each cache node will have one or more replicas. If a primary node fails, one of its replicas can be promoted to take over, minimizing downtime.

**Interviewer:** You mentioned Consistent Hashing. Can you elaborate on how that helps with scaling, especially when nodes are added or removed? And what happens when a cache node dies?

## Deep dives

**Candidate:** Excellent questions, those lead us into the **6. Deep dives**.

Let's start with **Consistent Hashing**. The traditional way to distribute keys is `hash(key) % N`, where N is the number of nodes. The problem with this approach is that if you add or remove a node, N changes, and almost all keys would remap to different nodes, leading to a massive cache miss storm and overwhelming the backend database.

**Consistent Hashing** solves this. Imagine a hash ring, where the hash space, say from zero to two to the power of thirty-two minus one, is mapped onto a circle. Each cache node is also mapped onto this ring by hashing its identifier. Each key is hashed and placed on the ring. To find a key's node, you traverse the ring clockwise from the key's position until you hit the first node. That node is responsible for the key.

The magic happens when a node is added or removed. If a node is added, it only takes over a small, contiguous range of keys from its clockwise neighbor. If a node is removed, its keys are simply taken over by the next node clockwise. This minimizes the number of remapped keys, typically affecting only `1/N` of the keys, where N is the number of nodes.

To further improve distribution and reduce the impact of a single node failure, we use **virtual nodes**. Instead of mapping each physical cache server to one point on the ring, we map it to many points, say one hundred or two hundred virtual nodes. This makes the distribution of keys much more even across physical nodes and ensures that when a physical node fails, its keys are spread out across many other nodes, not just one.

Regarding node failures, if a cache node dies, the **Consistent Hashing** mechanism will automatically remap the keys it was responsible for to the next available nodes on the ring. However, this means those keys will now result in cache misses until they are re-populated from the database. To prevent this data loss and ensure high availability, we'd implement **Replication**. Each logical shard of data, managed by Consistent Hashing, would exist on a primary node and one or more replica nodes.

When a primary node fails, a monitoring system, perhaps using something like Sentinel for Redis or a custom health check service, detects the failure. One of the replicas is then automatically promoted to become the new primary. The client library would be updated to reflect this change, either through a service discovery mechanism or by polling the monitoring system. This ensures that even if a node fails, the data remains available, just with a brief period of potential cache misses during the failover.

Finally, for **Eviction Policies**, given our eventual consistency requirement and TTL on `set` operations, a combination of **Time-To-Live (TTL)** and **Least Recently Used (LRU)** is very effective. TTL ensures data doesn't get excessively stale. LRU, which Redis supports, automatically evicts the least recently accessed items when the cache reaches its memory limit. Implementing LRU typically involves a doubly linked list to track access order and a hash map to quickly find items and their corresponding list nodes.

**Interviewer:** That's a solid approach to fault tolerance and data distribution. What about the "thundering herd" problem if a popular item expires or a cache node goes down? How would you mitigate that?

## Bottlenecks, failure modes and trade-offs

**Candidate:** That's a critical point, and it falls under **7. Bottlenecks, failure modes and trade-offs**. The "thundering herd" problem occurs when a highly requested item expires or is evicted, or when a cache node fails, causing many concurrent requests for the same key to hit the backend database simultaneously. This can overload the database and cascade into a system-wide failure.

To mitigate this, we can employ several strategies:
First, **Cache Stampede Prevention** or **Request Coalescing**. When a cache miss occurs for a hot key, only one request is allowed to fetch the data from the database. Subsequent concurrent requests for the same key are blocked or queued until the first request completes and populates the cache. This can be implemented using a distributed lock or a simple in-memory flag on the application server.

Second, **Graceful Degradation** and **Circuit Breakers**. If the cache or database starts to show signs of stress, the application can temporarily serve slightly stale data, or even return a default value, rather than failing completely. A **Circuit Breaker pattern** can prevent repeated calls to an unhealthy downstream service, allowing it to recover.

Third, **Proactive Caching/Pre-warming**. For extremely hot or critical data, we can pre-populate the cache, or refresh it in the background before items expire, rather than waiting for a request-driven cache miss.

Other potential **Bottlenecks** include:
*   **Network bandwidth:** While our estimates showed it's manageable, at ten times the scale, network capacity between application servers and cache nodes could become an issue.
*   **CPU on cache nodes:** Hashing, serialization/deserialization, and network I/O can consume significant CPU.
*   **Hot keys:** A few keys receiving disproportionately high access can overload a single cache node. This can be addressed by replicating hot keys across multiple nodes, or even using a local in-memory cache on the application servers for the hottest items.

The main **Trade-offs** in this design are:
*   **Consistency vs. Latency/Availability:** We've chosen eventual consistency to achieve very low latency and high availability. Accepting stale data for a few seconds is a deliberate trade-off.
*   **Cost vs. Performance:** In-memory caches are expensive per gigabyte compared to disk storage, but they offer unparalleled performance.
*   **Complexity vs. Simplicity:** Consistent Hashing and replication add complexity, but they are necessary for high availability and scalability.

At **ten times the scale**, meaning one thousand thousand reads per second and ten terabytes of data, we would need:
*   Significantly more cache nodes, potentially hundreds.
*   More robust monitoring and auto-scaling capabilities.
*   A multi-region deployment strategy for disaster recovery and lower latency for geographically dispersed users.
*   More advanced routing and load balancing, potentially at the network layer.
*   A dedicated team to manage and optimize the cache infrastructure.
*   More aggressive hot key handling, possibly using a multi-tier caching strategy (e.g., local application cache, then distributed cache).

## Wrap-up

**Candidate:** To wrap up, our distributed cache design leverages Redis instances across multiple nodes, employing **Consistent Hashing** for efficient data distribution and minimal remapping during scaling events. We use the **Cache-Aside pattern** for application interaction, ensuring the primary database remains the source of truth. **Replication** and **virtual nodes** provide high availability and fault tolerance, mitigating node failures. **TTL** and **LRU** manage data freshness and memory. We've considered challenges like the "thundering herd" problem and hot keys, with strategies like request coalescing and graceful degradation. This architecture provides a highly available, low-latency, and scalable caching solution for a high-traffic e-commerce platform.

**Interviewer:** Thank you, that's a comprehensive design.

Three to five key terms and patterns to remember from this problem are:
1.  **Consistent Hashing:** Essential for distributing data and minimizing remapping when nodes are added or removed.
2.  **Cache-Aside Pattern:** The most common way applications interact with a cache, ensuring the database remains the source of truth.
3.  **Replication and Fault Tolerance:** How to ensure the cache remains available even if nodes fail, often through primary-replica setups.
4.  **Eviction Policies (LRU, LFU, TTL):** Strategies to manage memory and data freshness in the cache.
5.  **Thundering Herd Problem:** A common failure mode where many requests for a missing or expired item overwhelm the backend, and techniques like request coalescing to prevent it.

A common mistake candidates make when designing a distributed cache is not adequately addressing how data is distributed across nodes, or how node failures are handled. Many candidates might suggest a simple `hash(key) % N` without recognizing its limitations during scaling. Another common oversight is not discussing cache invalidation or eviction policies in detail, which are fundamental to cache effectiveness. This candidate covered all these aspects thoroughly.
