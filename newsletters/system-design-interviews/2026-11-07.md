**Interviewer:** Hi, welcome. Today's problem is to design a search autocomplete system, sometimes called typeahead. When a user types a few characters into a search box, we want to suggest relevant queries in real time. How would you approach this?

**Candidate:** Thank you. This is a classic system design problem, and I'm ready to dive in. I'll start by clarifying the **1. Requirements**, then move to **2. Back-of-the-envelope estimates**, **3. API design**, **4. Data model and storage**, **5. High-level design**, and then deep dive into the hardest parts, discussing **6. Bottlenecks, failure modes, and trade-offs**, and finally a **7. Wrap-up**.

## Requirements

**Candidate:** Let's start with functional requirements. The core function is to take a prefix string and return a ranked list of suggested queries. What are the key criteria for these suggestions? Should they be based on popularity, recency, or other factors?

**Interviewer:** Primarily popularity and relevance. We want the top five to ten most popular suggestions that match the prefix.

**Candidate:** Got it. Are there any specific requirements around personalization, like suggestions based on a user's past search history?

**Interviewer:** Not for the initial design. Let's keep it global popularity for now. That could be a follow-up.

**Candidate:** Understood. Now for non-functional requirements. What kind of scale are we talking about? How many search queries per day, and what's the expected latency for autocomplete suggestions?

**Interviewer:** We're looking at about one billion search queries per day. For latency, users expect instant feedback, so P99 latency should be under 50 milliseconds. Availability should be high, say 99.99 percent.

**Candidate:** One billion searches per day is significant. For consistency, is it acceptable for new, very popular queries to take a few minutes to appear in suggestions, or do we need near real-time updates?

**Interviewer:** Eventual consistency is fine. A few minutes delay for popularity updates is acceptable, but new queries should be added to the system within, say, an hour.

## Back-of-the-envelope estimates

**Candidate:** Excellent, let's do some quick back-of-the-envelope estimates.
First, requests per second. If we have one billion searches per day, and assuming each search session involves a user typing, on average, five characters before selecting a suggestion or completing their search, that's five autocomplete requests per search. So, five billion autocomplete requests per day.
Dividing that by the number of seconds in a day, which is roughly 86,400, we get about 58,000 requests per second on average. We should account for peak traffic, which could be two to three times the average, so let's plan for around 150,000 requests per second.

**Candidate:** Next, storage. How many unique search queries do we anticipate storing?

**Interviewer:** Let's assume up to 100 million unique queries that are popular enough to be considered for suggestions.

**Candidate:** Okay, 100 million unique queries. If an average query string is 20 characters, that's 20 bytes per query. Plus, we'll need to store a popularity score and possibly other metadata, let's say another 30 bytes. So, 50 bytes per query.
Total storage for the raw query data would be 100 million queries multiplied by 50 bytes, which is 5 gigabytes. This is quite small.
However, the core data structure for autocomplete, typically a Trie, will consume more memory. A Trie stores prefixes. If we have 100 million queries, each averaging 20 characters, the total number of characters in all queries is 2 billion. A Radix Trie, which compresses common prefixes, would have fewer nodes than that. Let's estimate the Trie itself could be in the range of 10 to 20 gigabytes in memory, depending on implementation and how we store the top K suggestions at each node. This is a manageable size for modern servers.

**Candidate:** Finally, bandwidth. Each request sends a short prefix, say 5 characters. Each response returns 5 to 10 suggestions, each about 20 characters long. So, a response might be 10 suggestions times 20 characters, plus JSON overhead, let's say 200 bytes per response.
At 150,000 requests per second, that's 150,000 multiplied by 200 bytes, which is 30 megabytes per second. This is well within typical network capacities.

## API design

**Candidate:** For the API, we need a simple endpoint for clients to query. I propose a RESTful GET endpoint:

`GET /autocomplete?prefix={query_prefix}&limit={K}`

**Candidate:** The `query_prefix` parameter would be the string the user has typed so far. The `limit` parameter would specify the maximum number of suggestions to return, defaulting to, say, 10.
The response would be a JSON array of strings, where each string is a suggested query. For example:

`["design system", "design patterns", "design thinking", "design interview", "design a URL shortener"]`

## Data model and storage choice

**Candidate:** For the data model, we need to store the actual search queries and their associated metadata. A simple `Query` object would suffice:

*   `query_text`: String, the actual search query.
*   `score`: Long, representing its popularity. This could be a combination of frequency, recency, and perhaps click-through rate.
*   `last_updated`: Timestamp, for recency.

**Candidate:** For storage, given the low latency and high QPS requirements, the core autocomplete functionality will rely on an in-memory data structure. A **Trie**, specifically a **Radix Trie** or a **Ternary Search Tree**, is ideal for prefix matching. It offers O(L) lookup time, where L is the length of the prefix.

**Candidate:** This in-memory Trie will be built from a persistent store. For the persistent store, a relational database like PostgreSQL or MySQL would be suitable. It can reliably store our 100 million `Query` objects, handle updates from our data ingestion pipeline, and serve as the source of truth for rebuilding the Trie. It provides ACID properties for data integrity, which is important for our source data. NoSQL databases like Cassandra or DynamoDB could also work for storing the raw queries, but for this scale and structured data, a relational database is perfectly fine.

## High-level design

**Candidate:** Let's walk through the high-level design.

**Candidate:** At the front, we'll have clients, typically web browsers or mobile apps, sending requests to our service. These requests will first hit a **Load Balancer**, which distributes traffic across multiple instances of our **Autocomplete Service**.

**Candidate:** The **Autocomplete Service** instances are stateless. Each instance holds a full copy of the in-memory Radix Trie. When a request comes in with a prefix, the service traverses its local Trie to find matching suggestions, ranks them by score, and returns the top K. This approach ensures very low latency because all data is in memory and local to the service instance. This is an example of the **Read-Through Cache pattern**, where the cache (Trie) is loaded upfront.

**Candidate:** To keep the Trie up-to-date, we need a **Data Ingestion Pipeline**. This pipeline will process user search logs to update query popularity scores.
User searches are typically logged to a distributed message queue, like **Kafka**. A **Stream Processing System**, such as Apache Flink or Spark Streaming, would consume these logs from Kafka. It would aggregate query counts and update the `score` for each `Query_text`. This allows us to handle high volumes of log data in real time.

**Candidate:** The stream processing system then writes the updated `Query` data to our persistent database, say PostgreSQL.
Periodically, perhaps hourly or daily, a **Batch Job** reads all the `Query` data from PostgreSQL, rebuilds the entire Radix Trie from scratch, and then pushes this new Trie to all Autocomplete Service instances. This is a form of **blue-green deployment** for the Trie data: new Tries are built offline, then swapped in. This avoids complex incremental updates to a live, distributed Trie and ensures consistency across all service instances. The service instances could download the new Trie from a shared storage like S3 or a dedicated configuration service.

## Deep dives

**Candidate:** Let's deep dive into a few critical components.

**Candidate:** First, the **Radix Trie Implementation**. Each node in our Radix Trie will represent a character or a sequence of characters (for compression). To efficiently retrieve the top K suggestions, each node should store a small, fixed-size data structure, like a min-priority queue, containing the top K `(score, query_ID)` pairs that pass through that node. When traversing the Trie for a given prefix, we collect these top K lists from the matching node and its children, merge them, and return the overall top K. Storing `query_ID`s instead of full strings in the Trie saves memory, as the full query strings can be retrieved from a separate in-memory hash map indexed by `query_ID`. This is a classic **space-time trade-off**.

**Interviewer:** What happens if a particular Autocomplete Service node dies? How does the system handle that?

**Candidate:** That's a great question. Since our Autocomplete Service instances are stateless and identical, if one node dies, the Load Balancer will simply stop sending requests to it and redirect traffic to the remaining healthy nodes. We'd use a health check mechanism, like sending periodic pings to the service instances, to detect failures. This is a standard **failover** mechanism, ensuring high availability. We'd have enough redundant instances to handle a few failures without impacting performance.

**Interviewer:** You mentioned rebuilding the entire Trie periodically. Why not just update it incrementally in real-time?

**Candidate:** That's a valid alternative, but it introduces significant complexity. An incremental update would require a distributed, mutable Trie, which is very hard to keep consistent across many nodes, especially with concurrent writes and reads. It would involve distributed locking, complex synchronization, and potentially higher latency for updates. For our problem, where a few minutes or even an hour of staleness is acceptable, a full rebuild is much simpler, more robust, and easier to operate. The 10-20 gigabyte Trie can be rebuilt and loaded into memory within minutes, making the "downtime" for the Trie update negligible, especially with the blue-green deployment strategy. This is a **simplicity versus real-time freshness trade-off**.

**Interviewer:** How do you determine the "score" for a query?

**Candidate:** The score is crucial for ranking. A simple approach is to use the raw frequency count of how many times a query has been searched. However, this might favor old, popular queries over new, trending ones. A better approach is to use a **decaying popularity score**, where recent searches contribute more to the score than older ones. For example, we could apply an exponential decay function to past search counts. We could also incorporate **click-through rates** from past suggestions: if a suggestion is frequently clicked when presented, its score should increase. The stream processing system would be responsible for calculating and updating this composite score.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss potential bottlenecks and failure modes.

**Candidate:** **Bottlenecks**:
1.  **Memory**: If the number of unique queries grows significantly beyond 100 million, or if average query length increases, the in-memory Trie could exceed server RAM capacity.
2.  **Data Ingestion Pipeline**: If the volume of search logs spikes drastically, the Kafka cluster or the stream processing system might struggle to keep up, leading to delays in score updates.
3.  **Network Bandwidth**: While currently manageable, if we return many more suggestions or much longer strings, network bandwidth could become a bottleneck.

**Candidate:** **Failure Modes**:
1.  **Autocomplete Service Instance Failure**: As discussed, the load balancer handles this by redirecting traffic to healthy nodes.
2.  **Trie Rebuild Failure**: If the batch job fails to build a new Trie, the Autocomplete Service instances continue serving the old Trie. This means suggestions won't be as fresh, but the service remains operational. This is a **graceful degradation** scenario.
3.  **Database Failure**: If PostgreSQL goes down, the stream processing system can't persist new scores, and the batch job can't rebuild the Trie. Again, the Autocomplete Service continues serving the last known good Trie.

**Candidate:** **Trade-offs**:
1.  **Freshness vs. Complexity**: We chose periodic full rebuilds over real-time incremental updates for simplicity and operational stability, accepting some staleness.
2.  **Memory vs. CPU**: An in-memory Trie uses more RAM but provides extremely fast lookups. A disk-based solution would use less RAM but incur I/O latency. For low-latency requirements, in-memory is the right choice.
3.  **Global vs. Personalized Suggestions**: We opted for global popularity first. Adding personalization would require storing user profiles and their search histories, significantly increasing storage and query complexity.

**Candidate:** What happens at ten times the scale? If we hit 1.5 million QPS and a billion unique queries, the system would need adjustments.
1.  **Autocomplete Service**: We'd need proportionally more instances, potentially hundreds.
2.  **Trie Size**: A billion queries at 50 bytes each would be 50 GB for raw data, and the Trie could grow to 100-200 GB. This might still fit on very large single machines (e.g., AWS X1 instances), or we might need to explore **sharding the Trie**. Sharding could be done by the first character, but this can lead to uneven distribution. A more advanced approach might involve consistent hashing on the prefix to distribute parts of the Trie across multiple clusters. However, this adds significant complexity and might not be necessary if large memory instances are available.
3.  **Data Ingestion**: Kafka and the stream processing system are designed for high throughput and should scale well by adding more partitions and processing nodes.
4.  **Database**: PostgreSQL might become a bottleneck for writes at that scale. We might need to shard the database or migrate to a more horizontally scalable NoSQL solution for the raw query storage.

## Wrap-up

**Candidate:** To summarize, my design for Search Autocomplete leverages a highly available, low-latency **Autocomplete Service** that serves suggestions from an in-memory **Radix Trie**. This Trie is periodically rebuilt from a persistent relational database, which stores query popularity aggregated by a real-time **Stream Processing System** consuming logs from **Kafka**. This architecture prioritizes simplicity, high availability, and low latency, with clear trade-offs around data freshness and scalability for future growth.

Three to five key terms and patterns to remember from this problem are:
1.  **Radix Trie (or Ternary Search Tree)**: The fundamental data structure for efficient prefix matching.
2.  **In-memory data store**: Essential for achieving low latency.
3.  **Data Ingestion Pipeline with Stream Processing**: For collecting and aggregating popularity data at scale.
4.  **Blue-green deployment for data**: A robust way to update large, in-memory datasets without downtime.
5.  **Eventual Consistency**: A common and acceptable trade-off for many large-scale systems like this.

One common mistake candidates make is not considering the memory footprint of the Trie or not having a clear strategy for how to update the suggestions data over time. Another common miss is not adequately estimating the QPS and storage, which can lead to an undersized solution.
