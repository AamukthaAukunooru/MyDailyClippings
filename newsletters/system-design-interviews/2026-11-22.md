**Interviewer:** Alright, welcome. Today's problem is to design Netflix. Imagine you're building the core streaming platform, allowing users to browse, search, and watch video content globally. We have 200 million subscribers, with a peak of about 50 million concurrent users. Our content library has 100,000 titles, each averaging two hours in length. How would you approach designing such a system?

**Candidate:** Thank you. Designing Netflix is a fascinating challenge, primarily due to its global scale and the demanding nature of video streaming. I'll structure my answer using our usual template, starting with requirements.

## 1. Requirements

**Candidate:** First, let's clarify the functional requirements. Users need to be able to:
1.  **Register and log in** to their accounts.
2.  **Manage user profiles** within an account.
3.  **Browse the content catalog** by genre, new releases, etcetera.
4.  **Search for specific titles**.
5.  **Receive personalized recommendations**.
6.  **Stream video content** seamlessly, with options for different qualities.
7.  **Track watch history and progress**, allowing users to resume playback.
8.  **Rate content** and add it to a watchlist.

**Candidate:** For non-functional requirements, given the scale:
1.  **Availability:** The service must be highly available, especially for video playback. I'd aim for four or five nines of availability.
2.  **Latency:** Low latency is crucial for video playback to avoid buffering, and also for browsing and search responsiveness.
3.  **Scalability:** The system must handle millions of concurrent users and a massive content library, scaling globally.
4.  **Consistency:** For user account details and billing, strong consistency is preferred. For watch history, recommendations, and catalog browsing, eventual consistency is generally acceptable.
5.  **Durability:** Video content, user data, and metadata must be highly durable.

**Interviewer:** Those numbers sound good. Let's use your estimate of 50 million concurrent users at peak, and an average watch time of two hours per day per user. Assume a 4K video is roughly 7 gigabytes per hour.

**Candidate:** Excellent, those concrete numbers help a lot.

## 2. Back-of-the-envelope estimates

**Candidate:** Let's crunch some numbers for scale.
*   **Concurrent Users:** 50 million. This is our peak load for active streaming and browsing.
*   **Requests per second (RPS) for API calls:** If each user makes, say, 10 requests per minute for browsing, search, or updating watch progress, that's 50 million users multiplied by 10 requests per minute, divided by 60 seconds per minute. That gives us approximately 8.3 million requests per second for the API backend, excluding the actual video streaming. This is a very high RPS, indicating a need for highly scalable microservices and caching.
*   **Storage for video content:** We have 100,000 titles, averaging two hours each. At 7 gigabytes per hour for 4K, that's 14 gigabytes per title. So, 100,000 titles multiplied by 14 gigabytes per title equals 1.4 petabytes. However, we need multiple encodings for adaptive bitrate streaming – different resolutions and bitrates. Let's assume an average of 5 versions per title. That brings our total video storage to 1.4 petabytes multiplied by 5, which is 7 petabytes. This content needs to be stored durably and globally accessible.
*   **Bandwidth:** This is the most challenging aspect. If we assume an average stream quality of 5 megabits per second, which is good quality HD, then 50 million concurrent users multiplied by 5 megabits per second gives us a staggering 250 terabits per second. This immense bandwidth requirement immediately points to a Content Delivery Network, or CDN, as a critical component.

## 3. API design

**Candidate:** For the API, I'd design a RESTful interface, likely exposed through an API Gateway. Key endpoints would include:
1.  **Authentication:** `/auth/login` and `/auth/register` to handle user authentication and issue tokens.
2.  **User Profiles:** `/users/{userId}/profiles` for managing user profiles, supporting GET, POST, PUT, and DELETE operations.
3.  **Catalog Browsing:** `/catalog/titles` for fetching lists of titles, with query parameters for filtering by genre, year, or popularity. `/catalog/titles/{titleId}` to get detailed information about a specific title.
4.  **Search:** `/search?query={query}` to find content based on keywords.
5.  **Recommendations:** `/recommendations/{userId}` to retrieve personalized content suggestions.
6.  **Watch History:** `/users/{userId}/history` to get a user's watch history and `/users/{userId}/history/{titleId}` to update playback progress or remove an item. Updating progress would typically be a POST request with the current timestamp.
7.  **Streaming Control:** `/stream/{titleId}`. This endpoint wouldn't return the video itself, but rather a manifest file for adaptive bitrate streaming, containing URLs to video chunks hosted on a CDN.

## 4. Data model and storage choice

**Candidate:** We'll need a mix of database technologies to meet different requirements:
1.  **Video Metadata (titles, genres, descriptions):** For structured, relatively stable data that requires strong consistency for catalog integrity, a **relational database** like PostgreSQL or MySQL would be a good choice. It handles complex queries well for browsing.
2.  **User Data (profiles, settings, watchlist):** For user profiles, a relational database could also work. However, for high-volume, less strictly consistent data like watch history or user ratings, a **NoSQL database** like Cassandra or DynamoDB would be better. These offer high write throughput and availability, with eventual consistency being acceptable.
3.  **Recommendations:** Pre-computed recommendations could be stored in a fast **key-value store** like Redis for quick retrieval, or in a specialized graph database if relationships between content and users are complex.
4.  **Actual Video Files:** The raw video files, in all their encoded versions, should be stored in highly durable and scalable **object storage**, such as Amazon S3 or Google Cloud Storage. These services are designed for massive amounts of unstructured data and provide global distribution capabilities.

## 5. High-level design

**Candidate:** At a high level, the system would be a distributed microservices architecture, fronted by an API Gateway and heavily reliant on a global CDN.

1.  **Client Devices:** Users interact via web browsers, mobile apps, or smart TVs.
2.  **Load Balancer:** Incoming requests first hit a global load balancer to distribute traffic across regions and services.
3.  **API Gateway:** This acts as the single entry point for all client requests. It handles authentication, rate limiting, SSL termination, and routes requests to the appropriate microservice. This is an example of the **API Gateway pattern**, centralizing cross-cutting concerns.
4.  **Microservices:**
    *   **User Service:** Manages user registration, login, profiles, and authentication.
    *   **Catalog Service:** Manages all video metadata, genres, descriptions, and availability.
    *   **Search Service:** Likely powered by an inverted index database like Elasticsearch for fast, full-text search capabilities.
    *   **Recommendation Service:** Generates and serves personalized content recommendations.
    *   **Watch History Service:** Tracks user viewing progress and history.
    *   **Streaming Control Service:** Handles requests for video playback, authenticates users, and generates the adaptive bitrate streaming manifest.
5.  **Content Delivery Network (CDN):** This is absolutely critical. It's a globally distributed network of edge servers that cache video content close to users, reducing latency and offloading traffic from our origin servers.
6.  **Object Storage:** This is the origin for all video content, where the master copies of our 7 petabytes of video files reside.
7.  **Databases:** As discussed, a mix of relational, NoSQL, and key-value stores.
8.  **Caching Layer:** Distributed caches like Redis or Memcached would be used extensively across services for frequently accessed data, like popular titles, user session data, or pre-computed recommendations. This is the **cache-aside pattern**, where the application explicitly manages the cache.
9.  **Message Queues:** Technologies like Kafka or RabbitMQ would facilitate asynchronous communication between services, for example, updating watch history, processing analytics, or triggering recommendation model updates.

**Candidate:** Let's trace a request: When a user clicks on a movie to play it, their client application makes an API call to `/stream/{titleId}`. This request goes through the Load Balancer to the API Gateway. The API Gateway authenticates the user with the User Service and then routes the request to the Streaming Control Service. This service validates the user's subscription, retrieves metadata from the Catalog Service, and then generates an adaptive bitrate streaming manifest file, like HLS or DASH. This manifest contains URLs pointing to various video chunks at different bitrates, all hosted on the CDN. The client then receives this manifest and directly requests the video chunks from the nearest CDN edge server, which streams the content.

## 6. Deep dives

**Interviewer:** That's a solid high-level overview. Let's dive deeper into a couple of areas. The bandwidth requirement is enormous. How exactly does the CDN handle that, and what happens when an edge node fails?

**Candidate:** The CDN is the backbone for video delivery. It works by caching video content at "edge locations" geographically close to users. When a user requests a video chunk, the CDN directs them to the nearest edge server. If the content is cached there, it's served immediately, providing low latency and high throughput. If not, the edge server fetches it from a regional cache, or ultimately from our central object storage, and then caches it for future requests. This significantly reduces the load on our origin infrastructure and minimizes network hops.

**Candidate:** We'd use **adaptive bitrate streaming** protocols like HLS (HTTP Live Streaming) or MPEG-DASH. This means we encode each video title into multiple versions, each at a different resolution and bitrate. The client player dynamically switches between these versions based on the user's network conditions and device capabilities, ensuring the best possible viewing experience without buffering.

**Candidate:** Regarding edge node failures, CDNs are designed with high redundancy. If an edge node fails, the CDN's DNS system or traffic management logic would automatically redirect requests to another healthy edge node in the vicinity. For critical services like Netflix, we would likely employ a **multi-CDN strategy**, using two or more different CDN providers. This provides an additional layer of redundancy and allows us to route traffic dynamically to the best-performing or most available CDN, mitigating the risk of a single provider outage.

**Interviewer:** Good. Now, let's talk about the recommendation system. With 200 million subscribers, how do you scale that and ensure recommendations are fresh and relevant without excessive compute?

**Candidate:** The recommendation system is a complex beast. It typically involves a hybrid approach.
1.  **Batch Processing:** For the majority of recommendations, we'd use offline batch processing. Data like user watch history, ratings, and content metadata would be fed into machine learning models (e.g., collaborative filtering, content-based filtering) using big data frameworks like Apache Spark or Hadoop. These models would run periodically, perhaps daily or hourly, to generate updated recommendation lists for each user. This is an example of a **batch processing pipeline**.
2.  **Real-time Recommendations:** For more immediate relevance, we could have a component that generates recommendations based on the user's current viewing session or recent interactions. This might involve simpler, faster models or rule-based systems.
3.  **Storage and Serving:** The pre-computed recommendations would be stored in a fast key-value store like Redis or a specialized recommendation database, optimized for quick lookups by user ID. When a user logs in, the Recommendation Service fetches these pre-computed lists.
4.  **Scalability:** To handle 200 million users, the batch processing would be horizontally scaled across a large cluster. The serving layer would also be sharded by user ID, distributing the load across many instances. We'd also heavily cache recommendations. For users with very similar profiles, we might even pre-compute recommendations for "clusters" of users rather than individually, reducing the total computation. We'd also need to address the **cold start problem** for new users by providing popular or trending content recommendations until enough data is collected.

## 7. Bottlenecks, failure modes and trade-offs

**Candidate:** Identifying bottlenecks and failure modes is crucial for a resilient system.
*   **Bottlenecks:**
    *   **Bandwidth:** As discussed, this is the biggest. The CDN is the primary solution.
    *   **Database Hotspots:** Very popular titles or user data could create hotspots in our databases. We mitigate this with sharding, read replicas, and aggressive caching.
    *   **Recommendation Compute:** Generating recommendations for 200 million users is computationally intensive. Solved by batch processing, incremental updates, and caching.
    *   **API Gateway:** Could become a bottleneck if not properly scaled. Horizontal scaling and efficient routing are key.
*   **Failure Modes:**
    *   **CDN Failure:** Mitigated by a multi-CDN strategy and fallback to origin object storage, though with higher latency.
    *   **Database Failure:** Replication (primary-replica), automatic failover mechanisms, and data backups are essential.
    *   **Microservice Failure:** Individual services can fail. We'd implement **circuit breakers** to prevent cascading failures, **retries with exponential backoff**, and **graceful degradation** (e.g., if recommendations fail, show trending content instead).
    *   **Network Partitions:** Distributed systems are susceptible to network partitions. For certain data, we accept **eventual consistency** to maintain availability.
*   **Trade-offs:**
    *   **Consistency vs. Availability:** We've chosen eventual consistency for non-critical data like watch history and recommendations to ensure high availability, while maintaining stronger consistency for critical user account data.
    *   **Cost vs. Performance:** CDNs are expensive, but they are non-negotiable for performance and scale. Redundant systems and global distribution increase infrastructure costs.
    *   **Complexity vs. Scalability:** A microservices architecture is complex to build and operate but offers superior scalability, fault isolation, and development agility compared to a monolithic approach.

**Candidate:** If the system needed to scale to ten times its current size, say 2 billion subscribers:
*   We'd need even more sophisticated **global traffic management** and potentially more regional data centers.
*   **Database sharding** would become even more granular, possibly using **consistent hashing** for data distribution to minimize rebalancing.
*   The **caching strategy** would need to be even more aggressive and multi-layered.
*   The **recommendation system** would require further optimization, potentially using more advanced distributed ML frameworks and even more pre-computation.
*   A **multi-CDN strategy** would be absolutely essential, with dynamic routing based on real-time network conditions.
*   We'd explore more **serverless functions** for specific, stateless microservices to handle bursty loads efficiently.

## 8. Wrap-up

**Candidate:** In summary, designing Netflix at scale requires a highly distributed, resilient architecture. Key components include a **microservices architecture** for agility and scalability, fronted by an **API Gateway**. The massive bandwidth demands are met by a global **Content Delivery Network** leveraging **adaptive bitrate streaming**. Video content is stored durably in **object storage**. Data is managed across a mix of **relational and NoSQL databases**, with extensive **caching** to optimize performance. The system is designed with redundancy, failover mechanisms, and trade-offs between consistency and availability to ensure a seamless user experience for millions of concurrent users worldwide.

**Interviewer:** Excellent. That's a comprehensive design.

Three to five key terms and patterns to remember from this problem are:

2.  **Adaptive Bitrate Streaming (HLS/DASH):** The standard for delivering video efficiently across varying network conditions.
3.  **Microservices Architecture:** For scalability, fault isolation, and development agility.
4.  **Object Storage:** The ideal solution for storing massive amounts of unstructured video data durably.
