**Interviewer:** Hi there. Today, let's design a live cricket score application, similar to Cricbuzz. Think about how users would get real-time updates for ongoing matches, historical data, and schedules.

**Candidate:** Sounds like a fun challenge. I'll start by clarifying the **requirements**.

## 1. Requirements

**Candidate:** First, the functional requirements. Users should be able to view live scores, ball-by-ball commentary, match schedules, and past match results. For live matches, the scores and commentary need to be updated in near real-time. Do we need user accounts, personalized content, or push notifications as part of the core design, or are those stretch goals?

**Interviewer:** Let's keep user accounts and personalized content as out of scope for now. Push notifications for score updates would be a great stretch goal, but focus on the core real-time display first.

**Candidate:** Understood. So, core functional requirements are:
1.  Display live scores and match status for ongoing matches.
2.  Display ball-by-ball commentary for live matches.
3.  Display upcoming match schedules.
4.  Display past match results and detailed scorecards.

**Candidate:** Now for non-functional requirements. What kind of scale are we targeting? How many daily active users, and what's the peak concurrency during a major match?

**Interviewer:** Let's aim for a large scale. Imagine ten million daily active users, with up to one million concurrent users during peak match times, like a World Cup final.

**Candidate:** One million concurrent users, got it. That's significant.
*   **Latency:** For live score updates, what's an acceptable delay from when the event happens on the ground to when it appears on the user's screen?
*   **Availability:** What's our target for uptime?
*   **Consistency:** For live scores, do we need strong consistency, or is eventual consistency acceptable? For historical data, I assume strong consistency is preferred.

**Interviewer:** For live scores, we want near real-time, ideally within one to two seconds. For static data like schedules or past results, typical web response times, say under two hundred milliseconds, are fine. Availability should be high, let's target four nines, or 99.99 percent. For consistency, yes, strong consistency for historical data. For live scores, it's a bit nuanced: the *source* of truth must be strongly consistent, but propagating it to millions of users, eventual consistency is acceptable as long as it's fast.

**Candidate:** Excellent, that clarifies a lot. To summarize non-functional requirements:
*   **Scale:** Ten million DAU, one million peak concurrent users.
*   **Latency:** One to two seconds for live updates, under two hundred milliseconds for static data.
*   **Availability:** 99.99 percent.
*   **Consistency:** Strong for historical data and source of truth, fast eventual consistency for live score propagation.

## 2. Back-of-the-envelope estimates

**Candidate:** Let's do some quick **back-of-the-envelope estimates** to understand the load.
With one million concurrent users, if they're polling for live score updates, say, every five seconds, that's one million divided by five, which is two hundred thousand requests per second just for live score polling. On top of that, users will be loading match details, schedules, and past results. Let's conservatively estimate a peak of three hundred thousand requests per second for reads.

**Interviewer:** That's a good starting point for read traffic. What about write traffic?

**Candidate:** Good question. Write traffic primarily comes from score updates. A cricket match has many events: balls bowled, runs scored, wickets, overs completed. Let's say, on average, there are two hundred significant events per match per minute, and during peak times, we might have ten matches running concurrently. That's two hundred events per minute per match, times ten matches, which is two thousand events per minute, or about thirty-three events per second. These are internal writes from scorekeepers. This is a relatively low write throughput compared to reads.

**Candidate:** For storage, historical match data, including ball-by-ball commentary, might be a few megabytes per match. If we store data for ten thousand matches over several years, that's roughly ten thousand matches times five megabytes per match, which is fifty gigabytes. This is quite manageable for a database. Live match data will be in memory for quick access.

**Candidate:** Bandwidth is a bigger concern. If each live score update response is small, say one kilobyte, and we have two hundred thousand requests per second, that's two hundred thousand kilobytes per second, which is two hundred megabytes per second. This is significant and needs efficient delivery mechanisms.

## 3. API design

**Candidate:** Next, let's outline the main **API endpoints**. I'll propose a RESTful API structure.

*   `GET /matches/live`: This endpoint would return a list of all currently live matches, with essential summary information like teams, current score, and status.
*   `GET /matches/{match_id}/score`: This is the primary endpoint for detailed live score and commentary updates for a specific match. It would return the current score, overs, wickets, and the latest ball-by-ball events.
*   `GET /matches/{match_id}/full_card`: To fetch the complete scorecard for a match, either live or finished.
*   `GET /matches/schedule`: Returns a list of upcoming matches, filterable by date or series.
*   `GET /matches/past`: Returns a list of past match results, filterable by date, team, or series.
*   `POST /matches/{match_id}/update_event`: This would be an internal API, secured, used by scorekeepers to push individual ball-by-ball events or score changes. It would take an event object containing details like `ball_number`, `runs_scored`, `wicket_fallen`, `commentary_text`, etc.

**Interviewer:** That looks reasonable for the client-facing APIs and internal updates.

## 4. Data model and storage choice

**Candidate:** Now, let's think about the **data model and storage choice**. Given the mix of real-time, high-read, and historical data, I'd propose a hybrid approach.

For **live match data**, which requires extremely fast reads and frequent updates, I'd choose an in-memory key-value store like **Redis**. Each live match could be stored as a hash or a sorted set in Redis, with its `match_id` as the key. This allows for quick retrieval of the current state and efficient appending of new ball-by-ball events. Redis also offers publish/subscribe capabilities, which will be crucial for real-time updates.

For **historical match data, schedules, player profiles, and user data** (if we implement it later), a **relational database** like PostgreSQL would be a good fit. It provides strong consistency, ACID properties, and robust querying capabilities for complex joins, for example, fetching all matches a specific player participated in. We would have tables like:
*   `Matches`: `match_id` (PK), `series_id`, `team1_id`, `team2_id`, `date`, `venue`, `status` (live, finished, scheduled).
*   `MatchEvents`: `event_id` (PK), `match_id` (FK), `ball_number`, `over_number`, `commentary_text`, `runs_scored`, `wicket_fallen`, `timestamp`.
*   `Teams`: `team_id` (PK), `name`, `country`.
*   `Players`: `player_id` (PK), `name`, `team_id`, `role`.
*   `Scorecards`: `scorecard_id` (PK), `match_id` (FK), `player_id` (FK), `runs`, `balls_faced`, `wickets_taken`, etc.

**Interviewer:** Why Redis for live data instead of just using PostgreSQL with heavy caching?

**Candidate:** That's a good question. While we could use PostgreSQL with caching, Redis offers several advantages for this specific use case. First, its in-memory nature provides significantly lower latency for reads and writes compared to disk-backed databases, which is critical for near real-time updates. Second, Redis's native Pub/Sub feature is purpose-built for broadcasting messages, which is exactly what we need for pushing live score updates to many clients. Third, the data structure flexibility in Redis, like hashes for current match state and lists or sorted sets for ball-by-ball commentary, maps very well to the dynamic nature of live match data. PostgreSQL would require more complex querying and potentially higher load for the constant small updates. We would still use PostgreSQL as the durable store for *all* match events once they are final, but Redis serves as the high-speed, transient store for the *live* view.

## 5. High-level design

**Candidate:** Let's move on to the **high-level design**.

At the front, we'll have **Clients**: mobile applications (iOS, Android) and web browsers.

All client requests will first hit a **Load Balancer**, like an AWS Elastic Load Balancer or Nginx, to distribute traffic across our application servers.

Behind the load balancer, we'll have an **API Gateway**. This gateway will handle common concerns like authentication (if we add user features later), rate limiting, and request routing to different backend services.

Our backend will be composed of several microservices:
1.  **Live Score Service:** This service is responsible for serving live match data. It reads from and writes to the Redis cluster. It also manages WebSocket connections for pushing real-time updates.
2.  **Match Data Service:** This service handles requests for historical match results, schedules, and full scorecards. It interacts primarily with the PostgreSQL cluster.
3.  **Score Ingestion Service:** This is an internal service. It receives score updates from external data sources or ground reporters via our internal `POST /matches/{match_id}/update_event` API. It then processes these events and publishes them to a message queue.
4.  **Notification Service (Stretch Goal):** If we implement push notifications, this service would consume events from the message queue and send notifications.

For data flow:
*   **Data Ingestion:** Scorekeepers send updates to the **Score Ingestion Service**. This service validates the data and publishes it to a **Message Queue**, like Kafka or RabbitMQ. This acts as a buffer and decouples the ingestion from processing.
*   **Processing Live Data:** The **Live Score Service** consumes events from the Message Queue. It updates the live match state in the **Redis Cluster**.
*   **Real-time Client Updates:** The Live Score Service also uses Redis's Pub/Sub mechanism. When it updates a match in Redis, it publishes a message to a specific Redis channel for that match. Dedicated **WebSocket Servers** (part of the Live Score Service or a separate component) subscribe to these Redis channels and push updates to connected clients.
*   **Historical Data Persistence:** The Live Score Service or a separate worker could also asynchronously persist the detailed ball-by-ball events from the Message Queue into the **PostgreSQL Cluster** for long-term storage and historical queries. This uses an **eventual consistency** model for the historical database, ensuring the live view is prioritized.
*   **Static Content:** A **Content Delivery Network (CDN)** like Cloudflare or Akamai will be used to cache static assets such as images, CSS, and JavaScript files, reducing load on our origin servers and improving latency for users globally.

**Interviewer:** That's a comprehensive high-level view. How exactly do you plan to handle the real-time updates to one million concurrent users? WebSockets sound good, but that's a lot of open connections.

## 6. Deep dives

**Candidate:** You've hit on one of the hardest parts: **Real-time updates at scale**.

We'll use **WebSockets** as the primary mechanism. When a user opens a live match page, their client establishes a WebSocket connection to one of our dedicated WebSocket servers. These servers are part of or closely integrated with the Live Score Service.

The **Pub/Sub pattern** is key here. When the Score Ingestion Service receives an update, it publishes an event to a Kafka topic. The Live Score Service consumes this event, updates the relevant match data in Redis, and then publishes a concise update message to a Redis Pub/Sub channel specific to that `match_id`.

Our WebSocket servers are subscribed to these Redis Pub/Sub channels. When a message arrives for a match, the WebSocket server forwards it to all clients currently connected and subscribed to that specific match's updates. This way, we avoid polling, which is inefficient for both client and server, and push updates only when they occur.

To scale WebSockets, we'll run multiple **WebSocket servers** behind the Load Balancer. These servers need to be stateless or have shared state. If a client disconnects and reconnects to a different server, they should seamlessly resume. The Redis Pub/Sub acts as the shared message bus, so individual WebSocket servers don't need to communicate directly.

**Interviewer:** What happens if an update comes in twice, maybe due to a retry from the ingestion service? How do you ensure data integrity?

**Candidate:** That's a crucial point, especially with message queues and distributed systems. We'll implement **idempotency** in our Score Ingestion Service and Live Score Service. Each score event will have a unique `event_id` or a combination of `match_id`, `over_number`, and `ball_number`. When the Live Score Service processes an event, it first checks if this `event_id` has already been processed for that match. If it has, the duplicate event is simply ignored. This prevents erroneous double-counting of runs or wickets. This is a common pattern for ensuring reliability when dealing with "at-least-once" message delivery guarantees from queues like Kafka.

**Interviewer:** What about the initial load for a user joining a live match? They need the current score and recent commentary, not just future updates.

**Candidate:** For the initial load, when a client connects to a match, they first make a regular `GET /matches/{match_id}/score` API call to the Live Score Service. This fetches the current state of the match directly from Redis. Once they have the initial state, they then establish the WebSocket connection to receive subsequent real-time updates. This is a **cache-aside pattern** where the client first checks the "cache" (Redis via API) and then subscribes to future changes.

## 7. Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss **bottlenecks, failure modes, and trade-offs**.

**Bottlenecks:**
1.  **Redis Cluster:** While fast, a single Redis instance can become a bottleneck. We'll deploy a **Redis Cluster** for horizontal scaling, sharding data across multiple Redis nodes. This distributes the load and increases capacity. Each shard would handle a subset of matches.
2.  **PostgreSQL Cluster:** For historical data, read-heavy queries might strain the database. We'd use **read replicas** to offload read traffic from the primary. For extreme scale, we might consider **sharding** the PostgreSQL database based on `match_id` or `series_id`, though for fifty gigabytes of historical data, that's likely overkill initially.
3.  **WebSocket Servers:** Managing millions of concurrent connections requires sufficient server resources (CPU, memory, network I/O). We'll scale these horizontally by adding more instances behind the load balancer.
4.  **Network Bandwidth:** Pushing two hundred megabytes per second of updates is significant. We'll ensure our cloud provider infrastructure can handle this and optimize payload sizes.

**Failure Modes:**
1.  **Single Point of Failure:** Any single service or database instance failing could bring down parts of the application. We'll address this with **redundancy** at every layer: multiple instances of each service, database replication (primary-replica for PostgreSQL, cluster for Redis), and deploying across multiple availability zones.
2.  **Data Ingestion Pipeline Failure:** If the Score Ingestion Service or Message Queue fails, updates won't reach users. The Message Queue (Kafka) inherently provides durability and fault tolerance. We'd implement dead-letter queues for messages that cannot be processed and robust retry mechanisms.
3.  **Cache Invalidation Issues:** If Redis gets out of sync with the true score, users see incorrect data. Our design ensures Redis is updated directly from the ingestion pipeline, and historical data is asynchronously persisted. For non-live data, we'd use appropriate Time-To-Live (TTL) values in caches.

**Trade-offs:**
1.  **Consistency vs. Availability (CAP Theorem):** For live scores, we prioritize **availability** and **partition tolerance** over strong consistency across all users at all times. The source of truth is strongly consistent, but propagation is eventually consistent. For historical data, we prioritize strong consistency.
2.  **Polling vs. WebSockets:** WebSockets are more complex to implement and manage at scale but are far more efficient for real-time updates. Polling is simpler but generates much more traffic. We choose WebSockets for efficiency, with short polling as a fallback for older clients if necessary.

**What changes at ten times the scale?**
*   **Database Sharding:** PostgreSQL would definitely need sharding if historical data grows to terabytes.
*   **More Redis Shards:** The Redis cluster would need significantly more shards to handle the increased number of live matches and concurrent users.
*   **Global Distribution:** We'd likely need to deploy our services and databases across multiple geographical regions to reduce latency for users worldwide and provide disaster recovery. This involves complex data synchronization strategies.
*   **Edge Caching:** More aggressive caching at the edge for even dynamic content, perhaps using technologies like Varnish or custom edge compute.
*   **Optimized Data Formats:** Further optimization of payload sizes for WebSocket messages to reduce bandwidth costs.

## 8. Wrap-up

**Candidate:** To wrap up, we've designed a highly available and scalable live cricket score application. We started with clear functional and non-functional requirements, targeting ten million daily users and near real-time updates. Our design leverages a hybrid data storage approach with Redis for low-latency live scores and PostgreSQL for durable historical data. The core of our real-time system relies on a message queue for robust ingestion, a Pub/Sub pattern with WebSockets for efficient client updates, and idempotency to ensure data integrity. We've considered scaling bottlenecks, failure modes, and trade-offs, outlining how the system would evolve to handle even greater loads through techniques like sharding and global distribution.
