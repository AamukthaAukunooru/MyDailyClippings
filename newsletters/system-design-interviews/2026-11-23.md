**Interviewer:**
Alright, let's design YouTube. What are the core features you'd focus on for a system design interview?

**Candidate:**
Okay, I'll start by outlining the **1. Requirements**. I'll cover functional requirements first, then non-functional ones.

For functional requirements, the core features I'd prioritize are:
*   Users can upload videos.
*   Users can view videos.
*   Users can search for videos.
*   Users can subscribe to channels.
*   Users can like, dislike, and comment on videos.
*   The system should provide video recommendations.

For non-functional requirements, these are critical for a system like YouTube:
*   **Scale**: We're talking about billions of users, with millions of daily active users. I'd need some concrete numbers for daily uploads and views to make estimates.
*   **Latency**: Low latency for video playback, meaning quick start times and minimal buffering.
*   **Availability**: High availability, near one hundred percent, especially for video playback.
*   **Consistency**: Eventual consistency is acceptable for non-critical data like view counts, likes, or comments. However, strong consistency is required for critical data, such as ensuring a video's metadata is correct and available immediately after a successful upload.

**Interviewer:**
Good. Let's make some assumptions for scale. Assume one hundred million daily active users. Ten million videos uploaded per day. Average video length, say, five minutes. Average resolution, seven hundred and twenty pixels.

**Candidate:**
Excellent, thank you for those numbers, they're crucial for the next step.

## 2. Back-of-the-envelope estimates

Let's do some quick calculations to understand the scale of storage, bandwidth, and requests per second.

*   **Storage**:
    *   An average five-minute video at seven hundred and twenty pixels might be around fifty megabytes.
    *   Daily uploads: ten million videos times fifty megabytes per video equals five hundred terabytes per day.
    *   Annually, that's five hundred terabytes per day times three hundred and sixty-five days, which is approximately one hundred and eighty petabytes per year. This is a massive amount of storage, clearly requiring a distributed **blob storage** solution.
*   **Bandwidth**:
    *   If each of our one hundred million daily active users watches, on average, five videos per day, that's five hundred million views daily.
    *   Total daily data transferred: five hundred million views times fifty megabytes per view equals twenty-five petabytes per day. This is an immense amount of data, making a **Content Delivery Network**, or CDN, absolutely essential.
*   **Requests per second (RPS)**:
    *   Average views per second: five hundred million views per day divided by twenty-four hours times three thousand six hundred seconds per hour, which is roughly six thousand views per second. Peak traffic could easily be ten times that, so sixty thousand views per second.
    *   Uploads per second: ten million uploads per day divided by twenty-four hours times three thousand six hundred seconds per hour, which is about one hundred and fifteen uploads per second. This rate is much lower than views, but each upload involves a large file.

## 3. API design

I'd define a few key APIs to support these core functionalities:

*   `POST /videos`: This endpoint handles video uploads. It would take the video file, title, description, and the user's ID. It would return a video ID and the upload status. I would use an **idempotency key** here, a unique identifier generated by the client, to ensure that if a client retries an upload due to a network issue, it doesn't result in duplicate videos being created.
*   `GET /videos/{video_id}`: This is for retrieving video metadata and streaming URLs. It takes a `video_id` and returns details like title, description, uploader, view count, and crucially, a list of CDN URLs for different resolutions of the video.
*   `GET /search?query={query}`: For searching videos. It takes a search query and pagination parameters, returning a list of video metadata.
*   `POST /videos/{video_id}/like`: To like a video. Takes `video_id` and `user_id`.
*   `POST /videos/{video_id}/comment`: To add a comment. Takes `video_id`, `user_id`, and the comment text.

## 4. Data model and storage choice

*   **Video Metadata**:
    *   `Video` table: `video_id` (Primary Key), `user_id`, `title`, `description`, `upload_date`, `duration`, `thumbnail_url`, `status` (e.g., `PENDING`, `READY`), `view_count`, `likes`, `dislikes`.
    *   `User` table: `user_id` (PK), `username`, `email`, `profile_picture_url`.
    *   `Comment` table: `comment_id` (PK), `video_id`, `user_id`, `text`, `timestamp`.
    *   `Subscription` table: `subscriber_id`, `channel_id`.
    *   For this metadata, a relational database like PostgreSQL or MySQL would be a good choice due to its strong consistency and ACID properties, especially for the video's status. Given the scale, we would need to **shard** this database, perhaps by `video_id` or `user_id`, to distribute the load. For highly dynamic, less critical data like view counts, we could use a fast key-value store like Redis for caching and eventual consistency, updating the main database asynchronously.
*   **Video Files**:
    *   These are large binary objects. A distributed object storage system is essential. This is a **blob storage** solution, like Amazon S3, Google Cloud Storage, or Azure Blob Storage. It handles durability, availability, and scalability for large files.
*   **Search Index**:
    *   For efficient full-text search, a dedicated search engine like Elasticsearch or Apache Solr would be used. It provides powerful indexing and querying capabilities and scales horizontally.
*   **Recommendations**:
    *   A graph database like Neo4j or a specialized recommendation engine could store user-video interactions and generate personalized recommendations.

## 5. High-level design

Let's walk through the two main flows: video upload and video playback.

**Video Upload Flow:**
1.  **Client uploads video**: The user's device sends the video file to an **Upload Service** through a **Load Balancer** and **API Gateway**. For very large files, clients might directly upload to a pre-signed URL provided by the blob storage, bypassing our service entirely for the raw file transfer. This is an optimization to offload our application servers.
2.  **Upload Service**: This service authenticates the user, validates initial metadata, and generates a unique `video_id`. It stores initial metadata in the metadata database, setting the status to `PENDING`.
3.  **Blob Storage**: The raw video file is stored in our distributed object storage system.
4.  **Message Queue**: The Upload Service publishes a message to a **Video Processing Queue** (e.g., Kafka, RabbitMQ), containing the `video_id` and the storage location of the raw file. This is an example of the **asynchronous processing pattern**, decoupling the upload from the processing.
5.  **Video Processing Workers**: A pool of worker services consumes messages from this queue. Each worker performs several tasks:
    *   **Transcoding**: Converts the video into multiple formats and resolutions (e.g., 240p, 480p, 720p, 1080p) to support adaptive bitrate streaming. This is a very compute-intensive task.
    *   **Thumbnail Generation**: Extracts keyframes to create various thumbnails.
    *   **Metadata Extraction**: Extracts additional technical metadata like codecs, duration.
    *   **Watermarking/DRM**: If required.
6.  **Update Metadata**: Once all processing is complete and the transcoded files are stored, workers update the video's status to `READY` in the metadata database, along with `thumbnail_url` and available resolutions.
7.  **Notification**: A notification service can inform the uploader that their video is ready.

**Video Playback Flow:**
1.  **Client requests video**: The user's device sends a `GET /videos/{video_id}` request to the **API Gateway**.
2.  **Video Service**: This service handles metadata retrieval.
    *   It first checks a **distributed cache** (e.g., Redis) for the video metadata. This is the **cache-aside pattern**: check cache first, if not found, fetch from database, then populate cache.
    *   If not found in cache, it queries the **metadata database**.
    *   It constructs the streaming URLs, which point directly to the **Content Delivery Network (CDN)**, for the various resolutions available.
3.  **CDN**: The API Gateway returns these CDN URLs to the client. The client then requests the video segments directly from the CDN.
4.  **CDN Cache**: The CDN serves the video from its nearest edge server if it's cached there. This dramatically reduces latency and bandwidth load on our origin servers.
5.  **Origin Storage**: If the video is not in the CDN cache, the CDN requests it from our distributed blob storage (the origin). The video is then cached by the CDN for future requests.

## 6. Deep dives

**Interviewer:**
That's a good high-level overview. Let's dive into the video processing pipeline. You mentioned transcoding. How would you ensure this process is robust and scalable, especially when a worker node dies mid-transcode?

**Candidate:**
That's a critical point, as the video processing pipeline is indeed one of the hardest parts. To ensure robustness and scalability:

1.  **Message Queues for Decoupling and Reliability**: We leverage a persistent message queue like Kafka. When a worker picks up a task, it doesn't immediately acknowledge it. If the worker dies before completing the task, the message remains in the queue and will be picked up by another available worker after a configured timeout. This implements a **consumer-group pattern** for fault tolerance, ensuring tasks are eventually processed.
2.  **Idempotent Processing**: Each processing task, such as transcoding a specific resolution, must be designed to be **idempotent**. This means running it multiple times with the same input produces the same output and doesn't cause harmful side effects. For example, if a worker dies, another worker can safely re-process the same video segment without corrupting existing data or creating duplicates.
3.  **Distributed Task Management and Health Checks**: We could use a system like Apache ZooKeeper or HashiCorp Consul to manage worker registration, perform health checks, and facilitate dynamic task assignment. This allows us to detect failed workers quickly and reassign their tasks.
4.  **Containerization and Orchestration**: Deploying our workers in containers (e.g., Docker) managed by an orchestrator like Kubernetes provides automatic scaling, self-healing capabilities, and rolling updates. If a container instance, or pod, dies, Kubernetes automatically restarts it or provisions a new one.
5.  **Output Storage and Atomicity**: Processed video segments and thumbnails are stored in our distributed blob storage. Workers only update the metadata database with the `READY` status once *all* necessary outputs are successfully stored and verified. This ensures a form of atomicity for the processing step from a user's perspective; a video is either fully processed and ready, or it's still pending. We might use a temporary staging area in blob storage for intermediate files before moving them to their final, publicly accessible locations.

**Interviewer:**
Regarding video playback, you mentioned a CDN. Why not just stream directly from your own blob storage, given its massive scale? What are the advantages of a CDN beyond just caching?

**Candidate:**
That's a great question. While our blob storage is massively scalable and durable, it's typically optimized for raw storage capacity and data integrity, not necessarily for low-latency, global content delivery to end-users.

The primary advantages of a CDN, beyond just basic caching, are:

1.  **Global Distribution and Edge Locations**: CDNs have Points of Presence, or PoPs, strategically located geographically close to users worldwide. This significantly reduces network latency because content travels a shorter physical distance from the edge server to the user. Streaming directly from a centralized blob storage would mean higher latency for users far from the data center. This is effectively a form of **geographical sharding** for content delivery.
2.  **Reduced Load on Origin**: By serving the vast majority of requests from its edge caches, the CDN offloads a huge amount of traffic from our origin blob storage and our internal network infrastructure. This saves significant bandwidth costs and prevents our origin from becoming a bottleneck under heavy load.
3.  **Optimized Network Routing**: CDNs often employ sophisticated routing algorithms to find the fastest and least congested path to deliver content, dynamically bypassing internet bottlenecks.
4.  **Security Features**: Many CDNs offer built-in DDoS protection, Web Application Firewalls (WAF), and secure tokenized URLs to prevent unauthorized access or hotlinking, which is crucial for protecting our content.
5.  **Adaptive Bitrate Streaming Support**: CDNs are designed to work seamlessly with adaptive bitrate protocols like HLS or DASH. They can efficiently deliver appropriate video segments based on the user's current network condition and device capabilities, ensuring a smooth viewing experience. Our blob storage would simply serve the raw files; the CDN understands how to serve segments efficiently for streaming.

## 7. Bottlenecks, failure modes and trade-offs

**Interviewer:**
What are the potential bottlenecks in this design, and how would it behave at ten times the load?

**Candidate:**
At ten times the load, which would be one billion daily active users and one hundred million uploads per day, every component would be under extreme stress.

**Potential Bottlenecks:**
1.  **Metadata Database**: Our relational database, even if heavily sharded, could become a significant bottleneck for both reads and writes. We'd need even more aggressive caching, extensive use of read replicas, and potentially move to a more horizontally scalable NoSQL solution for certain types of metadata. We might even adopt a **Command Query Responsibility Segregation (CQRS)** pattern, separating read models from write models to optimize each.
2.  **Video Processing Pipeline**: Ten times the uploads means ten times the transcoding demand. Our message queue could back up severely, and we'd need a massive increase in worker instances. This is where robust auto-scaling based on queue depth and resource utilization becomes absolutely critical.
3.  **CDN Egress Costs**: While CDNs reduce load on our origin, the sheer volume of data egress from the CDN itself would become an enormous cost factor. Optimizing video encoding efficiency and sophisticated caching strategies would be paramount.
4.  **Search Index**: The search engine (Elasticsearch) would require substantial scaling, distributed across many nodes, and careful indexing strategies to handle the increased query load and data volume.
5.  **Recommendation Engine**: Generating real-time, personalized recommendations for a billion users would require a highly distributed, real-time processing system, likely leveraging advanced machine learning models and big data technologies like Spark or Flink.

**Failure Modes and Trade-offs:**
1.  **CDN Cache Misses**: If a video isn't popular or is very new, it might not be cached at the nearest edge location. This leads to higher latency for the first few viewers as the CDN fetches it from the origin. The trade-off is between cache freshness and latency; we accept higher latency for less popular content to optimize for the majority of views.
2.  **Asynchronous Processing Failures**: If the video processing pipeline fails for a specific video, it might remain in a "processing" state indefinitely. We'd need robust monitoring, alerting, and automated retry mechanisms with **dead-letter queues** for messages that consistently fail. The trade-off here is between immediate consistency and system throughput; we prioritize throughput and eventual consistency for video availability.
3.  **Database Sharding Complexity**: Sharding helps scale, but it introduces significant operational complexity in terms of query routing, data migration, and managing distributed transactions if they become necessary. We trade operational simplicity for massive scalability.
4.  **Eventual Consistency**: For non-critical data like view counts, likes, or comments, we accept eventual consistency. A user might not see their like immediately reflected globally, but it will propagate eventually. This trades strong consistency for higher availability and lower latency on writes.

At ten times the load, we'd likely see a greater shift towards highly specialized databases for different data types, even more reliance on event-driven architectures, and significant investment in advanced machine learning for recommendations and content moderation. The core principles of distributed systems, like fault tolerance, asynchronous processing, and caching, would become even more critical and sophisticated.

## 8. Wrap-up

**Candidate:**
To summarize, we designed YouTube focusing on the core functionalities of video upload, processing, and playback. We established functional and non-functional requirements, making back-of-the-envelope estimates for storage and bandwidth that highlighted the massive scale. Our API design defined key endpoints for content interaction. The data model leveraged relational databases for metadata, distributed blob storage for video files, and a search engine for discovery. The high-level design involved an asynchronous video processing pipeline with message queues and workers, and a critical reliance on a global Content Delivery Network for efficient video delivery. We deep-dived into ensuring the robustness of the processing pipeline using idempotency and message queues, and justified the CDN's role beyond simple caching. Finally, we discussed potential bottlenecks like the metadata database and processing capacity at ten times the scale, highlighting key trade-offs like eventual consistency for availability.

## Interviewer's notes

**Interviewer:**
That was a very strong answer. The candidate demonstrated a clear, structured approach, starting with requirements and estimates, which is essential for any system design. They effectively broke down the problem into manageable components and walked through the critical paths.

Three to five key terms and patterns to remember from this problem are:
1.  **Content Delivery Network (CDN)**: Absolutely crucial for any media streaming platform. Understand its role in reducing latency, offloading origin servers, and handling global distribution.
2.  **Asynchronous Processing with Message Queues**: For compute-intensive tasks like video transcoding, using a message queue (like Kafka) with worker pools is a fundamental pattern for scalability, reliability, and decoupling.
3.  **Blob Storage**: For storing large binary objects like video files, a distributed object storage system (like S3) is the go-to solution.
4.  **Idempotency**: Especially important for operations like video uploads or processing tasks, to ensure that retries don't lead to duplicate or corrupted data.
5.  **Cache-Aside Pattern**: Used for optimizing read performance by checking a cache before hitting the primary data store.

A common mistake candidates make with this problem is immediately jumping into complex details about recommendation algorithms or live streaming without first establishing a solid foundation for the core upload and playback functionality. Always start with the fundamentals and scale up.
