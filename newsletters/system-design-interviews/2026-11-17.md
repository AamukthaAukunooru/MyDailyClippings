**Interviewer:** Alright, let's design the Twitter timeline. Imagine you're building the core system that allows users to post tweets and view their personalized home timeline.

## Requirements

**Candidate:** Understood. I'll start by clarifying the functional and non-functional requirements.
Functionally, we need to support two main operations:
One, a user should be able to post a tweet. This tweet can include text and potentially media, though for this initial design, I'll focus on text and assume media is handled by a separate media service, returning a URL.
Two, a user should be able to view their home timeline, which is an ordered list of tweets from the users they follow.
Three, a user should also be able to view their own profile, which shows all tweets they've posted.

**Interviewer:** Good. Let's get some numbers for non-functional requirements. What kind of scale are we talking about?

**Candidate:** For non-functional requirements, I'll consider scale, latency, availability, and consistency.
For scale, let's assume Twitter's current numbers: around 350 million daily active users, or DAU.
How many tweets per day are posted?

**Interviewer:** Let's say 500 million tweets are posted daily.

**Candidate:** Okay, 500 million tweets per day.
For latency, what's an acceptable target for viewing the home timeline?

**Interviewer:** We're aiming for a fast, responsive experience. Let's target under 200 milliseconds for fetching the home timeline.

**Candidate:** Excellent. For availability, we need high availability, say 99.99 percent, as this is a core user experience.
Regarding consistency, for the home timeline, eventual consistency is generally acceptable. If a tweet appears a few seconds late, that's usually fine. For posting a tweet, we'd want stronger consistency, ensuring the tweet is durably stored.

**Interviewer:** That sounds reasonable.

## Back-of-the-envelope estimates

**Candidate:** Now, let's do some back-of-the-envelope estimates to understand the load.
First, for tweet writes: 500 million tweets per day. Dividing that by 24 hours, then 3,600 seconds, gives us roughly 5,787 tweets per second on average. Let's round that up to about 6,000 writes per second. This is a significant write load.

Next, for timeline reads: With 350 million DAU, if each user checks their timeline, say, 5 times a day, that's 1.75 billion timeline views per day. Dividing that by 24 hours and 3,600 seconds, we get approximately 20,250 reads per second. This tells us the system is significantly read-heavy, with roughly three to four times more reads than writes.

For storage, if a tweet is, say, 280 characters, that's about 280 bytes. Adding metadata like user ID, tweet ID, timestamp, and any media URL, let's estimate 500 bytes per tweet.
500 million tweets per day times 500 bytes per tweet is 250 gigabytes of new tweet data per day. Over a year, that's about 90 terabytes. This is manageable with distributed storage but implies we'll need to shard our data.

**Interviewer:** Good numbers.

## API design

**Candidate:** Moving on to API design, I'll define the main endpoints.
For posting a tweet, we'd have a `POST` request:
`POST /api/v1/tweets`
The request body would contain `user_id` and `text`. It would return the `tweet_id` and a success status.

For fetching the home timeline, a `GET` request:
`GET /api/v1/timeline`
This would take `user_id` as a query parameter, and optionally `max_id` for pagination, to fetch tweets older than a given tweet ID, and `count` for the number of tweets to return, defaulting to, say, 20. It would return a list of tweet objects, each containing `tweet_id`, `user_id`, `text`, `timestamp`, and `media_url` if present.

For fetching a user's own tweets, for their profile page:
`GET /api/v1/users/{user_id}/tweets`
Similar to the timeline, it would take `max_id` and `count` for pagination, returning a list of tweet objects.

**Interviewer:** Clear and concise.

## Data model and storage choice

**Candidate:** For the data model, we'll need a few entities.
First, a `Tweet` entity:
`tweet_id` (primary key, a globally unique identifier)
`user_id` (foreign key to the User table)
`text` (the tweet content)
`timestamp` (when the tweet was posted)
`media_url` (optional, URL to media content)

Second, a `User` entity:
`user_id` (primary key)
`username`
`display_name`
`email`
`followers_count`
`following_count`

Third, a `Follow` entity to represent the following relationship:
`follower_id` (part of composite primary key, foreign key to User)
`following_id` (part of composite primary key, foreign key to User)
`created_at`

For storage choice, given the high write throughput for tweets and the need for eventual consistency in timelines, a NoSQL wide-column store like Cassandra or a distributed key-value store like DynamoDB would be a strong candidate for storing the actual tweets and user timelines. These databases excel at horizontal scaling and high write availability. They also fit well with the fan-out pattern we'll discuss. For user profiles and follower lists, which require more relational integrity and might have less extreme write patterns, a sharded relational database like MySQL or PostgreSQL could also work, or even a graph database for the social graph if we wanted to do more complex queries on relationships. For this design, I'll assume a wide-column store for tweets and timelines, and a sharded relational database for user and follow data.

## High-level design

**Candidate:** Now, let's outline the high-level design, focusing on the two main flows: posting a tweet and viewing the home timeline.

We'll use a **fan-out on write** approach for the home timeline. This means when a user posts a tweet, we immediately push that tweet into the timelines of all their followers. This pre-computation makes timeline reads very fast, which aligns with our 200-millisecond latency requirement for reads.

**Tweet Posting Flow:**
1.  A user posts a tweet via a client application.
2.  The request goes through a **Load Balancer** to a **Tweet Service**.
3.  The Tweet Service validates the tweet, assigns a unique `tweet_id`, and stores the tweet data in a **Tweet Database**, which is a sharded wide-column store.
4.  Crucially, the Tweet Service then publishes a message to a **Message Queue**, like Kafka or RabbitMQ. This message contains the `tweet_id` and `user_id` of the tweet's author. This is an example of the **publish-subscribe pattern**, decoupling the tweet storage from the fan-out process.
5.  A **Fanout Service** consumes messages from the Message Queue.
6.  For each message, the Fanout Service queries a **Follower Service** to get the list of all followers for the `user_id` who posted the tweet. The Follower Service retrieves this from the sharded User/Follower Database.
7.  For each follower, the Fanout Service writes the `tweet_id` into that follower's personalized timeline. These timelines are stored in a **Timeline Database**, which is also a sharded wide-column store, optimized for fast retrieval by `user_id`. Each user's timeline is essentially a sorted list of tweet IDs.

**Home Timeline Viewing Flow:**
1.  A user requests their home timeline from their client.
2.  The request goes through a **Load Balancer** to a **Timeline Service**.
3.  The Timeline Service first checks a **Distributed Cache**, like Redis, for the user's timeline. This is the **cache-aside pattern**. The cache stores pre-computed lists of tweet IDs for active users.
4.  If the timeline is in the cache (a cache hit), the service retrieves the list of `tweet_id`s directly.
5.  If it's not in the cache (a cache miss), the Timeline Service fetches the list of `tweet_id`s from the **Timeline Database**.
6.  Once the list of `tweet_id`s is obtained, whether from cache or DB, the Timeline Service then fetches the full tweet content for these IDs from the **Tweet Database**. This might involve a batch read to optimize performance.
7.  Finally, the Timeline Service returns the fully hydrated list of tweet objects to the user's client.

**Interviewer:** That's a solid overview.

## Deep dives

**Interviewer:** Let's dive deeper into the fan-out strategy. You chose fan-out on write. What happens when a celebrity with, say, 100 million followers posts a tweet? Your Fanout Service would have to write to 100 million timelines. That sounds like a massive write amplification.

**Candidate:** That's an excellent point, and it's a known challenge with pure fan-out on write. This scenario with "super-users" or celebrities is where a **hybrid approach** often comes into play.
For the vast majority of users, fan-out on write works very well because their follower counts are manageable. The read latency benefits are significant.
For super-users with millions of followers, a full fan-out on write can indeed create a huge spike in writes and potentially overwhelm the Fanout Service or the Timeline Database.
Here's how we can handle it:
One, we can introduce a threshold. For users above a certain follower count, say a million, we switch to a **fan-out on read** model for their tweets. In this case, when a super-user tweets, we *don't* push it to all their followers' timelines immediately. Instead, when a follower of a super-user requests their timeline, the Timeline Service would fetch tweets from the users they follow who use fan-out on write, *and then separately query* for tweets from the super-users they follow, merging these results before returning them. This adds complexity and potentially latency to the read path for followers of super-users, but it significantly reduces the write load.

Two, we could implement a **lazy fan-out** or a tiered approach. For super-users, we might only fan out to a subset of their most active or recent followers, and then rely on a background process to gradually fan out to the rest, or for less active followers, they would fetch on demand.

Three, we can optimize the fan-out service itself. We can shard the Fanout Service by `follower_id` or `user_id` to distribute the load. We can also use **batching** to write multiple tweet IDs to a user's timeline in a single operation, reducing database round trips. The Message Queue also acts as a buffer, absorbing spikes and allowing the Fanout Service to process messages at its own pace. If the queue backs up, it means timelines might be slightly delayed, but the system remains available.

Given our 200-millisecond latency requirement for reads, I'd lean towards the hybrid approach, using fan-out on write for most users and fan-out on read for super-users, possibly combined with aggressive caching for super-user tweets.

**Interviewer:** Okay, that addresses the super-user problem. Let's talk about the Timeline Database. How exactly would you store a user's timeline, and how would you ensure fast retrieval and updates?

**Candidate:** In the Timeline Database, which I suggested as a wide-column store like Cassandra, each user's timeline would essentially be a row or a document. The primary key would be the `user_id`. Within that row, we would have a column for each tweet ID, with the column name being the `timestamp` or a composite of `timestamp` and `tweet_id` to ensure uniqueness and natural ordering.
So, a user's timeline would look something like:
`user_id: 123`
`{ 'timestamp_1': 'tweet_id_A', 'timestamp_2': 'tweet_id_B', ... }`
When a tweet is fanned out, we simply add a new column (tweet ID) to the appropriate user's timeline row.
Retrieval is efficient because we can query a specific `user_id` and fetch a range of columns (tweet IDs) sorted by timestamp, which directly gives us the latest tweets. This is a common pattern in wide-column stores.
To ensure fast updates, Cassandra, for example, is optimized for writes and handles eventual consistency well, which aligns with our requirements. We can also use **partitioning and sharding** based on `user_id` to distribute the timeline data across many nodes, preventing hot spots and allowing horizontal scaling.

**Interviewer:** What if a user deletes a tweet? How does that propagate to all the timelines it was fanned out to?

**Candidate:** That's a good follow-up. When a user deletes a tweet, we would trigger a similar process to the fan-out.
The Tweet Service would receive the delete request, mark the tweet as deleted in the Tweet Database, and then publish a "delete tweet" message to the Message Queue.
The Fanout Service, or a dedicated "Timeline Update Service," would consume this message. It would then need to identify all users who had this tweet in their timeline. This is the tricky part, as we don't have a reverse index from `tweet_id` to `follower_id` in our current design.
To solve this, we would need to store an additional mapping: `tweet_id` to `list_of_follower_ids` when the tweet is initially fanned out. This would be stored in a separate index table. Then, upon deletion, we would fetch this list and issue delete operations to each affected user's timeline in the Timeline Database.
Alternatively, we could implement a **soft delete** where the tweet is merely marked as deleted in the Tweet Database. When a timeline is fetched, the Timeline Service would filter out any tweets that are marked as deleted. This simplifies the fan-out deletion process but means deleted tweets still occupy space in timelines and require filtering on read. Given the scale, soft delete is often preferred for simplicity and performance during deletion, accepting the slight overhead on reads. I'd lean towards soft delete first, and if storage becomes an issue, then consider the more complex explicit deletion from timelines.

## Bottlenecks, failure modes and trade-offs

**Candidate:** Let's discuss bottlenecks, failure modes, and trade-offs.
The **Fanout Service** is a critical component and a potential bottleneck due to the write amplification. We mitigate this by making it highly scalable, running multiple instances, using a Message Queue for buffering, and implementing the hybrid fan-out strategy for super-users. If the Fanout Service fails, the Message Queue ensures messages are not lost and can be processed once the service recovers. This is an example of **durability** provided by the queue.

The **Timeline Database** and **Tweet Database** are also potential bottlenecks. We address this through extensive **sharding** based on `user_id` for timelines and `tweet_id` or `user_id` for tweets, ensuring data is distributed across many nodes.

A key trade-off is **consistency versus availability/latency**. We chose eventual consistency for timelines to achieve high availability and low read latency. This means a new tweet might not appear instantly on all followers' timelines, but the system remains fast and available.

What changes at ten times the scale? At ten times the scale, our current approach would still largely hold, but we'd need to aggressively scale out every component.
The number of shards for our databases would increase tenfold.
The Message Queue would need to handle ten times the throughput.
The Fanout Service would need significantly more instances and more sophisticated load balancing and possibly more fine-grained sharding of its work.
The caching layer would become even more critical, with more cache nodes and potentially more complex cache invalidation strategies.
The hybrid fan-out strategy would become even more important, as the number of super-users or users approaching that threshold would increase. We might need to dynamically adjust the follower count threshold for switching between fan-out on write and fan-out on read.

A potential failure mode is a **cascading failure** if one component, like the Follower Service, becomes overloaded and starts failing, impacting the Fanout Service, which then impacts timeline freshness. We'd implement **circuit breakers** and **rate limiting** to prevent such failures from propagating.

## Wrap-up

**Candidate:** In summary, our design for the Twitter timeline leverages a **fan-out on write** strategy for the home timeline, ensuring low read latency for the majority of users. We address the challenge of super-users with a **hybrid approach**, potentially switching to **fan-out on read** for their tweets. We use a **Message Queue** to decouple tweet posting from fan-out, providing resilience and scalability. Data is stored in sharded wide-column stores for high write throughput and eventual consistency, complemented by a **distributed cache** like Redis for fast timeline retrieval. This architecture prioritizes high availability and low read latency, which are critical for a real-time social feed.

**Interviewer:** Thank you. That's a comprehensive design.

Key terms and patterns to remember from this problem:
*   **Fan-out on Write (Push Model):** Pre-computing timelines for fast reads.
*   **Fan-out on Read (Pull Model):** Fetching tweets on demand, better for super-users.
*   **Hybrid Fan-out:** Combining both strategies based on follower count.
*   **Message Queues (e.g., Kafka):** For decoupling services and buffering writes during fan-out.
*   **Wide-Column Stores (e.g., Cassandra):** Ideal for high write throughput and eventual consistency of timelines.
*   **Distributed Caching (e.g., Redis):** For low-latency retrieval of frequently accessed timelines.
*   **Write Amplification:** The challenge of a single write leading to many writes for followers.

One common mistake candidates make:
Many candidates immediately jump to a pure fan-out on write solution without considering the implications for super-users. The ability to identify this bottleneck and propose a hybrid or alternative strategy is crucial. Another common miss is not considering the deletion of tweets and how that impacts a fanned-out timeline.
