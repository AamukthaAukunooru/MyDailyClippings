## Outages and postmortems

**Microsoft: Microsoft 365 Outage**
Microsoft experienced a major global outage of its Microsoft 365 services from November twelfth to fourteenth, 2026. Users worldwide, across more than seventy countries, reported problems with services including Outlook, Teams, and Copilot. The outage began between 5:00 PM and 6:00 PM UTC on November twelfth, initially affecting most Microsoft 365 services, with full restoration by the morning of November fourteenth.

The root cause was identified as a latent Windows defect that only affected newer, higher-core gateway servers, which were not adequately represented in Microsoft's load testing. This defect created a traffic congestion within each server, and the automatic traffic redistribution mechanisms, intended as safeguards, inadvertently spread the failure globally. Microsoft confirmed the incident was not a cyberattack or caused by AI tooling.

Microsoft's final report outlines thirteen fixes, including improving traffic distribution to prevent cascading failures, extending load testing to its newest hardware with production-like traffic, and increasing capacity headroom.
*Lesson for engineers: Thoroughly test new software updates on hardware configurations that precisely mirror production environments, especially for critical gateway services, and design traffic management systems to contain, rather than propagate, failures.*

**United Airlines: System Outage**
On November sixteenth, 2026, United Airlines experienced a system outage that delayed departing flights for over ninety minutes. Pilots reported difficulties in obtaining essential information for aircraft performance calculations, specifically data related to an aircraft's final weight before takeoff. The issue affected multiple crew-facing applications, including flight-planning, weather-briefing, and crew-management tools.

United Airlines stated the problem was a "technology issue" and confirmed there was no indication of a cybersecurity-related incident. The exact technical root cause was not immediately detailed by the airline. The problem was resolved approximately one hour and forty minutes after pilots first reported difficulties.
*Lesson for engineers: Critical operational systems, especially those impacting safety and real-time decision-making, require robust redundancy and immediate fallbacks for data delivery to prevent operational paralysis.*

**KDDI: Snow Outage**
KDDI, a major Japanese telecommunications provider, experienced mobile service outages starting November twentieth, 2026, due to heavy snowfall. The disruption affected au, UQ mobile, povo, and au-network MVNO communications, including emergency calls, across parts of Fukushima, Nagano, and Gifu prefectures.

KDDI attributed the failures to base-station power outages and transmission-line faults caused by the snow. As a primary continuity fallback, KDDI activated JAPAN Roaming. The incident highlighted structural vulnerabilities in physical infrastructure, particularly in base-station power and transmission lines, which no amount of software optimization can address.
*Lesson for engineers: Resilient system design must extend beyond software to include physical infrastructure hardening, power independence, and robust redundancy, especially in regions prone to extreme weather events.*

## Azure SQL Blog: SqlPackage Deployment History and Fast Comparison Preview

The Azure SQL team has introduced new `SqlPackage` capabilities to improve database deployment repeatability and performance. Historically, even when deploying the same database model, `SqlPackage` would perform a full schema comparison, which can be time-consuming in CI/CD pipelines. The new preview features, "Deployment history" and "Fast comparison," aim to address this.

Deployment history, enabled with the `LogDeployment` property, records deployment metadata in a `DeploymentHistory` table within the target database. Fast comparison, enabled with `EnableFastComparison`, leverages this history. If the model checksum and deployment options match the last deployment record, `SqlPackage` can skip the full schema comparison, significantly speeding up repeat deployments where no changes are needed. This is particularly useful for simulating CI/CD pipeline retries.

The preview targets `Microsoft.SqlPackage` version 170.6.40-preview. It's important to note that these options provide a record of deployments and a way to recognize a previously deployed database model; they are not a migration ordering system or an automatic rollback mechanism. The team advises against combining DAC registration with deployment-history versioning.

For a senior software engineer, this offers a clear path to optimizing database deployment pipelines, reducing build times, and improving the efficiency of idempotent deployments. Understanding the trade-off between full schema comparison and relying on deployment history checksums is key for balancing deployment speed with absolute verification.

## Lyft Engineering: Smooth Cruiser at Lyft: Built for Safety and Transparency

Lyft has engineered "Smooth Cruiser," a feature providing drivers with insights into their driving behavior, built on principles of real-world scoring and transparency. The core problem addressed is that traditional safety scoring often relies on fixed thresholds, which fail to account for the dynamic reality of driving conditions.

Smooth Cruiser measures four signals: smooth braking, smooth steering, vehicle speed, and mounted phone use. Each signal is measured relative to local conditions, considering the specific stretch of road, time of day, day of week, and time of year. For instance, a harsh brake where drivers commonly brake hard affects the score less than the same stop where they do not. Drivers are benchmarked against peers in their region and structurally similar markets, rather than a national average, ensuring fair comparisons. The score is computed using a rolling window of the last one hundred rides within twelve months, capturing typical behavior and balancing responsiveness with stability.

The data platform behind Smooth Cruiser processes a significant volume of telemetry, roughly one hundred thirty-five gigabytes of raw sensor data per hour during rush hours. This system transforms hundreds of thousands of raw sensor reports into consistent, standardized signals.

For a senior software engineer, this post highlights the complexities of building context-aware, fair, and transparent scoring systems at scale. The design choices around relative scoring, regional benchmarking, and rolling windows are crucial for accuracy and user acceptance. The mention of processing one hundred thirty-five gigabytes per hour underscores the performance engineering challenges in handling and transforming large-scale telemetry data.

## AWS Architecture Blog: How Rakbank built centralized observability at scale with Amazon OpenSearch Service

Rakbank, a retail digital banking platform, has implemented a centralized observability solution at scale using Amazon OpenSearch Service. The platform's containerized microservices on Amazon Elastic Kubernetes Service, or EKS, generate approximately one hundred fifty gigabytes of logs per day, a significant increase from five gigabytes per day before the migration.

The observability platform is designed for high availability and long-term retention. It uses a cross-account, Multi-Availability Zone Amazon OpenSearch Service with hot, warm, and cold tiering. The most recent thirty days of data are directly searchable, with a sixty-day window retaining nine terabytes in OpenSearch Service. For compliance, seven years of retention are required, backed by Amazon Simple Storage Service, or S3, archiving approximately three hundred eighty-three terabytes over that period. This architecture achieved approximately fifty-five percent cost savings compared to an all-hot cluster.

The telemetry pipeline uses Fluent Bit as a DaemonSet on the EKS cluster, performing a dual-write/parallel archive: one path sends logs to OpenSearch Service, and a parallel path lands raw log objects directly in Amazon S3 for durable backup. Cross-account log flow is secured via AWS Transit Gateway, keeping all communication private. Identity and cross-account authorization are managed through a layered security model, including VPC security groups, resource-based access policies, and fine-grained access control, with end-user access federated through SAML 2.0 single sign-on.

For a senior software engineer, this case study provides a robust example of designing a scalable, cost-effective, and compliant observability platform. Key takeaways include leveraging cloud-native services for data tiering and retention, implementing secure cross-account data flows, and the architectural significance of append-only data for optimizing storage and indexing.

## Netflix TechBlog: Engineering AI Discover

Netflix's "AI Discover" feature, a new tab in their TV app for finding content, is powered by a novel "intelligence layer" that combines large language models, or LLMs, with existing recommendation systems. This layer addresses the challenges of integrating generative AI into a product designed without it, while maintaining speed, reliability, and safety at Netflix's scale.

The intelligence layer acts as an agent harness, planning each request, executing it across various systems, serving results, and evaluating them offline. Key challenges included fitting LLMs into the existing architecture, ensuring recommendations are "grounded" in real, available titles, and managing the inherent slowness and unpredictability of LLMs. To mitigate these, LLMs are used selectively, their outputs are treated as untrusted input, and performance and quality are rigorously tested. The system also adapts to fast-changing models and prompts, and is built for the unique constraints of TV apps, such as difficult typing and slow update cycles, requiring rapid responses and updates without app releases.

Architecturally, when a member selects a theme, the TV app sends the request to a Page Server, which asynchronously hands it to the intelligence layer. This layer comprises a controller that decides what to run based on context and a planner, and an executor that runs a graph of approved "capabilities" (units of work like retrieval, ranking, generation, or packaging). Steps pass typed outputs, and independent steps run in parallel with deadlines and fallbacks. Member taste summaries, generated by an in-house language model called MemberLLM, are stored in Memory Hub, a per-member memory store, to personalize recommendations.

For a senior software engineer, this post offers valuable insights into integrating generative AI into large-scale, performance-critical systems. It highlights the importance of an architectural layer to orchestrate LLM interactions, manage their inherent limitations, and ensure system reliability and safety. The concepts of grounding recommendations, selective LLM use, and designing for diverse client environments are crucial for successful AI product development.

## Airbnb Engineering: De-identifying text at scale: How Airbnb protects personal data in AI training

Airbnb has implemented a robust system for de-identifying personally identifiable information, or PII, in text data at scale before it's used for machine learning model training. This initiative is driven by the need to protect user privacy and minimize PII copies, aligning with Airbnb's privacy policies.

The solution is built upon Presidio, an open-source library originally from Microsoft. Airbnb chose Presidio for its on-premises hosting capability, general-purpose functionality, modularity, multilingual support, and its ability to separate PII detection from obfuscation. It also supports redaction, masking, and realistic replacement of PII, ensuring consistent fake values within a run.

Presidio operates in two stages: the Analyzer identifies spans of text that look like personal data, labeling them with an entity type and confidence score, while the Anonymizer decides what replaces each span. Airbnb uses three kinds of recognizers: pattern-based, dictionary-based, and named entity recognition, or NER-based. Language detection is a prerequisite, performed on the whole record or taken from metadata, with a conservative configuration used if confidence is low.

The library is deployed as a Python package and integrated as a reusable pipeline step within Airbnb's shared machine learning workflow orchestrator. This ensures that raw personal data is de-identified in-process, avoiding a central bottleneck and simplifying data flow. Datasets are tagged as de-identified, and this tag gates model deployment to production. Each run records the library version and configuration for traceability.

For a senior software engineer, this post provides a practical blueprint for implementing privacy-preserving data pipelines for machine learning. It emphasizes the importance of a shared taxonomy for PII, the strategic choice of open-source tools, and architectural considerations for deploying de-identification as a scalable, in-process workflow step. The detailed explanation of recognizer types and the Analyzer/Anonymizer stages offers valuable insights into building effective PII detection and obfuscation systems.

## GitHub Engineering: Building the Agent Host Protocol for sessions that continue across devices

GitHub has developed the Agent Host Protocol, or AHP, an open standard that enables agent sessions, such as those for GitHub Copilot, to continue seamlessly across multiple devices and applications. This protocol addresses the limitations of tying agent lifetimes to specific applications, like a single VS Code window, and the need for bespoke integrations for each client.

The problem AHP solves is the "N:M" interaction between multiple clients and a shared set of agents, allowing a developer to start an agent session on a phone and continue it on a laptop. The protocol is designed to tolerate network interruptions, reconnections, and concurrent client mutations, while remaining full-featured enough for real work. Crucially, AHP avoids encoding how agents work, focusing instead on how clients interact with them, allowing for rapid evolution of agent capabilities.

AHP is oriented around URI-identified "channels," which are the coarsest unit of functionality. Every server must implement root, session, and chat channels, with optional channels for terminal support or telemetry. Within each channel, a reducer-based state object drives most client logic. The server acts as the arbiter of state, and clients send actions to mutate the state or trigger side effects. This design simplifies reconnection and replay in poor network conditions, makes clients and servers straightforward to debug, and integrates well with modern UI frameworks like React.

The adoption of AHP in VS Code required building a new harness and agentic stack, moving away from an extension-based model tied to the editor's lifecycle. GitHub also leveraged AHP for its cloud agents and to coordinate sessions running on personal devices via the Copilot app.

For a senior software engineer, this post offers a compelling case study in designing protocols for distributed, stateful AI agents. It highlights the importance of abstracting agent behavior from client interaction, the benefits of a reducer-based state model for managing complex, multi-client interactions, and the strategic shift from bespoke integrations to a standardized, extensible protocol for cross-device continuity.
