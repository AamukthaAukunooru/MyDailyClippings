## AWS Architecture Blog: How United Airlines streams database changes to Apache Iceberg

United Airlines faced a challenge in replicating frequently changing reference data from an operational Amazon Aurora MySQL-Compatible Edition database to a new cloud-native analytics system built on Apache Iceberg in near-real-time. Their legacy batch process could not keep pace, leading to stale data for analysts and delayed business decisions.

To address this, United Airlines built a near-real-time Change Data Capture, or CDC, pipeline. This pipeline uses Amazon Kinesis Data Streams, AWS Lambda, Amazon Data Firehose, and Apache Iceberg on Amazon S3. AWS Database Migration Service, or AWS DMS, acts as the CDC engine, writing change events to Kinesis Data Streams. Data Firehose then reads these events, writes them to the Iceberg table as Parquet files, applies inserts, updates, and deletes, and commits new table snapshots. This streaming layer simplifies operations by not requiring a separate application or server management for delivery.

The adoption of Iceberg removed scalability limits of their legacy SQL databases, allowing several hundred business analysts to run complex queries across a broader data domain. In United's testing, average query latency improved five times, and total job processing time dropped two times, while also reducing billed AWS Glue run time. The data, once in Iceberg tables, is queryable from AWS Glue, Amazon Redshift, and Amazon Athena. The post provides a simplified walkthrough for reproducing this approach, noting that the provided CloudFormation template is a representative view, not a complete production solution, and uses demo operational settings.

For a senior performance engineer, the key takeaway is the effective use of a serverless, managed CDC pipeline to achieve significant performance gains and scalability for analytical workloads. The ability to stream database changes in near-real-time to an open table format like Iceberg, coupled with the flexibility of multiple query engines, offers a powerful pattern for modern data architectures.

## Cloudflare Blog: An updated Clairic and Clairic-flash are now open-weight

Cloudflare's new Workers AI Superintelligence team has released updated versions of their frontier AI models, Clairic and Clairic-flash, as open-weight models. These models are designed for improved extraction from complex documents, including images and PDFs, with better handling of tables, lists, dates, and stronger grounding of answers in source material. Clairic-flash is a lighter, faster nine-billion-parameter version, while the updated Clairic is a twenty-seven-billion-parameter model.

The team redesigned Clairic's architecture after its preview release, focusing on extraction from unstructured data. For ordinary text and number extraction fields, they now use parallel slot autoregressive generation, where each field chooses its next token based on previously written tokens, advancing together in the serving batch for fast latency. Special heads were trained for computation, estimation, and extraction use cases, handling estimates, forecasts, durations, calculated dates, and explicit arithmetic.

Internal evaluations showed significant accuracy improvements. For example, on fresh text fields, Clairic improved from two hundred ninety-five out of three hundred thirty-six to three hundred thirty-five out of three hundred thirty-six. Latency tests demonstrated that even with the redesigned architecture, responses are typically under one second. Clairic-flash, being lighter, offers even faster performance, with p50 latencies ranging from one hundred fifty-five milliseconds for text fields to three hundred seventy-nine milliseconds for commercial leases. The models can now read PDFs and include up to four images or PDF pages in a single request, with image reading accuracy improving from two hundred seven errors to zero on internal benchmarks.

For a senior performance engineer, this post highlights advancements in efficient, specialized large language models for data extraction. The architectural choices, like parallel slot autoregressive generation and specialized heads, demonstrate strategies for optimizing accuracy and latency for specific tasks. The open-weight release and detailed performance metrics provide valuable insights into designing and evaluating high-performance AI inference systems.

## Datadog Engineering: How Datadog resolves evolving OpenTelemetry semantics at query time

Datadog faces the challenge of supporting evolving OpenTelemetry, or OTel, semantic conventions alongside Datadog-native conventions, ensuring that queries work transparently across all representations. OpenTelemetry's vocabulary changes, for instance, `http.method` became `http.request.method`. A simple name-only mapping is insufficient because semantic equivalence is more complex, involving different units, metric types, conditional applicability, and context-dependent meanings.

Datadog addresses this by representing these relationships in a knowledge graph called the Semantic Core. This graph captures equivalences between Datadog and OpenTelemetry metrics and span attributes, along with the conditions that determine when those equivalences are valid. Datadog applies this knowledge at query time, allowing queries to resolve equivalent telemetry data without requiring users to know how the data was produced or rewriting stored data.

A knowledge graph is preferred over a flat mapping table because it can represent transitive relationships, conditional equivalences, and metadata about when an equivalence is valid. For example, a deprecated-to-current edge allows deprecated names to be transitively queryable without explicit enumeration. The graph also captures provenance and scales better to multiple vocabularies. Conditional equivalences are crucial; for instance, `system.cpu.utilization` from OTel and `system.cpu.user` from Datadog represent user-space CPU utilization but require a tag filter (`state:user`) and a scaling factor (zero to one ratio versus zero to one hundred percentage) to be treated as equivalent.

For a senior performance engineer, the key takeaway is the sophisticated approach to managing schema evolution and semantic consistency in observability data. Using a knowledge graph to resolve conditional equivalences at query time is a powerful pattern for building flexible and future-proof monitoring systems, especially when integrating diverse and evolving data sources like OpenTelemetry. This method avoids costly data rewrites and simplifies the user experience for querying complex telemetry.

## Zerodha Tech: Distributed, high-performance blob storage on SQLite

Zerodha, a financial services company, needed a new solution for storing user preferences and metadata as opaque JSON blobs, ranging from a few kilobytes to several megabytes. Their existing solutions, CouchDB and later SSDB, became problematic due to SSDB being unmaintained, its C++ codebase not aligning with their stack, and its inability to scale horizontally, leading to size limits and latency degradation. They required a horizontally scalable, distributed, high-throughput key-value blob store with low latency, built-in compression, and economical maintenance.

After investigating various options like ScyllaDB, PostgreSQL, YugabyteDB, RocksDB, Ceph, SeaweedFS, S3/MinIO, and raw filesystem, each with its own drawbacks for their specific overwrite-heavy, high-throughput use case, Zerodha decided to build their own solution. They were inspired by SQLite's performance claims and their experience pushing PostgreSQL limits.

The result is Blobasaur, an open-source, sharded blob server written in Rust that uses SQLite as its storage engine and speaks the Redis protocol. This single-binary application is designed for high performance and ease of deployment and maintenance. It has successfully replaced SSDB in production at Zerodha. By speaking the Redis protocol, it allowed existing Go and Python services to integrate seamlessly without changes. Blobasaur is designed to serve both two-kilobyte settings blobs and five-megabyte chart layouts with single-digit millisecond latency, and includes built-in compression for repetitive JSON payloads.

For a senior performance engineer, this post offers a compelling case study in building a custom, high-performance distributed storage system tailored to specific workload characteristics. The decision to leverage SQLite in a sharded, distributed architecture, and to implement a Redis-compatible API, demonstrates a pragmatic approach to solving complex scaling and maintenance problems. The detailed analysis of why other established solutions were unsuitable provides valuable insights into trade-offs and design considerations for specialized storage needs.
