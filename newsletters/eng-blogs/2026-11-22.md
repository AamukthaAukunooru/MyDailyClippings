## Pinterest: Rebuilding a Real-Time Abuse Platform for Modern Infrastructure

Pinterest Engineering has detailed the rebuilding of Guardian, their real-time abuse platform, to address challenges with scalability, reliability, and compliance. The original Guardian V1 used a monolithic architecture that struggled to optimize interactive querying, continuous event processing, and backfill workflows independently as traffic and use cases expanded. This led to difficulties in maintaining reliability, with slow queries affecting investigations and indexing failures causing missed evaluations. The legacy data foundation also created governance and compliance risks, and the custom-built infrastructure made it costly to evolve.

Guardian V2 transforms the system from a monolithic, in-house solution into a modular platform built on Pinterest-supported data infrastructure. The core architectural shift involved separating real-time analytics, continuous signal generation, action evaluation, downstream processing, and historical replay into distinct paths, each designed for its own scaling and operational requirements. Key decisions included preserving a unified workflow with GSQL V2, reshaping the data plane with stream splitting and pruning, rebuilding real-time analytics on StarRocks, moving asynchronous evaluation and downstream processing to FlinkSQL, and rebuilding replay and rewind on Iceberg-backed datasets. This modular approach allows for independent scaling and improved operational efficiency.

For a senior performance engineer, the takeaway is the importance of evolving from monolithic systems to modular architectures, especially for high-scale, real-time data processing. Separating concerns like analytics, processing, and replay into distinct, optimized paths with appropriate modern data infrastructure, like StarRocks, FlinkSQL, and Iceberg, is crucial for achieving greater scalability, reliability, and maintainability.

## AWS: Updates to the Well-Architected Framework

AWS has announced significant updates to its Well-Architected Framework, providing new and improved guidance across its six pillars: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability. A key change is the separation of account and organization-level best practices from workload best practices. The Framework is now organized into two areas: Well-Architected Cloud Foundations and Well-Architected Cloud Workloads.

Well-Architected Cloud Foundations consolidates environment-wide decisions, such as multi-account structure, identity, and cost governance, into forty-five best practices across seven capabilities. This allows customers to establish foundational guardrails once and refine them as their environment matures. Well-Architected Cloud Workloads now focuses on how individual workloads are designed, built, and operated, reducing the number of best practices from three hundred and seven to two hundred and sixteen without losing technical coverage. This streamlines workload reviews, making them faster to run and automate. New best practices address secure coding, cyber resilience for backup data, generative AI for operational efficiency, and measuring resource efficiency. Best practices centered on business strategy, people, and organizational processes have been retired to focus on technical decisions that can be reviewed and acted on, potentially by AI agents.

The takeaway for a senior performance engineer is to adopt this updated framework to streamline architectural reviews and ensure foundational guardrails are in place at the organizational level, allowing workload-specific reviews to focus purely on technical architecture. The inclusion of generative AI for operational efficiency and updated guidance on resource efficiency are particularly relevant for optimizing cloud performance and cost.

## Microsoft Azure SQL: Innovations at Ignite 2026

Microsoft has announced several key updates across Azure SQL, SQL database in Fabric, SQL Server, and associated tools at Microsoft Ignite 2026, focusing on simplifying modernization and innovation for applications. Azure SQL Database Hyperscale is highlighted as a modernization target, offering a cloud architecture that separates compute and storage, allowing applications to grow without database replatforming. Recent updates include support for scale to zero, or serverless auto-pause preview, making it suitable for all workload sizes starting at ten gigabytes.

A significant new feature is Hyperscale cross-database querying, now in preview. This helps unblock SQL Server migrations by reducing the need for query rewrites and application redesign for applications with cross-database dependencies. It allows combining data across databases in the same Hyperscale elastic pool for reporting, analytics, and application workflows without creating extra data copies. Security enhancements include Regex-based dynamic data masking, now generally available, and AES keys support for Transparent Data Encryption with customer-managed keys in Azure SQL Database, also generally available. Database-level managed identity in Azure SQL Database, in public preview, enables separate, passwordless access to external data for each database.

For a senior performance engineer, these updates offer powerful tools for modernizing and optimizing database performance and security. Hyperscale's architectural separation of compute and storage, combined with features like scale to zero and cross-database querying, directly addresses scalability and migration challenges. The enhanced security features are also critical for maintaining robust data protection in modern applications.

## Datadog: Scaling Metrics Aggregation with Durable State in Storage

Datadog Engineering has shared insights into how they scaled their metrics aggregation system by moving durable state into storage, addressing the challenge of managing and recovering aggregation state as metrics volume grew by roughly ten times with each generation. The core problem is that metrics aggregation must maintain correctness even with late-arriving data, duplicate deliveries, or processing interruptions, requiring the system to be stateful.

Their initial distributed aggregation service used static partitioning, where payloads with the same key always landed on the same processor. This worked well at first but became difficult for recovery, horizontal scaling, and day-to-day operations as volume increased. They redesigned the system over three generations. The first generation, with static assignment, kept historical state close to processing. The second generation moved to transferable state, improving flexibility. The third-generation design delegates responsibility for durable correctness to storage. This architecture allows the streaming layer to resume at the live edge without restoring hours of historical aggregation state, significantly improving scaling and recovery. By offloading state management to storage, the processing layer becomes more stateless and resilient.

The key takeaway for a senior performance engineer is the architectural evolution from tightly coupled stateful processing to a more decoupled, storage-centric approach for managing durable state in high-volume streaming systems. This pattern, where storage reconciles partial aggregates, duplicate deliveries, and late data, can dramatically improve scalability, recovery times, and operational complexity by allowing the processing layer to be more ephemeral and horizontally scalable.

## Swiggy: Migrating a Deep Link Engine at Scale

Swiggy Bytes has published an article on migrating their Partner App’s deep link engine at scale, a complex task given the need to ensure existing links continue to function correctly without user action. The challenge lies in how operating systems decide to open an app from a URL, which happens before any application code runs and depends on public domain verification files. The new deep link provider introduced an extra segment in the URL path, meaning old and new URLs could never be the same string.

Swiggy’s solution involved replacing the resolver SDK in the app with a single new SDK. For existing published short links, they recreated them on the new provider with the same identifier and screen-name payload. When a partner taps an old-format URL, the app extracts the ID, rebuilds it in the new format, and asks the new SDK to resolve it. For web traffic, which never used a deep-link SDK, they used HAProxy to rewrite old short-link paths into the new shape before the browser follows the new host’s CNAME. This allowed them to ship the SDK swap in one app release and then move traffic via a configuration change, ensuring old links continued to open the correct screens.

For a senior performance engineer, this case study highlights the intricacies of large-scale system migrations, particularly when external dependencies like operating system behaviors are involved. The approach of maintaining a single SDK, backfilling old data into the new system, and using edge proxies like HAProxy for URL rewriting demonstrates a robust strategy for ensuring backward compatibility and minimizing user impact during a critical infrastructure change.
