## Azure SQL Blog: MSSQL Extension for VS Code: Local Azure SQL Database Provisioning, Query Performance Dashboard, and more

The Azure SQL team has released version 1.48 of the MSSQL extension for VS Code, introducing several new public preview features aimed at streamlining database development and performance analysis. The problem addressed is the often-disconnected workflow between local development, cloud deployment, and performance monitoring.

The new features include Azure SQL Database local container provisioning, which allows developers to build and test against the Azure SQL Database engine locally without an Azure subscription or credit card. This is a significant improvement for local development, as it provides an environment that closely mirrors the cloud service. Another key addition is a local-to-cloud deployment wizard, enabling the deployment of a local database's schema, or schema and data, to a new free-tier Azure SQL Database, including compatibility checks. For performance engineers, the Query Performance Dashboard is particularly noteworthy. It integrates historical Query Store data into VS Code, allowing investigation of resource-intensive queries, wait statistics, and execution plans directly from the editor. This dashboard helps identify high CPU, memory grants, duration, execution frequency, and logical reads, and allows comparison against a baseline. Other improvements include a multi-results grid for side-by-side comparison of query results and live query statistics to monitor execution progress.

The key takeaway for a senior performance engineer is the enhanced capability for local development and direct performance analysis within VS Code. The local container provisioning reduces friction for testing Azure SQL-specific features, while the Query Performance Dashboard provides critical insights into query behavior and resource consumption, bridging the gap between development and performance tuning. This release offers tools to proactively identify and address performance bottlenecks earlier in the development cycle.

## Grab Engineering: How a shared merchant data service can degrade gracefully

Grab Engineering published a postmortem detailing how their shared merchant data service, or MDS, experienced cascading failures when its cache became unreliable. The core problem was that cache reads timing out led to increased fallback requests to the database, which then caused database pressure and further service degradation. The trigger was localized, but the system's response amplified the impact, passing more work downstream instead of containing the failure.

Grab's redesign focused on preventing this amplification. They identified three gaps: cache errors following the same path as normal misses, unbounded fallback work, and callers with different business impacts competing for shared capacity. Their solution involved five mechanisms. First, they implemented a request classification system, deriving a request class (P0 Critical, P1 Standard, P2 Deferrable) from authentication to prioritize work. Second, they introduced an admission controller with a shared token budget immediately before the database on the cache-fallback path. This ensures that if capacity is unavailable, requests are rejected promptly rather than queuing for a saturated database, with separate budgets for distinct workload roles. The overall budget is coordinated across service instances and managed through runtime configuration, with costs reflecting query shape and priority.

The central lesson for a senior performance engineer is that a fallback mechanism is only effective if its work is bounded. Uncontrolled fallbacks can quickly overwhelm downstream dependencies, leading to cascading failures. Implementing explicit admission control, prioritizing requests based on business criticality, and bounding work sent to shared resources are crucial design principles for building resilient, gracefully degrading systems.

## Cloudflare Blog: How Cloudflare WAF helps protect against Java4Shell (CVE-2026-114938)

Cloudflare has published details on "Java4Shell," a critical memory-corruption vulnerability, CVE-2026-114938, found in the Base64 decoder of OpenJDK. Disclosed on November seventeenth, this flaw scores 9.2 out of 10 on the CVSS 4.0 scale. The vulnerability allows a remote, unauthenticated attacker to send malformed Base64 data to a Java application, overwriting memory next to the decoded output. This can lead to heap memory leaks and remote code execution.

The bug resides in the handwritten assembly code that handles the final characters of Base64 input, specifically when padding characters are misplaced, leading to a negative output length calculation and an out-of-bounds write. Cloudflare demonstrated pre-authentication remote code execution against applications like Keycloak, Atlassian Jira, and Jenkins, and post-authentication against Apache Kafka and Elasticsearch. The vulnerability affects OpenJDK 17.0.6 or newer, including various distributions, and x86-64 processors with AVX-512 VBMI support. ARM64 processors are not affected.

Cloudflare has released new WAF rules to detect malformed Base64 input patterns associated with this vulnerability, enabled by default in "Log" mode to avoid disrupting legitimate traffic. These rules provide an additional layer of defense but are not a replacement for patching. The only complete fix is to update the Java runtime. For those unable to patch immediately, two JVM startup flags, -XX:-UseBASE64Intrinsics and -XX:UseAVX=2, can disable the vulnerable code paths, though they may impact performance.

The key takeaway for a senior performance engineer is the immediate need to assess Java application environments for this critical vulnerability, especially those running OpenJDK 17.0.6 or newer on x86-64 processors with AVX-512. Prioritize patching Java runtimes, and if immediate patching is not possible, consider the JVM flags as a temporary mitigation, understanding their potential performance implications.

## AWS Architecture Blog: Resilience testing your agents on Amazon Bedrock AgentCore

The AWS Architecture Blog discusses the importance of resilience testing for AI agents, specifically on Amazon Bedrock AgentCore. The problem addressed is that in production, AI agent tools often fail due to timeouts, incorrect API data, or silently dropped fields. Without testing, assumptions are made about how agents handle these failures, potentially leading to confident but corrupted answers, raw errors to users, or silent failures without alerts.

AWS proposes using AWS Fault Injection Service, or AWS FIS, to test how Strands agents handle tool-level faults. The goal is to determine what the agent does when a tool fails or returns incorrect data, and whether these failures are detectable. The solution involves AWS FIS running an SSM Automation action to inject faults directly inside the agent, before or after the tool call, while the agent continues serving live traffic. Two types of faults are injected: pre-hook faults, which cancel the tool call and return an error (e.g., timeout, network error), and post-hook faults, which let the tool run but then corrupt its response (e.g., truncate fields, corrupt values). The latter is considered more dangerous as the agent might confidently use bad data.

Engineers are encouraged to define a measurable resilience hypothesis before running experiments, outlining expected agent behavior and detection mechanisms. For example, "When tool calls for [agent] are [canceled | corrupted], we expect it to [observable behavior] and to fail safe rather than fabricate."

The key takeaway for a senior performance engineer is the critical need to proactively test the resilience of AI agents, particularly how they handle failures and corrupted data from their underlying tools. Relying on assumptions about agent behavior in the face of dependency failures is risky. Implementing fault injection testing, as described, allows for empirical validation of an agent's resilience and observability, ensuring it fails safely and alerts operations teams when necessary.

## Meta Engineering: How Meta Uses AI Agents to Scale ML Innovations Across Ads Ranking Models

Meta Engineering shares how they use AI agents to efficiently propagate machine learning innovations across their large and diverse fleet of ads ranking models. The challenge is that while ML researchers continuously develop "techniques" to improve models, adapting these innovations to each model's unique architecture, data, and constraints is effort-intensive and doesn't scale. The speed of propagation is crucial because ML techniques have a limited shelf life.

Meta's solution involves a "technique propagation" system powered by AI agents. Since agents began driving execution in March two thousand twenty-six, they handle over sixty percent of all technique propagation, leading to an estimated three times greater engineering productivity, a median four times reduction in training compute, and over forty-five million dollars in compute savings by the end of the year. The system has three capabilities: Discovery, which identifies and prioritizes technique-model candidates; Generalization, which adapts proven techniques to work on models they weren't originally designed for, often once per template for models built from shared templates; and Adoption, which manages experiments, asynchronous training runs, monitoring, and failure recovery.

AI agents supercharge these capabilities by handling judgment-heavy, non-deterministic decision-making. They combine large language model-based reasoning with specialized ML tooling to decide which adaptations to try, diagnose failures, and automatically mitigate them. This approach allows Meta to scale the propagation of innovations much faster than manual adaptation, ensuring that new techniques reach applicable models within weeks.

For a senior performance engineer, the key takeaway is the power of automation and AI agents in scaling complex engineering workflows, even in areas like ML model optimization. The principles of standardizing components (like model templates), automating deterministic steps, and then using intelligent agents for non-deterministic decision-making can significantly boost productivity and efficiency, leading to substantial compute savings and faster innovation cycles.

## Shopify Engineering: Building secure mobile apps in the agentic era

Shopify Engineering discusses how they are scaling mobile application security in an era of rapidly increasing code throughput, driven by AI agents. The problem is that code throughput in their mobile apps has increased eleven times compared to the previous year, with approximately four hundred thirty-four thousand lines of code changed per week during a twelve-week rewrite of the Shopify app. This rapid pace, combined with a rise in industry-wide vulnerabilities, necessitated a new approach to security.

Shopify built a system centered around attack surface maps, focused AI reviews, and continuous learning from vulnerabilities. For each app, they maintain a map of security-sensitive items, grouped by surfaces like deep links, WebViews, and stored data. Each item has a verdict and a link to the code. This map is generated by a set of "skills," derived from OWASP's mobile app security standards and internal learnings from past incidents. These skills describe what to list, what constitutes good security, and what to check. To keep reviews manageable, each skill first takes a complete inventory, and then a model reviews one item at a time with only the relevant code.

The system learns from every incident: when a bug is fixed, that class of problem is added to the skills, ensuring future code is checked against it. Daily, the latest frontier models review code changes, update the attack surface map, and dig into individual changes for vulnerabilities using cybersecurity models. They also monitor external security news, checking industry-wide vulnerabilities against their map and code, only alerting the team when something affects them.

The key takeaway for a senior performance engineer is the innovative approach to scaling security in a high-velocity development environment. By mapping the attack surface, codifying security knowledge into "skills," performing granular AI-driven reviews, and continuously learning from incidents, Shopify ensures that security keeps pace with rapid code changes. This proactive and automated approach to security, especially with the integration of AI agents, is crucial for maintaining application integrity without becoming a bottleneck to development speed.
